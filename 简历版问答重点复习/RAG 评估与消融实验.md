## 四、RAG 评估与消融实验

### 32. 你说的 RAGAS 是直接接入官方库吗？

我们项目不是直接调 Python RAGAS 官方库，而是参考它的指标定义，在 Java 评估服务里自己实现的。我觉得这样做主要有几个好处：

首先是技术栈统一。项目后端全是 Java，如果要调 Python 库就得搞进程通信、环境管理这些额外的东西，维护成本挺高的。自己用 Java 实现的话，可以直接复用现有的 RagTrace、配置管理和异常处理机制，所有数据都在一个服务里，query、扩展 query、召回上下文、最终答案、Token、延迟、错误信息这些都能统一保存，调试起来也方便。

其次是可控性更强。我们可以加入超时控制、规则评分兜底、降级标记这些逻辑，评估本身也可能超时或不稳定嘛，所以四项指标可以并行执行，单项设置安全等待时间，异常的话返回可识别的失败值（比如 -1），报告里明确区分真实评分和缺失评分，不会把失败样本混进平均分里。

关于四项指标：Faithfulness 关注答案中的事实是否能被检索上下文支持，主要用来发现幻觉；Answer Relevancy 关注回答是否真正回应了问题；Context Precision 关注返回上下文里相关内容的比例，反映噪音程度；Context Recall 关注应该出现的证据是否被召回了，反映漏召回情况。前两项偏生成质量，后两项偏检索质量，组合起来才能定位问题在哪一层。

以 Faithfulness 为例，我们不是简单让模型输出一个总分，而是先让评估模型把答案拆成原子声明，再逐条判断是否被上下文支持，按支持比例聚合；解析失败时做规则或宽松匹配兜底，但会标记评估降级。

需要强调的是，这套评估不是线上绝对正确率。LLM judge 本身有偏差，Ground Truth 也可能不完整，所以我们主要用它做同一数据集、同一配置下的相对比较，再结合人工抽样、规则指标和多次运行方差来综合判断。

**可能追问：**

- **为什么不直接用官方 Python 库？**：项目是 Java 技术栈，调用 Python 需要额外的进程通信和环境管理，增加复杂度。自研可以直接复用 Java 服务的 trace、配置和异常处理，所有数据在一个服务里统一管理，调试和维护都更方便。

- **自研评估和官方库结果一致吗？**：指标定义是相同的，但实现细节（Prompt 怎么写、解析逻辑、超时处理）可能有差异。我们应该通过相同样本对比验证一致性，如果偏差太大就需要调整实现细节。

- **评估结果可以直接当线上指标吗？**：不能。LLM judge 有偏差和随机性，主要用于相对比较（方案 A vs B）和回归检测，不能解释成绝对准确率。线上质量还需要结合用户反馈、人工抽样等多种方式验证。

**补充细节：**

`EvaluationService` 实现四项指标评估，每项都调用 LLM 并解析结构化输出：

```java
// 并行执行四项评估，减少总耗时
CompletableFuture<Double> faithfulness = evaluateFaithfulness(query, answer, context);
CompletableFuture<Double> relevancy = evaluateRelevancy(query, answer);
CompletableFuture<Double> precision = evaluatePrecision(query, context);
CompletableFuture<Double> recall = evaluateRecall(query, context, groundTruth);

// 单项超时返回特殊值 -1，而非默认分数
faithfulness.orTimeout(30, TimeUnit.SECONDS).exceptionally(ex -> -1.0);
```

报告格式示例：

```text
总样本: 50
有效样本: 45
  Faithfulness 均值: 0.82
  Answer Relevancy 均值: 0.78
失败样本: 5 (3 个超时, 2 个解析失败)
```

验证方法：准备标注样本（问题、答案、上下文、预期证据），手工评估和 LLM judge 结果对比，计算一致率；不一致样本分析是评估 Prompt 问题还是标注问题。

### 33. 四个指标分别看什么？

我觉得这四项指标各有侧重，组合起来才能完整诊断 RAG 系统的问题。

首先是 Faithfulness，它看答案中的事实是否能被检索上下文支持，主要用来发现幻觉。如果 Faithfulness 低，说明模型在瞎编，没有基于检索到的证据生成答案。

然后是 Answer Relevancy，它看答案是否真正回应了问题，避免答非所问。有时候答案虽然基于证据，但跑题了，这时候 Faithfulness 可能挺高，但 Relevancy 就低了。

Context Precision 看的是召回上下文中相关内容的比例，反映噪音程度。如果 Precision 低，说明召回了太多无关内容，这时候需要精排或者调整 TopK。

Context Recall 看的是应该出现的证据是否被召回了，反映漏召回情况。如果 Recall 低，说明关键证据根本没召回上来，这是检索策略的问题。

前两个指标更偏生成质量，后两个更偏检索质量。四项结合才能判断问题来自漏召回、召回噪音还是模型生成偏离证据。比如：

- Context Recall 低 → 关键证据没召回，检索策略需要优化（可能需要 Query 扩展、调整 TopK、或者改进向量检索）
- Context Precision 低 → 召回了太多无关内容，需要精排或调 TopK
- Faithfulness 低但上下文正确 → 模型没有基于证据生成，可能是 Prompt 或模型问题
- Answer Relevancy 低 → 答案虽然基于证据但没回应问题核心，可能是 Prompt 引导不够明确

项目中通过 `EvaluationService` 分别计算四项指标，每项都调用 LLM 并解析结构化输出。报告按指标聚合均值、有效样本数和失败样本数，便于定位具体问题层。

重要的是，这四项不应该简单平均成一个综合分，因为它们反映不同维度的问题，需要分别分析。比如我可能愿意接受稍低的 Context Precision（多召回一些内容）来换取更高的 Context Recall（不漏掉关键证据），这是一个权衡。

**可能追问：**

- **Context Precision 和 Recall 有什么区别？**：Precision 看召回内容里有多少是相关的（噪音控制），Recall 看应该召回的内容有多少被召回了（覆盖完整性）。这是经典的查准率和查全率的关系，通常需要在两者之间做权衡。

- **Faithfulness 和 Answer Relevancy 有什么区别？**：Faithfulness 看答案是否基于证据（不瞎编），Relevancy 看答案是否回应问题（不跑题）。一个答案可能完全基于证据但答非所问，也可能回应了问题但加了一些证据里没有的内容。

- **四项指标都高就是好系统吗？**：不一定。还要看延迟、Token、成本和稳定性。高质量但慢、贵或经常超时的系统也不适合生产环境。我们需要在质量、成本、延迟之间找到平衡点。

**补充细节：**

每个指标的评估都可能失败或超时，因此报告应区分有效评分和缺失评分：

```text
实验配置：向量检索 + BM25 + RRF + Rerank
总样本: 50

Context Precision:
  有效样本: 48, 均值: 0.85
  失败样本: 2 (超时)

Context Recall:
  有效样本: 50, 均值: 0.78
  失败样本: 0

Faithfulness:
  有效样本: 45, 均值: 0.82
  失败样本: 5 (3 个超时, 2 个解析失败)

Answer Relevancy:
  有效样本: 47, 均值: 0.88
  失败样本: 3 (超时)
```

50 个样本中 5 个 Faithfulness 评估超时，应该报告"有效样本 45，均值 0.82，失败 5"，而不是把超时当 0 或 0.5 混入均值，那样会严重扭曲结果。

验证方法：人工标注部分样本的四项指标预期值，与 LLM judge 结果对比；不一致时分析是评估 Prompt 问题、模型理解偏差还是人工标注问题。

### 34. Faithfulness 怎么评估才更可解释？

我认为比起直接让模型输出一个总分，更稳的方式是先把答案拆成原子声明，再判断每条声明是否被上下文支持，最后按支持比例聚合。这样做的好处是过程可解释，失败时能看到具体哪条声明出了问题。

项目中 Faithfulness 评估分两步走：

第一步，让 LLM 把答案拆分成独立的事实声明列表。比如答案是"接口返回 404，需要检查路由配置"，应该拆成两条独立声明："接口返回 404" 和 "需要检查路由配置"。每条声明必须是独立的、可验证的事实，不能是"系统很好"这种主观评价。

第二步，逐条判断每个声明是否能在检索上下文中找到支持证据。对每条声明，评估模型返回 `supported: true/false` 和具体的支持依据（哪一段上下文支持了这个声明）。最终 Faithfulness 分数 = 被支持声明数 / 总声明数。

这种方式比直接打分透明多了。如果评估结果不理想，我能看到具体是哪条声明不被支持，是因为上下文里确实没有相关证据，还是评估模型理解出了偏差。

当然，声明拆分或判断可能失败。这时候我们会降级到规则匹配：检查答案关键词是否出现在上下文中，或者宽松判断为 0.5 并标记降级。重要的是保留原始声明列表和判断依据，便于人工抽样验证评估质量。

需要强调的是，这类 LLM judge 仍然不是绝对真值。它有偏差和随机性，所以我们主要把它用于同一测试集、同一配置下的相对比较，并保留原始声明和证据，方便后续人工抽样验证。

**可能追问：**

- **声明拆分失败怎么办？**：降级到规则评分（比如计算关键词覆盖率）或返回失败标记，不强行给出 0 或 1。报告中明确区分正常评分和降级评分，保证结果可追溯。

- **为什么不直接让模型打 0-1 分？**：直接打分缺少中间过程，无法解释为什么给这个分。拆分声明后可以看到具体哪些事实被支持、哪些不被支持，出问题时能快速定位是检索问题还是生成问题。

- **人工怎么验证评估质量？**：抽样查看声明拆分是否合理、判断依据是否准确，统计与人工标注的一致率。不一致样本需要分析是评估 Prompt 的问题还是标注问题，然后针对性调整。

**补充细节：**

原子声明示例：

```text
原始答案：
"接口超时可能是网络问题或服务端负载高，建议检查日志"

拆分后的原子声明：
1. "接口超时"
2. "可能原因：网络问题"
3. "可能原因：服务端负载高"
4. "建议检查日志"

逐条判断：
1. 支持 ✓ (上下文: "请求在 30s 后超时")
2. 支持 ✓ (上下文: "可能的原因包括网络延迟...")
3. 支持 ✓ (上下文: "或者服务端负载过高")
4. 不支持 ✗ (上下文中未提及日志检查)

Faithfulness = 3/4 = 0.75
```

评估记录应包含：

```java
{
  "answer": "原始答案...",
  "claims": ["声明1", "声明2", ...],
  "support": [
    {"claim": "声明1", "supported": true, "evidence": "支持证据..."},
    {"claim": "声明2", "supported": false, "evidence": null}
  ],
  "score": 0.75,
  "status": "SUCCESS"  // 或 PARSE_ERROR, TIMEOUT, MODEL_ERROR
}
```

验证方法：人工标注部分答案的原子声明和支持情况，与 LLM 拆分结果对比；Faithfulness 分数与人工判断的相关性应在 0.7 以上，如果低于这个阈值说明评估质量有问题，需要调整评估 Prompt。

### 35. 为什么评估任务需要超时和默认值？

我觉得这个问题的核心是要理解：默认值的作用是让批量任务能结束，不是伪造一个看起来正常的分数。

评估任务调用外部 LLM，可能会超时、解析失败、或者模型本身异常。如果不设超时，一个样本卡住就会导致整个批量评估永远跑不完。但更重要的是，处理失败的方式不能简单粗暴。

我们的做法是，每条评估结果同时保存多个字段：score（分数）、status（状态）、error（错误信息）、duration（耗时）和 evaluator version（评估器版本）。状态包括：
- `SUCCESS`：正常完成
- `TIMEOUT`：超时
- `PARSE_ERROR`：解析失败
- `MODEL_ERROR`：外部模型异常

关键是聚合的时候不能把超时样本全部当成 0.5，然后和真实评分混成一个平均数。这样做会严重扭曲结果，而且掩盖评估系统本身的问题。

更合理的报告至少要给出：有效样本数、失败样本数、各指标均值（只基于有效样本）和失败率。如果某组实验有效样本不足（比如 50 个样本里 20 个失败），就应该标记结论不可靠，而不是硬着头皮算一个平均分出来。

比较方案 A/B 时，还要确保两边有效样本口径一致。如果方案 A 有 45 个有效样本，方案 B 只有 30 个，直接比较均值是不公平的，要么单独报告缺失差异，要么只对比共同有效的样本。

另外，规则评分也要与 LLM 指标分开保存。回答为空、上下文为空、延迟超阈值、Token 超预算这些属于确定性的系统问题，不能完全交给 LLM judge。最终可以生成一个综合分，但必须保留子分数和原始证据，避免综合分掩盖”答案语义不错但检索全空”这种问题。

项目中我们对四项指标并行评估，单项设置超时（比如 30 秒），超时返回特殊值 `-1` 并标记状态为 `TIMEOUT`。报告生成时分别统计有效评分均值、失败数和失败率，不把失败样本混入均值计算。

**可能追问：**

- **超时应该设置多长？**：根据评估模型的调用延迟确定，一般 10-30 秒。过短会增加失败率，过长会拖慢批量评估。我们通常先跑几个样本观察平均耗时，然后设置为 P95 耗时的 2 倍作为超时阈值。

- **失败样本怎么处理？**：记录失败原因和样本 ID，人工排查是评估服务问题（比如网络不稳定）、模型不稳定（比如返回格式不一致）还是样本异常（比如答案过长导致超时）。修复问题后重新评估失败样本，而不是直接丢弃或给默认分。

- **为什么不能把失败当 0 分？**：0 分表示质量很差，失败表示无法评估，这是两个完全不同的概念。混在一起会低估真实质量并掩盖评估系统本身的问题。如果失败率很高，说明评估系统有问题，需要优先修复，而不是继续用错误的数据做决策。

**补充细节：**

评估结果存储格式：

```java
{
  “sampleId”: “qa-001”,
  “score”: 0.82,
  “status”: “SUCCESS”,  // 或 TIMEOUT, PARSE_ERROR, MODEL_ERROR
  “error”: null,
  “duration”: 2350,  // 毫秒
  “evaluatorVersion”: “v1.2”,
  “timestamp”: “2026-08-27T10:30:00Z”
}
```

报告格式示例：

```text
实验：Query扩展 + 向量检索 + BM25 + RRF
总样本: 50

Faithfulness:
  有效样本: 45 (90%)
  均值: 0.82 ± 0.08
  失败样本: 5 (10%)
    - 超时: 3
    - 解析失败: 2

Context Recall:
  有效样本: 48 (96%)
  均值: 0.78 ± 0.12
  失败样本: 2 (4%)
    - 模型异常: 2

结论可信度: 高 (有效样本率 > 85%)
```

规则评分示例：
- 答案长度 < 10 字符 → 标记为无效
- 上下文为空 → Context Precision/Recall 标记为 N/A
- 延迟 > 10 秒 → 系统性能扣分（独立于 LLM judge）

规则分数和 LLM judge 分数分开保存，最终报告同时展示两者，避免混淆。

验证方法：故意构造超时场景（Mock 慢模型）、解析失败场景（返回非法 JSON），断言系统正确标记失败状态且不影响其他样本的评估；报告应明确区分有效样本和失败样本统计，失败率过高时给出警告。

### 36. Skill 系统是干什么的？

Skill 系统主要是为了让 Agent 的专业能力能够**模块化、按需扩展**，而不是把所有能力都写死在 Agent 核心代码里。

比如 Agent 本身可以提供知识库检索、创建笔记、网页抓取这些基础能力，但如果以后要增加代码审查、SQL 生成、数据分析等专业能力，如果每增加一种能力都修改 Agent 核心逻辑，维护成本会比较高。

所以我把这些专业能力封装成独立的 Skill。Skill 包主要包含 `manifest.json`、Prompt 模板、示例以及可选的工具定义。用户导入 Skill 后，系统会根据 `capabilities` 等信息判断它适合什么任务，Agent 执行对应任务时再动态加载。

这样 Agent 核心保持比较稳定，专业能力可以独立扩展，也方便用户或者社区贡献新的 Skill，而不需要修改核心代码。

**可能追问：**

- **Skill 和 Tool 有什么区别？**：Tool 解决的是“Agent 能做什么具体操作”，比如搜索、创建笔记；Skill 更像是“怎么专业地完成一类任务”，主要提供 Prompt、能力描述和工具组合。
    
- **Skill 怎么保证安全？**：当前 Skill 本身不包含可执行代码，主要是 Prompt 和工具声明。真正的工具执行仍然由系统控制，并且会经过工具白名单和权限限制，所以不能因为导入一个 Skill 就直接执行任意代码。
    
- **Skill 和普通 Prompt 模板有什么区别？**：普通 Prompt 主要是一段提示词，而 Skill 除了 Prompt，还包含标准化的能力描述、版本和可选工具定义，可以被系统注册、匹配和按任务动态加载。
    

**补充细节：**

可以把 Skill 理解成一个**专业能力包**：

```text
Skill
├── manifest.json    → 我是谁、能做什么
├── prompt/          → 怎么专业地完成任务
├── examples/        → 给模型参考的示例
└── tools/           → 我需要哪些工具
```

例如：

```text
code-review Skill
        ↓
“我是代码审查专家”
        ↓
关注安全、性能、可维护性
        ↓
可以使用相关工具
```

所以它不是重新造一个 Agent，而是在**已有 Agent 上增加一层专业能力**。

核心可以记成一句话：

> **Skill 是对专业能力的声明式封装，让 Agent 可以按需加载能力，而不是把所有能力硬编码进 Agent。**


### 37. Skill 怎么和 Agent 结合？

Skill 和 Agent 的结合主要通过**任务匹配 + 动态加载**实现。

用户发起任务后，Supervisor 首先分析任务类型。如果任务和某个 Skill 的 `capabilities` 匹配，就可以加载这个 Skill。加载之后，Skill 的 Prompt 会加入当前 Agent 的执行上下文，对 Agent 的行为进行专业化约束；如果 Skill 声明了相关工具，也会加入当前任务允许使用的工具范围。

比如用户说“帮我审查这段代码”，Supervisor 判断这是 `code_review` 类型任务。如果系统里有 `code-review` Skill，就加载它的 Prompt，让 Agent 按照代码审查的规则执行。

用户也可以显式指定 Skill，这种情况下就不需要自动匹配，直接加载指定 Skill。

一个比较重要的设计是，**Skill 是任务级作用域的**。当前任务结束以后，Skill 的 Prompt 和工具配置就不会继续影响其他任务，这样可以减少不同 Skill 之间互相污染的问题。

**可能追问：**

- **多个 Skill 都匹配怎么办？**：可以按照优先级进行选择，比如用户显式指定的 Skill 优先；如果多个 Skill 都符合，也可以由 Supervisor 决定，避免无条件全部加载。
    
- **Skill 可以调用另一个 Skill 吗？**：当前不支持 Skill 嵌套。Skill 主要负责当前任务的能力增强，如果需要组合多个专业能力，可以交给 Supervisor 拆成多个子任务。
    
- **Skill 会增加 Token 消耗吗？**：会。Skill 的 Prompt 注入后会增加上下文长度，所以 Skill Prompt 应该尽量精简，只保留当前任务真正需要的专业规则。
    

**补充细节：**

整个过程可以理解成：

```text
用户：
“帮我审查这段代码”
       ↓
Supervisor
       ↓
判断任务类型：code_review
       ↓
匹配 Skill
       ↓
加载 code-review Skill
       ↓
Prompt + 工具声明
       ↓
当前 Agent
       ↓
执行代码审查
       ↓
任务结束
       ↓
Skill 作用域结束
```

这里要注意一个概念：

**Skill 不是 Agent 本身。**

更准确地说：

```text
Agent
= 负责理解目标、决策和执行

Skill
= 给 Agent 提供某一类专业任务的指导和能力配置

Tool
= Agent 实际调用的具体操作能力
```

所以可以记成：

> **Agent 决定怎么做，Skill 告诉它某类任务应该怎么专业地做，Tool 负责真正执行操作。**


### 38. Skill Center 怎么实现的？

Skill Center 在当前项目里并不是一个复杂的应用市场，主要可以理解成一个**Skill 清单 + 安装管理服务**。

后端提供 Skill 清单接口，返回 Skill 的名称、版本、描述、作者、标签、下载地址以及安装状态。前端的 Skill 管理页面展示这些信息，用户选择 Skill 后调用安装接口。

安装时，后端把 Skill 包下载到临时目录，解压后校验 `manifest.json` 和必要字段，校验通过后保存到 Skill 目录，并把 Skill 的元信息注册到数据库。之后 Agent 就可以查询已安装的 Skill 并进行匹配和加载。

版本管理主要通过 `manifest.json` 中的 `version` 字段完成，安装时保存版本信息，后续可以比较本地版本和市场版本来判断是否需要更新。

**可能追问：**

- **Skill 版本怎么管理？**：在 `manifest.json` 中维护版本号，数据库保存当前安装版本，更新时比较版本号，再下载新版本替换。
    
- **Skill 有依赖怎么办？**：当前 Skill 是自包含的，不支持 Skill 之间的依赖。如果未来需要组合依赖，可以在 manifest 中增加 `dependencies` 字段，再设计依赖解析机制。
    
- **Skill Center 真的是一个完整的市场吗？**：目前不是，更准确地说是一个轻量的 Skill 管理和分发机制。真正的市场还需要增加后台审核、发布、版本管理和安全扫描等能力。
    

**补充细节：**

你可以把 Skill Center 理解成：

```text
Skill Center
    ↓
Skill 清单
    ↓
用户选择
    ↓
下载安装包
    ↓
manifest 校验
    ↓
保存 Skill
    ↓
注册数据库
    ↓
Agent 可以使用
```

所以当前实现的核心并不是“做了一个像 npm 一样复杂的包管理平台”，而是：

> **定义统一的 Skill 包格式，然后提供发现、安装、注册和使用这几个基本能力。**

还有一个面试时非常值得强调的点：

> **Skill 的安全边界在系统，而不是 Skill 包自己。**

也就是说，即使 Skill 声明了某个工具：

```text
Skill
 ↓
声明：“我需要执行 SQL 的工具”
 ↓
系统检查
 ↓
权限 / 白名单 / 参数校验
 ↓
Tool 才真正执行
```

而不是：

```text
导入 Skill
 ↓
Skill 自己执行任意代码
```

这也是为什么你可以把当前 Skill 定位成**声明式能力扩展**，而不是传统意义上可以随便执行代码的插件系统。


### 39. 回归测试的目标是什么？

核心目标是在改动代码、配置或模型之后，快速发现质量退化，避免把退化版本推到生产环境。

RAG 系统经常需要调整检索配置、Prompt、模型版本、TopK、rerank 开关等。每次改动之后，不能只凭几次主观体验就上线，应该跑一遍固定测试集，对比改动前后的指标变化。

项目里的回归测试会保存一批固定的测试问题、预期答案和评估配置。每次改动之后，用新配置跑完整个测试集，生成报告，对比四项指标（Context Precision、Context Recall、Faithfulness、Answer Relevancy）、延迟、Token 和失败率。

如果发现某项指标明显下降（比如 Faithfulness 从 0.85 降到 0.70），就要排查是哪个改动导致的，评估是否可以接受这个代价。有时候为了降低延迟可能会牺牲一点质量，这种权衡需要明确。如果发现延迟或 Token 大幅增加，也要评估是否值得。

需要强调的是，回归测试不是为了证明系统完美，而是为了在改动之后快速发现问题。它是质量保障的最后防线，帮助我们在上线前及时发现和修复问题。

**可能追问：**

- **测试集怎么构建？**：从真实用户问题中抽样，覆盖常见场景、边界情况和历史失败案例。人工标注预期答案或关键证据，作为评估基准。测试集应该定期更新，加入新的失败案例，保持对系统弱点的覆盖。

- **多久跑一次回归测试？**：每次改动检索配置、Prompt、模型版本或工具逻辑之后都应该跑。理想情况下集成到 CI/CD 流程，代码合并前自动触发并生成报告。如果测试集很大，可以先跑快速冒烟测试，通过后再跑完整测试。

- **指标下降多少算退化？**：没有绝对标准，要根据业务容忍度定。通常 Faithfulness 和 Answer Relevancy 下降超过 5% 就要排查，因为这两项直接影响用户体验；Context Precision 和 Recall 下降超过 10% 也要关注。如果是为了优化延迟而牺牲质量，需要明确说明权衡点。

**补充细节：**

回归测试流程：

```text
改动代码/配置/模型
   ↓
触发回归测试（手动或自动）
   ↓
跑固定测试集（20-50 个样本）
   ↓
生成报告
  - 四项指标对比
  - 延迟 P50/P95 对比
  - Token 平均值对比
  - 失败率对比
   ↓
对比基线（改动前的结果）
   ↓
发现退化 → 排查原因 → 修复或回滚
未发现退化 → 继续上线流程
```

测试集结构示例：

```json
[
  {
    "id": "test-001",
    "query": "502 错误怎么排查",
    "expectedEvidence": ["网关超时", "上游服务"],
    "expectedAnswer": "检查上游服务状态和网关配置",
    "category": "故障排查"
  },
  {
    "id": "test-002",
    "query": "如何优化 SQL 查询",
    "expectedEvidence": ["索引", "EXPLAIN"],
    "expectedAnswer": "使用 EXPLAIN 分析执行计划，添加合适索引",
    "category": "性能优化"
  }
]
```

报告示例：

```text
回归测试报告 - 2026-08-27

配置变更：TopK 从 5 增加到 10

结果对比：
                 基线      当前      变化
Context Recall   0.78     0.85     +9%  ✓
Context Precision 0.82    0.75     -8%  ⚠
Faithfulness     0.85     0.84     -1%  ✓
Answer Relevancy 0.88     0.87     -1%  ✓
延迟 P95         2.3s     3.1s    +35%  ⚠
Token 平均       1200     1800    +50%  ⚠

结论：召回提升明显，但精度下降、延迟和成本增加。
建议：根据业务场景权衡，或尝试增加 rerank 改善精度。
```

核心原则：

> **回归测试是质量保障的最后防线。改动之后必须跑测试，对比基线，发现退化及时修复或权衡。**

### 40. 消融实验和回归测试有什么区别？

我觉得这两者的目标不同：消融实验是为了搞清楚每个组件的贡献，回归测试是为了防止质量退化。

消融实验主要用在优化阶段。你想知道 Query 扩展、向量检索、BM25、RRF、rerank 这些组件各自贡献了多少，哪些是必要的、哪些在特定场景下可以关闭。做法是基于完整流水线配置（Query扩展 + BM25 + 向量检索 + RRF + rerank 全开）作为基线，然后逐个关闭组件，观察指标变化。每一步只改一个变量，这样才能归因到具体组件。

比如我想验证 rerank 的价值，就跑两组实验：基线（全开）和关闭 rerank，对比 Context Precision、延迟和成本变化。如果想知道向量检索是否必要，就跑基线和关闭向量检索（只保留 BM25），对比召回率和语义理解能力。如果想验证 Query 扩展的收益，就跑基线和关闭 Query 扩展，对比召回覆盖率和噪音比例。

回归测试主要用在开发和维护阶段。每次改动代码、调整配置、升级模型之后，跑一遍固定测试集，对比改动前后的指标。目的是快速发现"我这次改动是不是把系统搞坏了"，而不是搞清楚各组件贡献。

两者的测试集可以共用，但侧重点不同。消融实验需要控制变量，一次只改一个组件，多次运行对比；回归测试是改动前后的一次对比，关注整体质量有没有退化。

消融实验的结果可以指导架构决策，比如"rerank 提升精度 15% 但延迟增加 35%，性能敏感场景可以关闭"或者"关闭向量检索后召回率下降 27%，说明向量检索是必要的，不能随便关"或者"Query 扩展提升召回 9% 但噪音增加 3%，需要结合 rerank 一起使用才能发挥价值"。回归测试的结果用于质量把控，比如"这次 Prompt 调整导致 Faithfulness 下降 8%，必须回滚"。

**可能追问：**

- **消融实验怎么设计？**：先固定测试集、文档版本、模型、Prompt 和评估配置。基线选完整流水线配置（全开）。然后设计实验组：关闭 Query 扩展、关闭 rerank、关闭向量检索、关闭 RRF。每组跑完整测试集，保存四项指标、延迟、Token、降级率。分析时不能只看综合分，要看各指标变化并归因到具体组件。

- **回归测试和消融实验能合并吗？**：可以共用测试集和评估逻辑，但触发时机和对比方式不同。消融实验是一次性多组对比（基线 vs 各关闭组件的配置），回归测试是改动前后两组对比（旧版本 vs 新版本）。

- **没有测试集能做消融实验吗？**：不能。消融实验需要稳定的测试集来对比各组件效果。没有测试集时，只能说"实现了消融实验框架"，不能声称"rerank 提升了 X%"或"关闭向量检索导致召回下降 Y%"，因为没有数据支撑。

**补充细节：**

消融实验示例：

```text
目标：评估各检索组件的必要性和贡献

测试集：50 个标注问题

实验配置：
1. 基线（完整流水线）：Query扩展 + BM25 + 向量 + RRF + rerank, TopK=5
2. 实验A：关闭 Query 扩展
3. 实验B：关闭 rerank
4. 实验C：关闭向量检索（仅 BM25）
5. 实验D：关闭 RRF（多路简单合并）

结果对比：
                基线    实验A   实验B   实验C   实验D
Context Recall  0.82    0.75   0.83    0.60    0.80
Context Precision 0.82  0.84   0.70    0.75    0.75
Faithfulness    0.88    0.86   0.85    0.82    0.86
Answer Relevancy 0.88   0.87   0.86    0.80    0.87
延迟(s)         2.6     2.4    1.9     1.2     2.5
Token          1500    1300   1500    1000    1500

结论：
- 关闭 Query 扩展：召回下降 9%，精度提升 2%（噪音减少），成本降低 13%
  建议：精确查询场景可以关闭，探索性查询保留
- 关闭 rerank：精度下降 15%，延迟降低 27%
  建议：性能敏感场景可以关闭，质量要求高时必须保留
- 关闭向量检索：召回下降 27%，答案相关性下降明显
  建议：向量检索是必要的，不能关闭
- 关闭 RRF：精度下降 9%，延迟影响小
  建议：RRF 融合是必要的，保留
```

回归测试示例：

```text
目标：验证 Prompt 调整未导致退化

改动：优化系统 Prompt，引导模型更简洁回答

结果对比：
                改动前   改动后   变化
Faithfulness    0.85     0.82    -3%  ✓
Answer Relevancy 0.88    0.91    +3%  ✓
延迟            2.3s     2.1s    -9%  ✓
Token           1500     1200   -20%  ✓

结论：Faithfulness 轻微下降可接受，
回答相关性和成本都有改善，通过测试。
```

核心原则：

> **消融实验搞清楚各组件贡献，指导架构决策。回归测试防止质量退化，保障上线质量。两者目标不同，但可以共用测试集和评估逻辑。基线应该是完整流水线配置（全开），消融实验通过逐个关闭组件来验证每个组件的必要性。**

### 41. 评估结果波动很大，怎么排查？

我觉得评估结果波动的排查应该从三个层面入手：数据层、模型层和评估层。

首先要确认测试集、知识库版本和 Ground Truth 有没有变化。这个看起来很基础，但实际上很容易被忽略。比如知识库里新增或删除了文档，召回的 chunk 就会变化；测试集被别人误改了，评估基准就不一样了。所以第一步我会对比前后召回的 chunk ID 列表，如果 ID 都变了，那肯定是检索层出问题了。

然后是模型配置层面。模型版本、温度参数、Prompt 调整都会影响答案的表述。即使召回的证据一样，温度从 0.7 改成 0.3，答案的风格可能就完全不同。所以我会检查模型配置和 Prompt 有没有改动，最好每次实验都保存配置快照，包括模型版本、温度、Prompt hash、检索配置（TopK、RRF_K、是否启用扩展/rerank）、评估器版本和知识库文档数量。

最后是评估层本身的问题。评估模型也有随机性，超时导致部分样本降级评分，或者评估 Prompt 被改了，都会导致结果不稳定。我的做法是检查评估日志中有多少样本超时或降级，如果失败率很高，说明评估系统本身有问题。如果是评估器随机性导致的波动，就应该多次运行取均值和标准差，标准差大于 0.1 说明评估不稳定，需要增加样本数或者固定随机种子。

我认为 RAG 评估更适合看多次运行的均值、方差和相对差异，不能拿一次跑出来的 0.83 当成线上真实准确率 83%。每次实验必须保存配置快照和 trace，这样才能复现和回溯问题。

**可能追问：**

- **如何确认是检索变化还是生成变化？**：固定答案生成部分，只对比检索结果 chunk ID；如果 chunk 变了是检索问题，chunk 没变但答案变了是生成问题。
- **评估器随机性如何量化？**：相同样本运行 5-10 次，计算每个样本评分的标准差；标准差过大的样本单独排查或标记不稳定。
- **配置快照保存什么？**：模型版本、温度、Prompt hash、检索配置（TopK、RRF_K、是否启用扩展/rerank）、评估器版本、知识库版本或文档数量。

**补充细节：**

配置快照应包含所有影响结果的因素，便于复现和回溯。每次实验生成配置 hash，相同配置的多次运行应该结果相近（考虑随机性）。

验证方法：固定所有配置运行多次，计算指标方差；方差小于阈值（如 0.05）认为稳定；更换单一配置项（如模型温度），观察指标变化是否符合预期。
