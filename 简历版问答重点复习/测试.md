# AI Agent 功能测试用例  
  
## 测试前准备  
  
1. 启动后端服务  
2. 获取 JWT Token（登录接口）  
3. 上传几篇测试文档到知识库  
4. 创建几篇测试笔记  
  
```bash  
# 登录获取 TokenTOKEN=$(curl -s -X POST http://localhost:8080/user/login \  
  -H "Content-Type: application/json" \  -d '{"username":"test","password":"123456"}' | jq -r '.data.token')  
# 通用请求函数  
ask() {  
  curl -s -N -X POST http://localhost:8080/chat/agent/query/stream \    -H "Content-Type: application/json" \    -H "Authorization: Bearer $TOKEN" \    -d "{\"query\":\"$1\"}" 2>/dev/null}  
```

## 一、意图识别测试  
  
### 1.1 模糊提问 → 应触发澄清  
```bash  
ask "帮我学习AI"  
```  
**预期**: 返回澄清方向选项（3-4 个具体方向），或直接给出宽泛回答  
  
### 1.2 清晰查询 → 直接执行  
```bash  
ask "搜索我笔记里关于 BM25 的内容"  
```  
**预期**: 调用 searchNotes 工具，返回相关笔记列表  
  
### 1.3 多意图混合 → 应拆分处理  
```bash  
ask "帮我搜索笔记里关于机器学习的内容，再从知识库里找相关文档，最后统计一下我有多少笔记"  
```  
**预期**: 调用 searchNotes + ragSummary + getNoteStats 三个工具  
  
### 1.4 专业术语 → 直接回答  
```bash  
ask "什么是 Transformer 的自注意力机制？"  
```  
**预期**: 直接用通用知识回答，不调用工具  
  
### 1.5 闲聊 → 不调工具  
```bash  
ask "你好，今天天气怎么样？"  
```  
**预期**: 直接回复，不调用任何工具  
  
### 1.6 歧义问句 → 应澄清或合理推断  
```bash  
ask "帮我看看"  
```  
**预期**: 要么返回澄清选项，要么推断为查看笔记列表  
  
---  
  
## 二、工具调用链路测试  
  
### 2.1 单工具调用 — 笔记搜索  
```bash  
ask "搜索我的笔记里有没有关于 RAG 的内容"  
```  
**预期**: 调用 searchNotes(query="RAG")  
**验证**: 返回结果中应包含相关笔记标题  
  
### 2.2 单工具调用 — 知识库检索  
```bash  
ask "知识库里是怎么定义 BM25 算法的？"  
```  
**预期**: 调用 ragSummary(query="BM25算法定义")  
**验证**: 返回结果应基于知识库文档  
  
### 2.3 单工具调用 — 创建笔记  
```bash  
ask "帮我创建一篇笔记，标题是'学习记录'，内容是'今天学习了 RAG 原理'"  
```  
**预期**: 调用 createNote(title="学习记录", content="今天学习了 RAG 原理")  
**验证**: 笔记创建成功  
  
### 2.4 多工具串联 — 搜索后创建  
```bash  
ask "帮我搜索知识库里关于 Transformer 的内容，然后把搜索结果整理成一篇新笔记"  
```  
**预期**: 先调 ragSummary → 再调 createNote  
**验证**: 两个工具按顺序调用，新笔记内容基于检索结果  
  
### 2.5 多工具并行 — 同时查询  
```bash  
ask "我的笔记有几篇？知识库里有多少文档？"  
```  
**预期**: 调用 getNoteStats + ragSummary（可能并行）  
**验证**: 返回两部分信息  
  
### 2.6 工具参数填充 — 部分参数  
```bash  
ask "帮我创建一篇笔记"  
```  
**预期**: Agent 应该追问标题和内容，或用默认值创建  
**验证**: 不应因缺少参数而崩溃  
  
### 2.7 工具调用失败 — 不存在的笔记  
```bash  
ask "帮我找到 ID 为 99999 的笔记"  
```  
**预期**: 工具返回"未找到"，Agent 用自然语言告知用户  
**验证**: 不应返回错误堆栈

## 三、任务拆解与规划测试  
  
### 3.1 复杂任务 — 自动拆分  
```bash  
ask "帮我整理一下我的 AI 学习笔记，总结知识库里的内容，再看看今天有什么要复习的"  
```  
**预期**: Supervisor 拆分为 3 个子任务并行执行  
**验证**: 思考过程中应显示"规划→研究→写作"阶段  
  
### 3.2 简单任务 — 不拆分  
```bash  
ask "搜索笔记 BM25"```  
**预期**: 走单 Agent 流程，不触发 Supervisor 拆分  
**验证**: 思考过程中不应出现"规划"阶段  
  
### 3.3 子任务独立性  
```bash  
ask "帮我对比笔记里的 RAG 内容和知识库里的 RAG 内容有什么区别"  
```  
**预期**: 拆分为两个独立检索子任务 + 一个对比写作任务  
**验证**: 两个检索应并行执行  
  
### 3.4 任务终止判断  
```bash  
ask "创建一篇空笔记"  
```  
**预期**: Agent 直接创建，不需要多轮对话  
**验证**: 一次工具调用后返回结果

## 四、记忆管理测试  
  
### 4.1 短期记忆 — 上下文连贯  
```bash  
# 第一轮  
ask "什么是 RAG？"  
# 第二轮（不提 RAG）  
ask "它有什么优缺点？"  
```  
**预期**: 第二轮回答应理解"它"指的是 RAG  
**验证**: 回答内容与 RAG 相关  
  
### 4.2 多轮记忆 — 前文引用  
```bash  
# 第一轮  
ask "帮我搜索笔记里关于机器学习的内容"  
# 第二轮  
ask "刚才搜索到的笔记有几篇？"  
```  
**预期**: Agent 应理解"刚才搜索到的笔记"指上一轮结果  
**验证**: 回答引用前文信息  
  
### 4.3 话题切换 — 记忆隔离  
```bash  
# 第一轮  
ask "什么是 BM25？"  
# 第二轮（切换话题）  
ask "帮我创建一篇笔记"  
# 第三轮  
ask "继续刚才的话题"  
```  
**预期**: "继续"应回到 BM25 话题，而非创建笔记  
**验证**: 回答与 BM25 相关  
  
### 4.4 长对话 — 上下文压缩  
```bash  
# 连续问 15+ 个问题，然后问一个需要早期信息的问题  
ask "我第一个问题问的是什么？"  
```  
**预期**: 即使触发了上下文压缩，仍能回忆早期关键信息  
**验证**: 回答正确或给出合理近似  
  
### 4.5 记忆溢出 — 超长对话  
```bash  
# 发送 30+ 条消息后  
ask "总结一下我们刚才讨论的所有话题"  
```  
**预期**: 不应因上下文过长而崩溃  
**验证**: 给出合理的摘要

# Agent Trace
下面按 5 类解释这些 Agent Trace 指标，并说明测试时怎么看。

## 1. 执行规模

### `loopCount`

Agent 完成一次任务经历的循环轮数。一次循环通常包括“分析/规划 → 调用工具 → 获取结果 → 再判断”。

- 数值低：通常路径直接。
    
- 数值高：可能任务复杂，也可能 Agent 反复试错、绕路或陷入循环。
    
- 测试关注：同类任务在新版本中是否明显增加。
    
- 注意：复杂任务不适合统一限制为 `<= 5`，最好按任务类型设置基线。
    

### `toolCallCount`

一次任务调用工具的总次数，如搜索、数据库查询、代码执行、RAG 检索等。

- 数值低：工具使用较克制。
    
- 数值高：可能确有需要，也可能重复调用、选错工具或检索效果差。
    
- 测试关注：是否存在相同参数的重复调用，以及调用次数突然上涨。
    
- 和 `loopCount` 结合看：轮次、调用次数同时增加，通常更值得排查。
    

---

## 2. 性能指标

### `totalLatencyMs`

从接收任务到输出最终结果的总耗时，单位通常是毫秒。

一般可以近似理解为：

[  
总耗时 \approx 规划耗时 + 执行耗时 + 反思耗时 + 其他开销  
]

“其他开销”可能包括网络、队列、序列化、模型调用和框架调度，因此三个阶段耗时之和未必严格等于总耗时。

### `planningLatencyMs`

Agent 识别意图、分析任务和生成执行计划所花的时间。

- 过高：提示词过长、历史上下文过多，或规划逻辑过于复杂。
    
- 过低但结果差：可能没有充分分析就开始执行。
    
- 测试关注：同样输入下，规划耗时是否发生明显回归。
    

### `executionLatencyMs`

执行计划和调用工具所花的时间，通常是主要耗时来源。

- 过高：外部工具响应慢、调用次数多、串行调用过多或发生重试。
    
- 测试关注：结合 `toolCalls` 定位具体哪个工具慢。
    
- 建议进一步观察：单次工具调用耗时、最大耗时和失败重试次数。
    

### `reflectionLatencyMs`

Agent 检查中间结果、发现问题、修正计划或验证答案所花的时间。

- 适量反思：有助于提高准确性。
    
- 过高：可能反复自检、迟迟不能结束。
    
- 为零：不一定是问题，简单任务可能不需要反思。
    
- 测试关注：要结合 `reflectionRecords` 判断时间是否花得合理。
    

---

## 3. Token 指标

### `totalTokens`

整个任务消耗的 Token 总量，通常包含输入和输出，以及可能存在的多轮模型调用。

它是衡量模型成本和上下文规模的核心指标。

- 突然升高：可能轮次增加、历史过长、工具结果过大或提示词膨胀。
    
- 测试关注：同一测试集不同版本的均值、P95 和最大值。
    
- 不建议只设固定阈值，应同时比较历史基线。
    

### `systemPromptTokens`

系统提示词占用的 Token 数，包括角色、规则、工具定义和固定业务说明等。

- 每次任务都可能重复产生，因此属于固定成本的重要部分。
    
- 突然增加：可能加入了过多规则、工具描述或重复指令。
    
- 测试关注：版本升级后是否出现非预期增长。
    

### `historyTokens`

对话历史和已有上下文占用的 Token 数。

- 过高：可能导致成本和延迟上升，也可能稀释当前问题的重要信息。
    
- 持续增长：说明历史裁剪、摘要或上下文管理可能有问题。
    
- 测试时可构造长对话，验证 Agent 是否仍能正确理解最新请求。
    

### `toolResultTokens`

工具返回结果被放进模型上下文后占用的 Token 数。

- 过高：常见原因是搜索结果、日志、网页、代码或数据库记录返回过多。
    
- 可能 可能影响：成本增加、上下文溢出、关键内容被噪声淹没。
    
- 测试关注：工具是否支持分页、截断、摘要和字段过滤。
    

需要注意：

[  
totalTokens  
]

不一定严格等于上述三个字段之和，因为还可能包含用户输入、Agent 输出、规划结果、反思内容及其他模型调用。

## 4. 决策质量

### `intentRecognition`

Agent 对用户意图的识别结果，例如任务类型、目标、限制条件和期望输出。

测试时重点检查：

- 是否识别了正确任务；
    
- 是否遗漏时间、格式、范围等约束；
    
- 是否把“查询”误判为“执行”；
    
- 是否把“解释问题”误判为“修改系统”。
    

这是判断后续执行为什么偏离目标的重要依据。

### `replanningTriggered`

是否触发了重新规划，通常是布尔值。

触发重规划并不一定代表质量差。例如工具失败、信息不足或环境变化时，重规划是合理行为。

异常信号包括：

- 简单任务频繁重规划；
    
- 每次都因相同原因重规划；
    
- 明知工具失败仍重复原计划；
    
- 重规划后计划没有实质变化。
    

### `replanningReason`

触发重新规划的具体原因，例如：

- 工具调用失败；
    
- 返回信息不足；
    
- 原计划不可执行；
    
- 用户约束发生变化；
    
- 中间结果与预期不符。
    

测试时要判断理由是否真实、具体，并且与 Trace 中的工具结果或错误记录一致。

### `originalPlan`

Agent 最初生成的执行计划。

用于检查：

- 是否正确理解目标；
    
- 步骤是否完整；
    
- 顺序是否合理；
    
- 是否包含不必要或高风险操作；
    
- 是否选择了正确工具。
    

### `revisedPlan`

Agent 重新规划后的计划。

应与 `originalPlan` 对比：

- 是否解决了原计划的问题；
    
- 是否根据新信息进行了实际调整；
    
- 是否只是换一种表达、执行逻辑却没变；
    
- 是否引入了新的无关步骤。
    

### `reflectionRecords`

Agent 在执行过程中进行检查、评估和纠错的记录。

常见内容包括：

- 当前结果是否满足目标；
    
- 工具结果是否可信；
    
- 是否需要补充信息；
    
- 是否应该重试或换工具；
    
- 最终答案是否符合约束。
    

好的反思记录应当有事实依据并能影响后续行动。若反思很多，但仍不断重复错误工具，说明反思机制可能流于形式。

## 5. 结果与异常

### `status`

任务最终状态，常见值包括：

|状态|含义|
|---|---|
|`COMPLETED`|流程正常结束|
|`FAILED`|因错误而失败|
|`TIMEOUT`|超过允许时间仍未完成|

需要注意：`COMPLETED` 只说明流程结束，不代表答案一定正确。因此还要检查 `finalAnswer`、工具结果和业务断言。

### `errors`

执行过程中产生的错误集合，可能包括错误类型、错误信息、发生阶段、工具名称和堆栈信息。

测试时关注：

- `COMPLETED` 状态下是否仍有未处理错误；
    
- 是否重复发生同一种错误；
    
- 错误是否被正确恢复；
    
- 错误信息能否支持问题定位；
    
- 是否意外记录敏感信息。
    

“`errors` 为空”适合作为正常场景的断言，但在容错测试中，出现已恢复错误可能是预期行为。

### `finalAnswer`

Agent 最终返回给用户的答案。

应检查：

- 是否正确；
    
- 是否完整回答问题；
    
- 是否符合格式要求；
    
- 是否和工具证据一致；
    
- 是否包含虚构内容；
    
- 是否泄露内部规划、日志或敏感数据。
    

### `toolCalls`

每次工具调用的详细记录，通常包含工具名称、输入参数、返回结果、耗时、状态及错误。

这是排查 Agent 行为最有价值的字段之一。可以用它发现：

- 工具选择错误；
    
- 参数构造错误；
    
- 重复调用；
    
- 调用顺序异常；
    
- 工具失败后未切换方案；
    
- 工具返回正确，但 Agent 解读错误。
    

`toolCallCount` 是汇总数量，`toolCalls` 是每次调用的明细。

### `artifacts`

执行过程中生成的产物，例如文件、报告、代码、图片、表格或导出数据。

测试时检查：

- 是否成功生成；
    
- 文件格式是否正确；
    
- 内容是否完整；
    
- 文件是否可打开；
    
- 路径或下载地址是否有效；
    
- 是否生成重复或无关文件；
    
- 是否含有敏感数据。
    

### `ragTraceIds`

RAG 检索链路的追踪 ID，用于关联检索系统中的日志和证据。

它通常不直接表示质量，而是用于继续定位：

- 实际执行了什么查询；
    
- 召回了哪些文档；
    
- 文档排名和分数如何；
    
- 是否召回错误知识；
    
- 最终答案是否使用了召回内容。
    

如果答案出现事实错误，可以通过该 ID 判断问题出在“没有召回”“召回错误”，还是“召回正确但 Agent 使用错误”。

## 测试判断建议

不要孤立判断单个指标，最好组合分析：

|现象|可能原因|
|---|---|
|`loopCount` 高且 `toolCallCount` 高|Agent 绕路或重复试错|
|`totalLatencyMs` 高但调用次数低|单个工具或模型调用很慢|
|`totalTokens` 高且 `historyTokens` 高|历史上下文膨胀|
|`totalTokens` 高且 `toolResultTokens` 高|工具返回内容过多|
|`replanningTriggered` 频繁为真|初始规划质量差或工具不稳定|
|`status=COMPLETED` 但有大量 `errors`|错误被恢复，也可能状态判定过于宽松|
|`status=COMPLETED` 但答案错误|流程完成，不代表业务正确|
|反思记录很多但重复相同调用|反思没有真正改变决策|

推荐把 `loopCount <= 5`、`toolCallCount <= 6`、`totalLatencyMs <= 8s` 作为特定场景的初始基线，而不是所有任务统一的硬性标准。更稳妥的做法是按任务类型分别设置历史均值、P95 和允许增长比例。

## 6.面试描述
我在这个项目中主要负责 AI Agent 的测试与可观测性建设。

我们的系统是一个基于 RAG 的智能笔记 Agent。它会进行意图识别、任务规划、知识库检索、工具调用、反思和重新规划。刚开始测试时，我们只能看到最终答案和普通日志。这样虽然能判断答案对不对，但如果 Agent 响应很慢、调用工具次数异常，或者偶发失败，我们很难还原它中间到底做了什么。

所以我设计了一套 Agent Trace 数据模型，把一次 Agent 任务的执行过程完整记录下来，指标主要分为五类。

第一类是执行规模，包括 loopCount 和 toolCallCount，用来判断 Agent 是否绕路或者重复调用工具。

第二类是性能指标，包括总耗时、规划耗时、执行耗时和反思耗时，用来定位时间具体消耗在哪个阶段。

第三类是 Token 指标，我拆分了 system prompt、历史上下文和工具结果的 Token，用于发现 Prompt 膨胀和模型成本异常。

第四类是决策质量，记录意图识别、原始计划、重新规划原因和反思结果，用于判断 Agent 的决策过程是否合理。

第五类是结果和异常，包括最终状态、错误、工具调用明细、最终答案以及关联的 RAG Trace。

在这套 Trace 基础上，我按任务类型建立了回归测试基线，而不是对所有任务使用相同阈值。例如，简单知识问答通常要求 Agent 在三轮以内完成，工具调用不超过四次；复杂总结任务则允许更多轮次。同时，我会比较不同版本的平均值、P95 和最大值，监控性能与成本是否退化。

有一次模型和 Prompt 升级后，答案正确率没有明显下降，但回归测试发现，同一批知识库问答的平均总耗时从大约 4.8 秒增加到了 7.6 秒，P95 从 7 秒上升到接近 12 秒；平均工具调用次数也从 2.3 次增加到了 4.9 次，Token 消耗增加了约 35%。

如果只看最终答案，这个版本可能会正常发布。但通过 Trace，我发现主要问题不是数据库或者模型接口变慢，而是 Agent 的执行路径发生了变化。

具体表现是：Agent 第一次 RAG 检索已经召回了正确文档，但反思阶段认为证据不足，于是触发重新规划；重新规划后的计划没有实质变化，又使用几乎相同的参数调用了一次检索工具。部分任务甚至连续检索三次。RagTrace 显示这几次召回结果的重合率很高，因此可以判断是无效重复检索，而不是真正需要补充证据。

我进一步分析 reflectionRecords 和 toolCalls，最后定位到两个原因。

第一个原因是成功标准写得过于模糊，Agent 不知道什么情况下证据已经充分。

第二个原因是工具结果直接把大量文档内容放回模型上下文，使 toolResultTokens 明显增加，同时噪声又影响了反思判断。

针对这个问题，我做了三项优化。

第一，给检索步骤增加明确的完成条件，例如正确文档进入 Top-K、存在能够支持回答的证据片段时，就不再重复检索。

第二，增加相同工具加相同参数的重复调用检测。如果查询和候选文档没有变化，Agent 必须调整查询或者结束，不能原样重试。

第三，对 RAG 工具结果进行去重和压缩，只保留文档 ID、相关片段、评分和必要的引用信息，不再把整篇内容重复放入上下文。

优化之后，在答案正确率和引用正确率基本不变的情况下，平均工具调用次数从 4.9 次降到了 2.6 次，平均总耗时从 7.6 秒降到了 5.1 秒，P95 降到了约 8 秒，平均 Token 消耗下降了约 28%，重复检索用例减少了约 80%。

后来我又引入 OpenTelemetry 作为外层技术链路观测。原来的 AgentTrace 和 RagTrace 继续负责记录规划、反思、证据和工具决策等业务语义；OTel 负责 HTTP、异步线程、数据库、Redis、RAG、LLM 和工具调用的耗时及异常。我通过 traceId 把两套数据关联起来。

这样，当回归测试失败时，我可以先判断是答案质量问题、Agent 决策问题，还是基础设施性能问题。例如，RagTrace 用于判断有没有召回正确文档，AgentTrace 用于判断 Agent 是否正确使用证据，OTel 则用于判断延迟是不是来自 Redis、数据库、模型服务或者异步上下文传播。

这套工作的核心价值是：我不只是对最终答案做黑盒测试，而是把 Agent 的质量、行为、性能和成本变成可度量、可回归、可定位的工程指标，并将它们接入版本发布门禁。

# Otel框架
# 举2个贴合你AI笔记Agent项目的真实场景例子，一听就懂

## 前置铺垫

一次用户提问完整流程： 用户发消息 → 对话服务主线程 → Agent调度器 → 丢任务到**异步线程池**执行工具调用（查知识库/增删笔记）→ 操作Redis缓存、MySQL笔记库 → 请求LLM大模型接口 → RAG检索文档 → 拼接结果返回用户

- 你的 **AgentTrace**：只记AI思考环节（规划、反思、循环次数、token、重复检索）
- **OTel**：盯着上面每一步底层技术调用，记耗时、报错、排队、网络延迟

## 例子1：接口整体很慢，但AgentTrace看不出问题，靠OTel定位底层瓶颈

### 现象

回归测试发现所有问答平均耗时涨到9秒，但查看AgentTrace指标： loopCount、toolCallCount、token消耗全部和基线一致，没有重复检索、没有频繁重规划，AI自身逻辑完全正常。 单纯看业务Trace完全找不到原因。

### 用OTel查链路（同一个traceId串联所有底层操作）

1. OTel抓到：**异步线程池队列堆积严重** 主线程提交工具任务后，线程池满了，任务排队等待2.8s才分到空闲线程；
2. OTel记录MySQL查询笔记文档单次耗时1.6s，存在未加索引的慢SQL；
3. OTel记录调用第三方LLM模型接口网络波动，单次HTTP请求RT稳定2s。

### 结论

慢不是AI Agent决策逻辑差，是**基础设施/线程资源瓶颈**，属于技术层问题，只有OTel能捕获。 优化：给数据库加索引、调大线程池核心线程数、模型接口增加缓存。

## 例子2：偶发工具调用超时、任务失败，分不清是AI逻辑还是网络/Redis问题

### 现象

线上少量任务状态为TIMEOUT超时，AgentTrace只能看到“工具调用失败”，不知道失败在哪一层。

### OTel链路明细：

同一个traceId下拆分多层埋点日志：

1. Agent发起检索工具调用；
2. OTel埋点：Redis读取知识库缓存超时，连接Redis发生网络IO异常，直接抛出超时；
3. 工具执行直接中断，返回错误给Agent。

### 结论

不是Agent规划错误、不是重复调用工具，是Redis服务网络抖动导致缓存读取失败。 如果没有OTel，只能看到模糊的“工具执行失败”，无法定位是缓存、数据库还是模型接口出问题。

## 例子3：你项目核心场景——异步多线程执行工具，OTel追踪跨线程链路

### 痛点

工具是主线程丢到线程池异步执行，普通日志会出现链路断档：主线程日志和子线程日志无关联，分不清哪个用户请求对应的异步任务报错。

### OTel解决：

自动透传traceId上下文，主线程、线程池异步子线程、数据库、LLM接口全部带上同一个traceId。 能直观看到： 主线程投递任务耗时0.1ms → 线程池排队等待1.2s → 子线程执行RAG检索1.5s → MySQL读取0.8s。 可以精准区分耗时是**排队等待**，还是**工具本身执行慢**。

# 一句话区分两者场景（面试直接背）

1. 看AgentTrace：判断AI自己“会不会思考”，有没有乱调用工具、反复检索、token暴涨；
2. 看OTel：判断支撑AI运行的底层资源“卡在哪了”，线程、数据库、缓存、网络、模型接口、异步任务排队全部归它管。

| 1 | 清空某会话的历史消息 | 清空成功 |
| 2 | 在该会话中发送一条新消息 | Agent 正常响应，不因空历史崩溃 |

### 4.2 超大上下文 + 工具调用

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 上传 5 篇较长文档到知识库 | 上传成功 |
| 2 | 连续进行 15 轮 RAG 检索问答 | 每轮正常返回 |
| 3 | 第 16 轮问"刚才所有回答中提到了哪些核心概念？" | Agent 能给出归纳总结 |

**判定标准**: 16 轮后仍能正常运转，不因 OOM 或 Token 超限崩溃。

### 4.3 账号退出后上下文清空

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 在某个会话中聊几轮 | 历史存在 |
| 2 | 退出登录（logout） | 登出成功 |
| 3 | 重新登录，进入同一会话 | 能看到之前的对话历史 |

**判定标准**: 退出登录不影响 MySQL 中存储的会话历史，重新登录后可继续对话。
