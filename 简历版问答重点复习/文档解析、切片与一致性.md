## 五、文档解析、切片与一致性

### 79. 文档入库为什么拆成同步和异步？

我觉得这个设计主要是为了平衡用户体验和系统稳定性。

文档上传之后，用户肯定希望尽快看到上传成功的反馈，不想一直等着。但是向量化和写入 Chroma 这个过程比较耗时，一个文档可能要几秒甚至几十秒。如果全部同步执行，用户体验会很差，而且还会占用 Web 请求的线程，影响整体并发能力。

所以我的设计是这样的：文档处理先计算 MD5，检查同一用户是否已经上传过相同文件，避免重复上传。然后进行解析和切片，MySQL 和 BM25 相关数据先同步写入，这样文档元信息和关键词检索能尽快可用。数据库的唯一约束可以兜底并发上传的问题，避免两个请求都通过了”先查询后插入”的检查。

MySQL 主流程成功之后，我会投递一个 Chroma 异步任务，embedding 和向量写入不占用上传请求的长事务。异步任务需要记录文档 ID、chunk、批次、状态、重试次数和错误原因，这样出问题的时候能追溯。

批量 embedding 如果失败了，会先有限重试，实在不行可以回退到单条处理，避免一条坏数据拖垮整个批次。写入 Chroma 的时候应该使用稳定的 chunk ID，任务重试时跳过已经成功的 chunk 或者覆盖同一个 ID，避免重复向量。

如果 MySQL 成功但 Chroma 失败，系统短时间内会允许文档处于”向量未完成”状态，这时候检索可以走 BM25 或关键词路径降级。失败任务之后由补偿机制重试，超过最大次数就进入明确的失败或人工处理状态。

我认为这里实现的是最终一致性，不是分布式强事务。验证的时候不能只看上传接口返回 200 就认为成功了，还要检查 MySQL、BM25、Chroma 的实际数据、状态机流转和补偿后的最终结果。

**可能追问：**

- **为什么不全部同步？**：embedding 和向量写入耗时长（几秒到几十秒），同步执行会阻塞上传接口响应；异步后用户立即得到上传成功反馈。
- **异步失败怎么通知用户？**：文档状态标记为 `vector_failed`，用户查询文档列表时可以看到；也可以通过 WebSocket 或轮询推送状态变更。
- **补偿任务如何触发？**：定时任务扫描 `vector_pending` 或 `vector_failed` 状态且创建时间超过阈值的文档，重新投递异步任务；超过最大重试次数进入人工处理。

**补充细节：**

同步写入流程：上传 → MD5 去重 → 解析切片 → MySQL 事务（文档 + chunk） → BM25 索引 → 返回成功。
异步写入流程：投递任务 → 批量 embedding → 写入 Chroma → 更新状态为 `completed`；失败记录错误并标记 `vector_failed`。

验证方法：上传文档后立即查询，断言 MySQL 和 BM25 已有数据；等待异步完成后查询 Chroma，断言向量存在；故障注入 Chroma 不可用，断言文档状态为 `vector_failed` 且检索降级到 BM25。

### 44. 为什么还需要规则评分？

我认为 LLM judge 只能判断语义质量，但系统质量不能只看语义，还有很多硬指标必须保证。

比如回答为空、上下文为空、延迟超阈值、相似度过低、Token 超预算，这些都可以用确定性规则判断。这些是系统必须保证的基本约束，不应该完全依赖 LLM 评估。LLM 可能会给一个空回答打个 0.3 分，但实际上空回答就是 100% 的失败，不应该有任何模糊性。

项目里的规则评分包括：答案长度检查（小于 10 字符标记异常）、上下文非空检查、延迟阈值（超过 10 秒扣分）、Token 预算检查、检索降级标记。这些规则分数单独保存，不与 LLM judge 的语义评分直接混合。最终报告可以生成一个综合分，但必须同时展示规则分和语义分，避免一个综合分掩盖"答案语义不错但检索全空"这种问题。

规则权重应该通过回归样本校准，而不是随意设置。比如我发现历史失败样本中 80% 都是延迟超 10 秒，那延迟应该是高权重规则；如果答案长度和质量相关性不高，就降低长度规则权重。

我觉得规则和语义评分结合才能全面反映系统质量。只用 LLM judge 的话，无法捕捉系统性能和可用性问题；只用规则的话，又无法判断答案是否答非所问或产生幻觉。两者结合才是完整的评估体系。

**可能追问：**

- **规则和 LLM judge 如何组合？**：分开保存，报告同时展示。需要综合分时按校准权重加权，但不能让综合分掩盖子项问题。
    
- **规则权重如何校准？**：用历史失败样本统计各规则与实际问题相关性，调整权重使综合分与人工判断相关性最高。
    
- **为什么不只用规则？**：规则无法判断语义质量，比如答案长度够、延迟正常，但答非所问或产生幻觉，需要 LLM judge 补充。
    

**补充细节：**

常见规则示例：

```text
答案长度 < 10 或 > 2000 → 标记异常
上下文为空 → Context Precision/Recall 标记 N/A
延迟 > P95 阈值 → 扣分
Token > 预算 → 扣分
检索降级到关键词 → 标记质量降级
```

验证方法：

- 构造明确违反规则的样本（空答案、超长延迟）
- 断言规则正确识别并扣分
- 规则分和语义分应独立展示
- 综合分变化应可解释

核心原则：

> **规则评分捕捉系统硬指标，LLM judge 评估语义质量。两者结合才能全面反映系统质量。**

### 45. 多格式文档怎么解析？

我的做法是非 PDF 文件统一走 Apache Tika，PDF 单独使用 PDFBox 按页抽取，并保留页码信息。

项目里 `DocumentProcessor` 会先根据文件扩展名和 MIME 类型判断格式。PDF 文件我选择用 PDFBox 逐页提取文本，每页可以保存为独立 chunk 或者合并到段落，同时记录页码。这样做的好处是召回结果可以显示”第 3 页”，方便用户定位原文，这个对企业知识库场景挺重要的。

非 PDF 文件，比如 Word、TXT、Markdown、HTML，统一用 Tika 解析。Tika 内部会调用对应的解析器，支持几十种格式，基本能覆盖常见的办公文档。解析后的文本我会做 Unicode 归一化（NFKC），统一全角半角、兼容字符，避免”３”和”3”无法匹配这种问题。

解析失败、空文档、扫描图片 PDF 和超长文件都要有明确状态，不能只看接口是否返回 200。扫描 PDF 如果解析出的文本为空或很少，我会标记为 `OCR_REQUIRED`。OCR 如果没有实现，应该如实说是后续能力，不要含糊其辞。超长文件（比如超过 10MB 或 1000 页）应该限流或拒绝，避免解析占用过多资源把服务拖垮。

我认为文档解析这块的关键是异常处理要清晰。解析失败要保存错误信息到文档状态，空文档标记为空不入库，扫描 PDF 标记需要 OCR，超长文件直接拒绝或限流。不能让异常文档静默丢弃，否则用户根本不知道自己的文档有没有真正入库。

**可能追问：**

- **Tika 支持哪些格式？**：Office 文档（docx/xlsx/pptx）、PDF、HTML、XML、纯文本、Markdown、RTF、邮件等几十种格式。不支持的格式返回解析失败。
    
- **为什么 PDF 不用 Tika？**：Tika 也可以解析 PDF，但不方便精确控制页码和分页逻辑。PDFBox 可以逐页处理并保留页码元数据。
    
- **扫描 PDF 怎么办？**：当前只能标记为需要 OCR，不自动执行 OCR。生产化建议接入 OCR 服务（如 Tesseract、百度 OCR），将图片转文字后再切片入库。
    

**补充细节：**

解析流程：

```text
上传文件
   ↓
检测格式（扩展名 + MIME）
   ↓
选择解析器
├─ PDF → PDFBox 逐页提取 + 保留页码
└─ 其他 → Tika 统一解析
   ↓
提取文本
   ↓
Unicode 归一化（NFKC）
   ↓
切片
```

解析异常处理：

```text
解析失败 → 保存错误信息到文档状态
空文档 → 标记为空，不入库
扫描 PDF → 标记 OCR_REQUIRED
超长文件 → 拒绝或限流
```

验证方法：

- 准备各格式测试文件（PDF、Word、TXT、Markdown）
- 上传后检查文本提取正确、页码保留、归一化生效
- 扫描 PDF 应标记 `OCR_REQUIRED`
- 超长文件应拒绝或限流

核心原则：

> **PDF 单独处理保留页码，其他格式用 Tika 统一解析。解析异常有明确状态，不静默丢弃。**

### 46. 切片怎么做？为什么有 overlap？

我觉得切片这块的核心问题是：固定长度切片实现简单，但容易在段落、代码、表格或步骤中间截断，导致语义不完整。

截断之后一个 chunk 可能缺少主语或前置条件，向量表达就不完整；另一个 chunk 可能只剩结论，检索命中后模型仍然无法理解上下文。这种情况在技术文档里特别常见，比如"配置 xxx 参数"被截断了，前面的 chunk 没有说是什么参数，后面的 chunk 没有说为什么要配置。

当前的实现流程是这样的：先用 Tika 处理非 PDF，PDF 用 PDFBox 按页提取，并保留页码。文本经过清洗后交给切片逻辑，普通文本我会优先按段落、换行、句子等自然边界切分；代码、列表和表格尽量保持结构完整，实在太长的话按行切；相邻 chunk 之间保留 overlap，减少跨边界信息丢失。每个 chunk 同时保存文档标题、章节、内容类型和页码等元数据。

Overlap 是指相邻 chunk 之间有一定重叠内容，比如前一个 chunk 结尾 100 字符和后一个 chunk 开头 100 字符重复。这样做的好处是即使关键信息在边界附近，也能被至少一个 chunk 完整包含。代价是索引存储和检索计算量增加，但我认为能提高召回完整性，这个代价是值得的。

切片参数不是越大越好。chunk 太小会导致证据碎片化和召回次数增加，太大则会把无关内容一起送给模型，增加 Token 和上下文噪音。应该用固定测试集比较 Recall@K、Context Precision、答案忠实度、Token 和延迟，找到最优的平衡点。

**可能追问：**

- **Overlap 大小如何选择？**：一般 10%-20% chunk 大小，如 chunk 500 字符则 overlap 50-100 字符。太小无法覆盖边界信息，太大增加冗余。
    
- **代码和表格为什么要特殊处理？**：代码截断会破坏语法结构，表格截断会丢失列对应关系。应按函数、代码块或表格行切分。
    
- **切片后如何去重？**：相同 chunk 内容（去除空白后）用 MD5 去重。overlap 导致的部分重复是预期行为，不去重。
    

**补充细节：**

切片策略示例：

```text
普通文本：
优先按段落（双换行）
→ 超长段落按句子
→ 超长句子按标点
→ 兜底按字符数

代码：
按函数、类或代码块
保留完整语法结构

表格：
保留表头，按行切分
或保持整表（小表格）

Markdown：
按标题层级切分
保留标题路径
```

Overlap 示例：

```text
Chunk 1：...前面内容 [边界区域 100 字符]
Chunk 2：[边界区域 100 字符] 后面内容...

重叠部分确保边界附近信息完整
```

验证方法：

- 准备包含长段落、代码、表格的测试文档
- 检查切片是否在自然边界
- 检查 overlap 是否生效
- 检查元数据是否正确
- 人工评估边界附近的检索效果

核心原则：

> **优先自然边界切分，保留结构。Overlap 提高召回完整性，代价是冗余增加。**

### 47. MD5 去重能解决什么，不能解决什么？

我觉得 MD5 去重主要是用来识别同一用户重复上传的相同文件，减少重复解析和索引，但它也有明确的边界。

项目里上传文件时，我会先计算完整文件的 MD5，然后查询 `user_id + md5` 是否已存在。如果存在就直接返回已有文档，不重复解析。数据库对 `user_id + md5` 建立了唯一索引，即使两个并发请求同时通过了查询，插入时也会有一个失败并返回唯一约束冲突，前端可以提示”文件已存在”。

但是 MD5 不能识别内容相同但格式或排版不同的文件，比如同一篇文章的 Word 和 PDF 版本，它们的 MD5 是完全不同的。MD5 也不能表示 embedding 模型和切片版本的变化。如果 embedding 模型从 v1 升级到 v2，已有文档的向量应该重新生成，但 MD5 没变，系统不知道需要重建。

我认为生产化的幂等键应该纳入 parser version、chunk version 和 embedding model，这样模型或切片策略变化时能自动触发重建。但当前实现只用了 MD5，所以 MD5 只负责文件内容去重，不负责版本化重建。

另外，MD5 只在同一用户范围内去重。不同用户可以上传相同文件，因为权限是隔离的。但系统层面可以考虑全局 MD5 索引，相同文件只存一份物理数据，通过权限控制访问，类似文件系统的硬链接。不过当前按用户隔离会更简单，不用处理引用计数和复杂的删除逻辑。

**可能追问：**

- **为什么不用全局 MD5 去重？**：不同用户可能上传相同公开资料但需要独立管理和删除。全局去重需要引用计数和权限控制，当前按用户隔离更简单。
    
- **切片或模型变化怎么处理？**：生产化应增加 `parser_version` 和 `embedding_model` 字段，变更时触发重建任务。当前未实现版本化重建。
    
- **MD5 碰撞怎么办？**：MD5 碰撞概率极低（2^64），对业务文件去重足够。如果要求更高安全性可用 SHA-256。
    

**补充细节：**

去重流程：

```text
上传文件
   ↓
计算 MD5
   ↓
查询 user_id + md5
   ↓
命中 → 返回已有文档（快速）
未命中 → 继续解析
   ↓
插入时唯一约束兜底并发
```

唯一约束示例：

```sql
UNIQUE KEY uk_user_md5 (user_id, md5)
```

保证同一用户相同文件只有一条记录。

验证方法：

- 上传文件两次，第二次应命中去重并快速返回
- 并发上传相同文件，断言最终只有一条记录且无重复解析
- 修改文件内容后 MD5 变化，应作为新文档入库

核心原则：

> **MD5 负责文件内容去重，不负责版本化重建。按用户隔离，数据库唯一约束兜底并发。**

### 48. Chroma 写入失败如何恢复？

我觉得这里首先要承认这是最终一致性设计，不是强一致。

项目里文档入库流程是 MySQL 和 BM25 同步成功后就返回了，然后异步投递 Chroma 写入任务。任务执行时先批量生成 embedding（比如 10 个 chunk 一批），再批量写入 Chroma。任何一步失败都会记录到文档状态（从 `vector_pending` 变成 `vector_failed`）和错误原因。

任务支持有限重试，一般是 3 次，每次重试之间指数退避（1秒、2秒、4秒）。如果批量失败了，我会回退到单条处理，逐个处理并跳过已经成功的 chunk。这样可以避免一条坏数据拖垮整个批次。

补偿机制必须保证幂等：使用稳定的文档/chunk ID、唯一约束或者任务锁，避免重复向量。写入 Chroma 时我用 chunk ID 作为向量 ID，重试时相同 ID 会覆盖而不是新增，这样就能保证幂等。超过最大重试次数的任务会进入人工处理或死信状态，不能无限重试。

另外还有定时补偿任务，会扫描 `vector_failed` 或者超时未完成的文档，重新投递任务。成功后更新状态为 `completed`。

我认为面试中不要说”保证强一致”或者”使用分布式事务”，因为 Chroma 和 embedding 根本不在 MySQL 事务内。准确的表述应该是”通过状态标记、有限重试和补偿任务实现最终一致性”。

**可能追问：**

- **批量写入为什么要回退单条？**：一条坏数据（如文本过长、特殊字符）可能导致整批失败。回退单条可以跳过问题 chunk，让其他正常 chunk 入库。
    
- **如何保证幂等？**：用稳定 chunk ID 作为向量 ID，Chroma 写入时相同 ID 覆盖。补偿任务重试前检查 Chroma 中是否已有该 ID，有则跳过。
    
- **补偿任务如何避免重复处理？**：任务领取时用乐观锁或状态原子更新（如 `CAS vector_failed → processing`），处理完成后更新为 `completed`。
    

**补充细节：**

状态流转：

```text
pending → processing → completed（成功）
                    → vector_failed（失败）
```

补偿任务只处理 `vector_failed` 和超时 `pending` 状态文档。

重试策略：

```text
第 1 次失败 → 等待 1 秒 → 重试
第 2 次失败 → 等待 2 秒 → 重试
第 3 次失败 → 等待 4 秒 → 重试
超过 3 次 → 标记 vector_failed
```

幂等保证：

```text
Chroma 写入：
use chunk_id as vector_id
相同 ID 写入 → 覆盖，不新增
```

核心原则：

> **最终一致性，不是强一致性。状态标记 + 有限重试 + 幂等补偿。**

### 49. SSE 推送断线怎么办？

验证方法：故障注入 Chroma 不可用，断言文档状态为 `vector_failed`；恢复 Chroma 后触发补偿，断言状态变为 `completed` 且向量存在；重复补偿不应产生重复向量。

我觉得 SSE 断线其实不是大问题，因为 SSE 只是实时推送机制，不是状态的唯一来源。

项目里前端通过 SSE 接收任务进度事件，但是任务状态和 trace 都持久化在 MySQL 里。如果 SSE 断线了，前端应该从持久化的快照查询，而不是依赖 SSE 重传。当前是否支持自动重订阅属于接口和前端流程的问题，但核心原则是不能把 SSE 当成持久化存储。

所以我的设计是：SSE 只负责推送进度通知，比如"正在检索""调用了某个工具""生成答案"这些实时消息。真正的任务状态、工具调用记录和异常信息都要落到 Trace 里。用户刷新页面或者 SSE 断线重连后，前端应该先查询任务当前状态，再决定是否重新订阅 SSE。

### 50. 批量 embedding 为什么失败后还要单条回退？

我觉得这个设计的核心思想是：批量请求吞吐高，但一个坏 chunk、上游限制或者瞬时错误可能导致整批失败。有限重试后回退单条，可以定位和跳过问题 chunk，提升整体成功率。

项目中 `DocumentTaskExecutor` 执行异步向量化时，我会先把文档的所有 chunk 按批次（比如 10 个一批）调用 embedding 服务，再批量写入 Chroma。如果批量调用失败了，比如网络超时、服务限流、或者某个 chunk 文本过长，整批都无法入库。

这时候我不是直接放弃，而是把这批 chunk 拆开，逐个调用 embedding 和写入 Chroma。单条成功就标记成功，单条失败记录具体错误原因。这样正常 chunk 不会被坏数据拖累，至少能保证大部分数据能入库。

代价是请求次数和处理时间会增加，所以要设置批大小、总超时和最大重试次数，并记录批次 ID、失败 chunk 和最终状态。失败补偿的时候不能只重试整份文档，否则会重复处理已经成功的 chunk。应该先查询哪些 chunk 向量已经存在，只处理缺失的 chunk。

我认为这个策略的关键是在吞吐和成功率之间找平衡。批量 10 个假设 1 秒，单条 10 次需要 10 秒，看起来慢了。但如果批量失败率高，单条回退反而能提高成功率，总体更可控。

**可能追问：**

- **批量大小如何选择？**：根据 embedding 服务限制和网络稳定性，一般 5-20 个 chunk 一批；太小增加请求次数，太大一个失败影响面大。
- **如何识别坏 chunk？**：单条重试仍失败的 chunk，记录错误原因（如文本过长、特殊字符、编码问题）；人工排查后可以删除或修复。
- **单条回退增加多少耗时？**：批量 10 个假设 1 秒，单条 10 次需要 10 秒；但如果批量失败率高，单条回退反而能提高成功率，总体更可控。

**补充细节：**

批量策略：优先批量 → 批量失败重试 → 重试仍失败则单条回退 → 单条失败记录并跳过。补偿任务重新处理文档时，先查询 Chroma 已有 chunk ID，只处理缺失部分。

验证方法：构造包含一个超长 chunk 的批次，断言批量失败后单条回退，正常 chunk 成功、超长 chunk 失败并记录原因；补偿任务应跳过已成功 chunk，只重试失败部分。

### 51. 如何验证入库链路最终一致？

我觉得验证最终一致性的核心是对账：查 MySQL 文档记录、对应的 chunk 数量、Lucene 和 Chroma 的实际索引数量，如果都一致,说明最终一致达成。

项目中文档入库后，数据分布在多个存储：MySQL `knowledge_document` 保存文档元信息，MySQL `knowledge_document_chunk` 保存文本 chunk，Lucene 保存 BM25 索引，ChromaDB 保存向量。由于异步处理和外部调用，写入可能有延迟或失败。

我的验证方式分三种：

**1. 主键对齐验证**：从 `knowledge_document` 查出所有文档 ID，对每个文档查 `knowledge_document_chunk` 得到 chunk 数量，再查 Lucene 索引得到该文档的 chunk 数量，最后查 ChromaDB 得到该文档的向量数量。三者应该相等。如果不等，说明某个环节没写成功。

**2. 轮询验证**：异步任务完成后等待几秒（比如 5 秒），再查 Chroma。如果数量不匹配，标记为失败待补偿。这个适合实时校验，但要注意不能等太久，否则用户体验差。

**3. 对账任务**：定时任务（比如每天凌晨 2 点）扫描所有文档，对比 MySQL chunk 数量和向量数量，找出不一致的文档 ID，记录到日志或补偿队列。这个是兜底机制，保证长期运行下不会积累太多坏数据。

我认为现实中网络抖动、Chroma 写入慢、embedding 限流都可能导致短暂不一致。只要有补偿机制和定期对账，就能保证最终一致。关键是不要假设写入一定成功，也不要每次都同步等待所有存储都成功才返回，那样延迟太高。

不能只断言上传接口返回 200。要验证 MySQL 文档和 chunk 是否存在、状态是否从 processing 推进到 completed 或 vector_failed、Chroma 是否有对应 chunk、失败后重试是否成功、检索在向量未完成时是否按预期降级。

还要做故障注入：MySQL 提交后进程崩溃、embedding 超时、Chroma 不可用、批量部分失败和重复补偿。最终验证数据没有重复、状态可追踪、任务可恢复。检索降级验证：向量未完成时检索应走 BM25，断言仍能返回结果但质量可能下降。

**可能追问：**

- **如何模拟进程崩溃？**：在 MySQL 提交后、异步任务投递前强制退出或抛异常，重启后检查文档状态和补偿任务是否恢复。
- **如何验证幂等？**：同一文档触发多次补偿任务，断言 Chroma 中向量数量不变、没有重复 ID。
- **如何验证检索降级？**：向量未完成时发起检索，断言走 BM25 路径（trace 中记录降级）且能返回基本结果；向量完成后再检索，断言走完整混合检索路径。

**补充细节：**

验证脚本示例：上传文档 → 等待 5 秒 → 查询文档状态 → 查询 MySQL chunk 数量 → 查询 Chroma 向量数量 → 断言一致。故障注入后检查状态、错误日志、重试记录和最终恢复结果。

自动化测试应覆盖正常流程、各类故障和补偿恢复，不能只测正常路径。
