## 二、多agent任务规划

### 1. Supervisor-Worker 具体怎么实现？

我这个 Supervisor-Worker 的设计主要是为了区分简单问题和复杂问题。

当用户请求进来之后，Supervisor 会先判断这个问题是不是需要拆分，主要看它有没有相对独立的子目标、会不会需要多种工具，或者需不需要多步证据。如果是比较简单的问题，Supervisor 就返回一个空数组,系统直接走单 Agent 流程；如果判断是复杂问题，Supervisor 会生成一个子任务数组，每个子任务至少包含 `label`（任务标签）、`description`（任务描述）、`toolHint`（建议使用的工具）。当前的设计还支持 `goal`（目标）、`successCriteria`（成功条件）、`dependsOn`（依赖关系）和 `executionMode`（执行模式）。

在实现上，`SupervisorService` 会调用一个比较精确的模型来生成这个计划，返回结果之后我会先通过 `cleanLlmJson` 和 `extractJsonArray` 做清洗、抽取和解析。如果这些处理都失败了，就回退到单 Agent，避免因为规划失败导致整个请求不可用。

子任务生成之后，系统会根据依赖关系进行调度。如果任务之间没有前置依赖，理论上可以并行执行；如果有前置关系，就必须按顺序执行。每个 Worker 执行的时候有自己独立的 `AgentState`、工具历史和结果，执行完成后会记录步骤和 trace。

最后还有一个合成阶段，合成器会把各个子任务的结果、证据以及失败原因结合起来，生成最终答案。如果某个子任务失败了，合成器也会明确说明哪些部分没有覆盖到。

**可能追问：**

- **如果规划失败会怎样？**：清洗和数组抽取都失败的时候，系统会返回一个空计划，然后走单 Agent，这样可以避免因为规划异常导致简单问题也失败。
    
- **你怎么判断任务能不能并行？**：主要看任务之间有没有依赖关系，以及它们的结果是不是相互独立。不过目前全局并发控制、租户限流这些属于生产化建议，还没有完全实现。
    
- **为什么 LLM 返回的 JSON 还需要清洗？**：因为模型实际返回的内容不一定严格符合 JSON 格式，比如可能会带 Markdown 代码块、前后会有一些额外的说明文字，或者数组外面还有其他内容。所以我在解析之前会先做一层清洗和 JSON 数组提取，提高计划解析的鲁棒性。如果清洗之后还是解析失败，就回退到单 Agent。
    

**补充细节：**

你可以简单理解成：

```text
用户请求
   ↓
Supervisor 判断复杂度
   ↓
简单问题 → 空数组 → 单 Agent
   ↓
复杂问题 → 子任务数组
   ↓
├── 子任务 A (Worker 1)
├── 子任务 B (Worker 2)  ← 如果无依赖，可以并行
└── 子任务 C (Worker 3)  ← 如果依赖 A，就顺序执行
   ↓
合成器汇总结果
   ↓
最终答案
```

对于顺序执行的任务，我只会把压缩之后的必要结果放进 `completedContext`，避免上下文过长。对于并行执行的任务，会尽量隔离各自的上下文，避免互相污染。

这里要特别说明一点：规划、工具白名单、轮次、Token、时间和权限都是由后端约束的，所以当前更准确的说法是**受约束的任务编排型 Agent**，而不是开放式自主 Agent。

### 2. 为什么不能所有请求都走多 Agent？

主要是因为多 Agent 会带来额外的成本和复杂度。

首先，多 Agent 会增加模型调用次数、Token 消耗和整体延迟。因为 Supervisor 规划本身就需要调用一次模型，每个 Worker 执行又是独立的 Agent 循环，还有最后的结果合成，这些都会增加整体的响应时间和成本。

其次，规划本身也可能出错。Supervisor 可能会误拆分，把一个本来很简单的问题拆成多个子任务，反而增加了失败的可能性。比如用户只是问一个简单的定义，如果硬要拆成"查定义""查示例""查应用场景"，反而会让整个流程变得更复杂、更容易出错。

所以我的策略是：**简单问题直接走单 Agent，复杂问题才走 Supervisor-Worker**。判断标准不是看问题的字数或者长度，而是看这个问题有没有相对独立的子目标、需不需要用到多种不同的工具，或者需不需要多步证据。

另外，即使 Supervisor 判断需要拆分，如果最后只生成了一个子任务，或者规划的收益不明显，系统也会做二次降级，还是走单 Agent。这样可以避免为了拆分而拆分。

**可能追问：**

- **怎么验证 Supervisor 是不是真的有用？**：最好是用一个固定的问题集，分别用单 Agent 和 Supervisor-Worker 跑一遍，然后对比子任务完成率、最终答案质量、P95 延迟、Token 消耗以及失败率。通过这些数据来判断 Supervisor 是不是值得保留。
    
- **后续怎么优化这个机制？**：生产化的话可以考虑根据任务类型、租户预算、历史指标来动态路由，比如某些类型的问题历史数据显示拆分效果不好，就直接走单 Agent。另外还可以增加全局并发控制。不过这些都是后续的优化方向，不是当前已经实现的能力。
    
- **什么样的问题适合拆分？**：比如需要分别查询现象原因和历史解决方案，而且这两者互不依赖，这种就比较适合拆分成并行任务。但如果第二步必须依赖第一步提取出来的版本号或者错误码，那就应该按顺序执行，或者干脆不拆分。
    

**补充细节：**

你可以这样理解多 Agent 的成本：

```text
单 Agent：
用户问题 → Agent Loop → 工具调用 → 生成答案
               ↑
            一次模型循环

多 Agent：
用户问题 → Supervisor 规划 → 子任务 A (Agent Loop)
                           → 子任务 B (Agent Loop)
                           → 子任务 C (Agent Loop)
                           → 合成结果
               ↑              ↑                    ↑
            规划调用      多个 Agent 循环       合成调用
```

所以多 Agent 的模型调用次数、Token 和延迟都会明显增加。

另外，多 Agent 的收益不能只看一次响应快不快，还要综合看：

- **任务成功率**：拆分之后是不是更容易完成任务
- **拆分率**：多少比例的问题被拆分了
- **回退率**：拆分之后又回退到单 Agent 的比例
- **延迟**：P95 或 P99 延迟有没有增加
- **Token 消耗**：平均 Token 增加了多少
- **单位成本**：每个任务的平均成本

如果没有做量化压测，只能说"已经实现了路由和降级机制"，不能说"多 Agent 一定能提升 X% 的效果"或者"一定能降低 Y% 的延迟"。

核心逻辑是：

> **多 Agent 不是越多越好，而是要在任务复杂度、成本和收益之间找到平衡点。**

### 3. 如果面试官说这只是工作流，不是真 Agent，怎么回答？

更准确地说，我这个项目是一个**基于 LLM 规划、受后端约束的任务编排型 Agent**，而不是完全开放式的自主 Agent。

它和固定工作流的主要区别在于，工作流通常是后端提前定义好”第一步做什么、第二步做什么”。而我的 Agent Loop 中，模型会根据当前目标、历史工具调用和工具返回的 Observation，决定下一步是否调用工具、调用哪个工具，以及是否继续执行。连续没有进展时，还会触发反思和策略调整。

但另一方面，它确实不是完全自主的。后端会限制工具白名单、最大执行轮次、Token 和工具调用次数，关键步骤失败时也会进行阻断或者降级。所以我更倾向于把它定义成**受约束的 Agent**。

对于研发知识库这种场景，我认为这种设计反而更合适，因为重点不是追求 Agent 无限自主，而是保证**权限可控、执行可追踪、结果可回归、失败可以处理**。所以我不会把它包装成通用的自主智能体。

**可能追问：**

- **那 Agent 和普通工作流到底有什么区别？**：核心区别是执行过程中的部分决策由模型根据当前状态动态决定，而不是所有步骤都由代码预先写死。不过工具范围、状态和终止条件仍然由后端控制。
    
- **为什么不追求完全自主？**：完全自主会增加越权、循环调用、成本不可控以及结果难以回归等风险。对于企业知识库场景，我更看重可控性和稳定性。
    
- **怎么证明你不是简单拼了几个 Prompt？**：可以从执行机制看。系统有独立的 `AgentState`、工具调用历史、Observation、目标判断、预算和轮次控制，还有反思事件以及持久化 Trace，模型是在一个受约束的执行循环中做决策，而不是一次 Prompt 直接生成最终答案。
    

**补充细节：**

你可以把两者简单理解成：

```text
固定工作流：
A → B → C → D
步骤提前写死
```

而你的 Agent 是：

```text
目标
 ↓
LLM 判断下一步
 ↓
调用 Tool
 ↓
Observation
 ↓
LLM 再判断
 ↓
继续调用 / 换工具 / 结束
```

但是这个循环外面还有后端”护栏”：

```text
            Agent Loop
                ↓
      ┌─────────────────┐
      │ Tool 白名单      │
      │ 最大轮次         │
      │ Token 预算       │
      │ 工具调用限制     │
      │ 权限 / 审批       │
      └─────────────────┘
```

所以最准确的定位不是：

> “完全自主 Agent”

也不是：

> “纯固定工作流”

而是：

> **LLM 负责局部决策，后端负责边界和约束的 Agent 系统。**

另外，如果面试官继续追问”那你这个和 Workflow 到底是不是一个东西”，不要陷入概念争论。你可以直接说：

> “从工程实现角度，两者确实存在交叉，我这个系统也有比较强的工作流编排特征。区别主要在于其中的 Agent Loop 部分不是固定步骤，而是允许 LLM 根据执行状态动态选择下一步动作。所以我认为称为'受约束的任务编排型 Agent'会比'完全自主 Agent'更准确。”

### 4. LLM 规划结果不稳定，怎么处理？

LLM 生成规划的时候，返回结果确实不太稳定，所以我设计了一个分层处理的机制。

第一层是从 Prompt 层面约束。在 `SupervisorService` 的系统消息里，我会明确要求模型只返回纯 JSON 数组，不要有额外的说明文字，并且使用一个相对精确的模型配置，尽量减少格式问题。

第二层是后端清洗。因为模型实际返回的内容经常会带 Markdown 代码块（比如 ```json...```），或者前后会有一些解释性文字，所以我会先移除这些 Markdown 标记和前后说明，然后截取第一个看起来像 JSON 的主体部分。

第三层是兜底提取。如果经过清洗之后还是解析失败，我会用括号计数的方式来提取 JSON 数组，通过追踪括号的深度来定位数组的起始和结束位置。

如果这三层处理都失败了，就返回空列表，`AgentRuntime` 会保存一个空计划，然后系统回退到单 Agent 执行。这样可以避免因为规划解析失败导致简单问答也失败。

不过这里要特别说明一点：**JSON 能解析成功，只能说明格式正确，不能证明规划本身是合理的**。也就是说，任务边界、依赖关系或者工具建议可能还是不合理的。所以当前这些清洗机制只是保证格式层面不出错，并不能保证规划的语义正确性。

**可能追问：**

- **清洗之后还是不是合法 JSON 怎么办？**：会用 `extractJsonArray` 这个方法，通过维护字符串状态和括号深度来提取数组。如果还是失败，就返回空计划并降级到单 Agent。
    
- **JSON 合法了就可以直接执行吗？**：不可以。还需要校验字段是否完整、工具名是否在白名单里、依赖关系是否合法、任务数量是否合理，以及用户权限。完整的 schema 校验和依赖环检测属于生产化需要补强的部分。
    
- **怎么评估规划质量？**：最好是建立一个固定的问题集，人工标注每个问题是否应该拆分、子任务边界应该在哪里、依赖关系是什么、应该用哪些工具，然后统计 Supervisor 的误拆率（不该拆的拆了）、漏拆率（该拆的没拆）、完成率和回退率。
    

**补充细节：**

你可以把这三层处理理解成：

```text
LLM 返回
   ↓
“好的，规划如下：```json[{...}]```”
   ↓
第一层清洗：移除 Markdown 代码块
   ↓
“好的，规划如下：[{...}]”
   ↓
第二层清洗：截取第一个 JSON 主体
   ↓
“[{...}]”
   ↓
第三层：括号计数提取数组
   ↓
成功解析 or 返回空数组
   ↓
空数组 → 回退单 Agent
```

规划结果还会写入任务计划快照和 Agent trace，这样可以方便后续复盘。`SubTask` 的数据结构支持 `goal`、`successCriteria`、`dependsOn` 和 `executionMode` 这些字段。

要强调的是：**当前没有证据表明清洗机制能保证规划的语义正确性**，也没有可以公开的固定收益数据。这些清洗只是让格式层面不出错，语义层面的规划质量还需要通过标注数据集和持续评估来提升。

### 5. Supervisor 结果为什么缓存？缓存有什么风险？

Supervisor 主要负责根据用户问题生成子任务计划，缓存 Supervisor 规划主要是为了避免重复的模型调用。

因为相同的查询，在模型和规划配置没有变化的情况下，Supervisor 生成的规划通常是差不多的，如果每次都重新调用模型生成规划，会增加不必要的响应延迟和 Token 消耗。所以项目中把 Supervisor 的规划结果放到 Redis 中缓存，TTL 设置为 **10 分钟**。命中缓存就直接复用，未命中才调用模型生成。

在缓存设计上，我做了几个优化。

第一，**对 query 做有限规范化**。比如去掉首尾空格、合并连续空白，但不会做大小写转换或者同义词替换。这样可以消除一些无意义的格式差异，同时避免修改类名、接口名、异常码等技术术语。
第二，**缓存 key 包括实际生效的模型名**：
```
query-cache:supervisor:v2:
SHA256(normalizedQuery + effectiveModelName)
```
这样同一个问题使用不同模型时，会得到不同的缓存，避免模型切换以后继续复用其他模型生成的规划。

第三，**缓存 value 增加 schemaVersion**，不再直接保存裸的 `List<SubTask>`：
```
{
  "schemaVersion": 1,
  "createdAt": "...",
  "modelName": "glm-4-plus",
  "plan": [...]
}
```
这里的 `schemaVersion` 主要用于缓存数据结构的版本管理。如果以后修改缓存对象结构，可以升级 schema 版本，旧缓存就按 miss 处理，避免反序列化或者字段兼容问题。

 缓存主要有哪些风险？

**第一是缓存失效和错误复用。** 如果模型或者规划配置发生变化，旧规划可能不再适用。目前通过实际模型名和 TTL 控制缓存生命周期；如果以后规划 Prompt 或其他影响规划结果的配置变化比较频繁，也可以进一步把对应版本加入 key。
**第二是缓存结构升级。** 缓存 value 增加 `schemaVersion`，用于管理 Redis 缓存对象结构变化。例如后续 SubTask 增加字段或者缓存包装结构调整时，可以通过 schemaVersion 判断旧缓存是否兼容，不兼容则按照 cache miss 重新生成。
**第三是缓存内容本身可能不正确。** JSON 能正常解析，只代表结构合法，不代表 Supervisor 的规划一定合理。因此缓存不能替代规划质量评估，还需要通过任务完成率、fallback 比例以及回归测试观察规划质量。
**第四是 Redis 本身可能故障。** Redis 只是缓存，不是业务事实来源。读取或者写入 Redis 失败时，系统会按照缓存 miss 处理，重新调用 Supervisor。这样虽然会增加模型调用次数和延迟，但不会因为 Redis 故障导致整个问答流程不可用。

另外，我只缓存 **Supervisor 的抽象任务规划**，不缓存最终答案。因为最终答案还依赖用户权限、历史上下文、知识库内容和实时检索结果。Worker 真正执行时，仍然会根据当前用户重新进行权限、工具白名单和业务参数校验，缓存不会绕过这些检查。

**所以这个缓存的核心原则是：**

> **缓存可重复计算的规划结果，不缓存用户业务数据和最终答案。**


**可能追问：**

- **为什么不把 userId 放进 key？**：因为这样会降低缓存复用率。当前 Supervisor 的输入并不依赖用户私有知识，规划本身不涉及用户数据，因此没有必要把 userId 加入 key。如果以后 Supervisor 的规划依赖用户配置、Space 或其他私有上下文，再把对应的用户/租户配置指纹加入 key。
    
- **如果 Prompt 改了，怎么避免用到旧的规划？**：当前只能等 10 分钟 TTL 过期。当前 Supervisor Prompt 相对固定，所以目前没有单独加入 Prompt 版本；如果规划 Prompt 后续进入频繁迭代，就应该加入。
    
- **Redis 挂了会怎样？**：缓存读取或写入异常会被捕获并吞掉，未命中的时候会重新调用模型生成规划。代价是模型调用次数和延迟会上升，但不会导致核心流程直接失败。
    
- **如果两个请求同时 miss，会不会同时调用两次 LLM？** 会存在这种可能，这属于典型的 **cache stampede / 缓存击穿**问题。当前 TTL 比较短、Supervisor 本身调用量有限，所以暂时没有做复杂的请求合并。如果生产规模扩大，可以增加分布式锁 / single flight，先等第一个请求生成规划，其他请求等待并复用结果。或者增加短时间随机 TTL，降低大量缓存同时过期的概率。

**补充细节：**

缓存流程：

```text
用户 query
   ↓
query 规范化
   ↓
计算 Redis key
   ↓
查询 Redis
   ↓
命中缓存
   ↓
读取缓存对象
   ↓
检查 schemaVersion
   ↓
      ├── 兼容当前版本
      │        ↓
      │    反序列化 plan
      │        ↓
      │    基础校验通过
      │        ↓
      │    返回缓存规划
      │
      └── 不兼容
               ↓
          cache miss
               ↓
          调用 Supervisor 重新生成
               ↓
          写入新 schemaVersion 缓存
```

当前实现了有限 TTL 和 Redis 故障下的降级，但没有证据表明做了请求合并或者严格的主动失效。生产化建议把模型版本、Prompt 版本、规划配置和必要的租户边界都纳入 key，并增加版本化、主动失效、命中率监控、脏命中监控和缓存延迟监控。

### 6. 多子任务并行一定比串行好吗？

多子任务并行不一定比串行更好，关键取决于任务之间有没有依赖关系。
在我的设计里，多 Agent 执行不是简单地把所有子任务同时启动，而是根据 Supervisor 生成的任务依赖关系构建 DAG有向无环图，由依赖关系决定哪些任务可以并行，哪些任务必须等待。
Supervisor 会一次生成多个 `SubTask`，每个任务除了包含目标、描述、工具限制之外，还会携带 `dependsOn` 依赖信息。系统拿到这些任务后，会先根据依赖关系构建 DAG，并进行环检测。如果发现任务规划存在循环依赖，会降级为顺序执行，避免调度进入死循环。对于没有依赖关系的任务，会通过拓扑排序划分到同一个执行波次，在波次内部并行执行。

```
比如：
- R1：检索错误原因
- R2：查询历史类似故障案例

两个任务都只依赖用户问题本身，可以放在同一个 Wave 中，通过线程池并发执行。

但是：
- R1：解析日志，提取异常版本号
- R2：根据版本号查询对应发布记录

R2 依赖 R1 的输出，就会被划分到后续 Wave，等待前置任务完成后再执行。
这样既可以利用并行降低整体响应时间，也避免因为强行并发导致上下文缺失。
```

在执行过程中，每个 Worker 都会基于独立的 `AgentState` 快照运行，包含自己的工具调用记录、Observation 和执行产物，避免多个任务并发修改同一个状态导致数据竞争。
一个 Wave 内所有 Worker 执行完成后，会进入状态合并阶段。系统按照固定顺序把各个子任务产生的结果合并回共享状态，保证最终结果具有确定性。

同时，事件推送也采用异步队列方式处理：
Worker 执行过程中只产生事件并写入 Event Queue，由独立消费者线程按照顺序消费，再统一通过 SSE 推送给前端。
这样可以避免多个 Worker 同时操作 SSE emitter 导致事件乱序或者并发异常。

并行执行也会带来一些额外成本。

第一是资源压力增加。多个 Worker 同时调用 LLM、检索服务或者外部工具，会提高瞬时请求量，所以需要通过线程池大小、Token 预算和调用次数限制控制资源消耗。
第二是结果融合复杂度增加。多个任务可能返回重复信息、不同粒度结果，甚至存在冲突，所以合并阶段需要保留任务来源、执行状态和证据信息，不能简单拼接文本。
第三是调试复杂度提升。并发执行后，任务之间的执行顺序不固定，需要依赖 Trace、TaskId 和事件时间戳进行问题定位。

所以在我的设计里，并行能力的核心不是提高任务数量，而是**通过 DAG 感知任务依赖，在保证正确性的前提下，把真正独立的任务并行执行**。

整体流程可以概括为：

```text
用户请求
   ↓
Supervisor生成SubTask
   ↓
构建DAG + 环检测
   ↓
拓扑分层生成Wave
   ↓
Wave内并行执行Worker
   ↓
状态合并
   ↓
依赖检查
   ↓
下一Wave执行
   ↓
最终结果生成
```

**可能追问：**

- **为什么不用简单的 CompletableFuture 把所有 Worker 都并行执行？** 因为任务之间存在依赖关系。简单并行只能解决执行速度问题，但无法处理上下游输入依赖。例如后一个任务需要前一个任务提取的信息时，提前执行没有意义。DAG 调度可以根据真实依赖关系决定并行边界。
    
- **如果两个 Worker 修改了同一个状态怎么办？** Worker 执行阶段不共享可变状态，每个任务使用自己的 State 快照。只有 Wave 完成后进入单线程合并阶段，根据固定规则把结果合入共享状态，避免并发修改。
    
- **并行一定会降低延迟吗？** 不一定。如果任务数量少、任务本身耗时短，增加调度和合并成本可能收益有限。另外如果下游服务存在限流，并行反而可能增加失败率。所以需要通过 P95 延迟、Token 消耗、失败率和资源占用进行评估。

- **DAG怎么构建？** Supervisor 输出的 SubTask 中包含 dependsOn 数组，我会把每个 SubTask 作为 DAG 节点，根据 dependsOn 建立有向边，然后通过 Kahn 拓扑排序检测环并生成执行层级。入度为0的节点属于同一个执行 Wave，可以并行执行；下一层节点等待上一层完成。
	
	如果检测到环，说明规划结果存在循环依赖，会记录 Trace，然后降级为顺序执行，保证任务可用性。
	
	并行执行时每个 Worker 使用独立 AgentState，执行结果以 WorkerResult 形式返回。一个 Wave 完成后，由单线程按照固定顺序合并 observations、artifacts 和任务状态，再生成下一 Wave 的执行上下文，避免多个 Worker 并发修改共享状态。

### 7. 多 Agent 结果怎么融合？

多 Agent 结果融合的核心问题是需要解决任务边界、结果粒度和失败状态的问题。

如果直接把多个 Worker 的输出拼接起来，会有几个问题：
第一，**重复问题**。不同 Worker 可能执行相似检索任务，召回相同文档片段，如果直接合并，会导致答案重复。
第二，**结果粒度不一致**。有的 Worker 返回的是检索到的原始资料，有的返回的是总结，有的返回的是执行结果，如果没有统一结构，最终答案容易混乱。
第三，**部分任务失败的问题**。多 Agent 执行过程中，某个子任务可能失败。如果简单忽略失败结果，用户不知道哪些内容已经覆盖，哪些没有完成。

所以我的设计思路是：
> 不直接融合 Worker 的自然语言输出，而是先保留每个子任务的上下文信息，再由统一的结果生成阶段进行整理。

在当前实现中，Supervisor 会生成结构化 `SubTask`，里面包含：
- task label
- goal
- description
- successCriteria
- dependsOn
- executionMode

Worker 执行时，每个任务有独立的 `AgentState`，记录：
- 当前任务目标
- 工具调用历史
- observation
- 执行状态
- 失败信息
- 产生的结果

AgentLoop 执行完成后，会根据目标评估结果判断该子任务是否完成，并将执行过程写入 Trace。

最终合成阶段，不是简单按照 Worker 顺序拼接，而是：
1. 根据任务关系组织结果顺序；
2. 优先使用工具返回和检索得到的内容作为依据；
3. 对失败任务保留状态信息；
4. 让最终生成模块根据这些结构化结果组织回答。

例如：
```
Worker A:
目标：查询接口错误原因
结果：找到异常码文档

Worker B:
目标：分析解决方案
结果：根据文档总结排查步骤

Worker C:
状态：失败
原因：未找到相关配置

            ↓

ResponseComposer

            ↓

最终回答：
- 已确认的问题原因
- 对应解决方案
- 未覆盖的信息
```

这样用户能知道哪些结论来自检索证据，哪些是模型基于资料的分析。

**可能追问：**

- **怎么避免重复内容？**：ResponseComposer 会根据多个 Worker 返回结果进行整理，避免重复表达。Worker 返回统一 Evidence 对象，然后融合阶段基于 chunkId 做严格去重。
    
- **如果两个子任务结果冲突怎么办？**：不要强行投票或者只选一个。因为 Agent 输出可能一个来自旧文档，一个来自新文档，也可能一个是事实，一个是推测。处理方式应该：
		1. 保留两个来源；
		2. 标记来源和时间；
		3. 提升可信来源优先级；
		4. 如果无法判断，明确告诉用户存在冲突。
例如：
> 文档 A 描述接口版本为 v1，文档 B 描述已经升级到 v2，需要确认当前线上版本。
    
- **怎么区分事实和推测？**：检索到的原文可以标记为"检索证据"，模型根据证据推理出来的内容标记为"推测"或"分析"，两者的可信度不同。
    

**补充细节：**

```text
错误的融合方式：
Worker A 结果 + Worker B 结果 + Worker C 结果
直接拼文本 → 重复、层次乱、无法溯源

正确的融合方式：
Worker A → { 任务标签、目标、结果、证据、状态 }
Worker B → { 任务标签、目标、结果、证据、状态 }
Worker C → { 任务标签、目标、结果、证据、状态 }
         ↓
    统一合成器
         ↓
   - 去重（根据 chunk ID 或内容 hash）
   - 按证据级别排序（检索证据 > 推测）
   - 标记未覆盖部分
   - 标注冲突和不确定性
         ↓
    最终答案
```

### 8. Agent 什么时候触发反思和重规划？

反思和重规划主要发生在 Agent 执行过程中遇到问题的时候。

Supervisor 的规划是在任务开始之前做的，主要是根据用户问题和初始上下文决定是否拆分、怎么拆分。而反思和重规划发生在执行过程中，输入是当前的 `AgentState`、目标、工具历史、失败的动作以及观察结果，目标是分析为什么没有推进，并改变后续的执行策略。

当 Agent 连续两轮都没有新的工具调用、没有获得有效证据、或者目标没有推进的时候，就会触发 `ReflectionService`。反思的结果不是直接给出最终答案，而是一个问题描述和建议策略，比如"工具参数可能错误""关键词过窄""应该换一个搜索工具"或者"需要补充用户信息"。

拿到反思结果之后，`ReplanningService` 会根据这个建议更新待执行的步骤，然后再进入下一轮循环。反思结果也会写入 trace，这样可以知道在哪一轮触发了反思、原因是什么、采用了什么替代策略。

不过要注意，反思和重规划也不能变成无限重试。它们仍然受到最大轮次、时间、Token 和工具调用次数的限制。如果新的策略还是没有进展，就会终止并说明原因。

**可能追问：**

- **重规划和 Supervisor 规划有什么区别？**：Supervisor 是任务开始时的初始规划，主要根据用户的问题判断是否需要拆分任务，并生成多个 SubTask，同时确定任务之间的依赖关系和执行模式。它解决的是整个任务应该怎么拆、怎么组织。ReplanningService 则是在 Agent 执行过程中发现问题后，对当前执行策略进行调整。它会结合当前 AgentState 和 ReflectionResult，告诉 Agent 当前哪里出了问题、后面可以尝试什么不同的策略。它解决的是当前这个子任务接下来应该怎么走。
    
- **什么情况下会触发反思？**：连续两轮没有新的工具调用、没有获得有效证据、或者目标一直没有推进的时候。具体的触发条件可以根据任务类型调整。
    
- **反思之后一定能成功吗？**：不一定。反思只是尝试换一个策略，如果新策略还是没用，或者已经达到了预算上限，任务就会终止并记录失败原因。
    

**补充细节：**

你可以这样理解两者的区别：

```text
Supervisor 规划（事前）：
用户问题 + 初始上下文
   ↓
判断要不要拆分
   ↓
生成子任务结构
   ↓
开始执行

反思和重规划（事中）：
Agent 执行卡住了
   ↓
分析 AgentState、工具历史、观察结果
   ↓
识别问题：参数错误？关键词不对？工具不合适？
   ↓
生成建议策略
   ↓
更新待执行步骤
   ↓
继续执行
```

反思机制的关键是：

> **不是简单重试，而是分析为什么失败，然后尝试不同的策略。**

### 9. Agent 如何控制预算？

目前主要控制四类预算：
1. **最大执行轮次**：10轮
2. **最大执行时间**：600秒
3. **最大 Token 消耗**：32000 token
4. **最大工具调用次数**：20次

因为单独限制某一个维度是不够的。
比如只限制轮次，某一轮模型可能生成大量内容；只限制 Token，模型仍然可能频繁调用工具；只限制工具次数，又无法控制模型推理过程过长。所以需要多个维度组合约束。

每轮开始之前，系统会读取当前状态，累计已经消耗的 Token、工具调用历史和开始时间，检查是否超过了阈值。如果超过了，就返回明确的预算超限原因，记录到任务和 trace 里，不再继续调用模型。

**可能追问：**

- **预算超限了会怎样？**：任务会终止，并记录预算超限的原因（比如超过最大轮次、超过最大 Token 或超过最大时间）。前端会收到一个明确的超限提示，用户可以看到任务执行到哪里、为什么停止了。
    
- **不同任务的预算怎么设置？**：可以按任务类型区分。比如简单的检索问答可能设置 5 轮、3000 Token；复杂的生成任务可能设置 10 轮、8000 Token。具体阈值需要根据固定测试集和历史数据调整。
    
- **怎么验证预算设置是否合理？**：主要看预算超限率、平均 Token、任务成功率、超时率和单位任务成本。如果超限率太高，说明预算太紧；如果平均 Token 远低于上限，说明预算太松。阈值不能只往上调，要找到可接受的折中。
    
### 10. Supervisor 生成的子任务如何做结构校验？

>Supervisor 返回的内容即使能够被解析成 JSON，也不能直接执行，后端会先做自动校验。解析只解决格式问题，执行前还需要做结构和语义层面的校验，避免模型生成越权、重复或者无法完成的任务。

答：
首先校验任务数量。当前项目设计上Supervisor 默认生成 2~4 个子任务，复杂任务允许扩展到 5 个，但通过最大任务数限制控制成本。任务数量为 0 时按单 Agent 处理；数量超过上限5时不能无限创建 Worker，超过限制时优先让 Supervisor 重新合并任务粒度，如果仍然无法满足，则降级为单 Agent 或请求用户补充信息。然后校验每个任务的必填字段，例如 `label`、`description`、`toolHint`，如果有目标驱动执行，还要检查 `goal` 和 `successCriteria` 是否为空。

其次校验字段内容。`label` 只能使用系统支持的任务类型，`toolHint` 只能作为建议，真正执行时还要和后端工具注册表比对，不能因为模型返回了一个字符串就动态加载任意工具。`dependsOn` 只能引用当前计划中已经存在的任务标识，不能引用自身，也不能出现环。`executionMode` 只能取系统支持的枚举值，未知值按安全的串行模式处理或者让规划失效。

最后校验任务是否符合当前用户权限和业务目标。比如用户只有查询权限时，计划不能生成创建笔记、删除文档等写操作；如果任务描述和原始问题没有关系，也不能因为 JSON 合法就执行。校验失败后优先重新规划一次；仍然失败就返回空计划，回退到单 Agent 或直接请求用户补充信息。

**可能追问：**

- **为什么不只使用 Java Bean 校验？**：Java Bean 校验主要解决对象结构合法性，比如字段是否为空、类型是否正确、枚举值是否合法。但是 Supervisor 输出的问题不仅是数据格式问题，还包含业务逻辑问题，例如 dependsOn 引用是否存在、任务之间是否形成环、toolHint 是否属于系统支持范围等。所以我会分两层校验：
	第一层是结构校验，例如 JSON 解析、字段完整性、枚举校验；
	第二层是业务校验，例如依赖关系检查、工具白名单检查和任务合法性检查。
	两层结合才能保证生成的计划可以执行。
    
- **模型返回未知工具名怎么办？**：Supervisor 返回的 toolHint 只是规划建议，不代表真实可执行工具。
	Worker 执行前会根据子任务允许调用的工具列表和后端工具注册表进行匹配。如果模型返回不存在的工具：- 如果可以通过其他合法工具完成，则重新规划；- 如果没有替代方案，则将该子任务标记失败，不执行非法调用。
    
- **依赖关系如何检查？**：依赖关系校验主要分三个步骤。第一，根据任务 id 建立节点映射。第二，检查 dependsOn 引用是否合法，包括：- 依赖任务是否存在； - 是否依赖自身。第三，构建 DAG，通过拓扑排序判断是否存在环。如果存在环，说明 Supervisor 生成的执行计划无法确定顺序，需要重新规划，而不是进入执行阶段。
    
- **校验失败是否一定回退单 Agent？**：不一定，需要区分失败类型。
	如果只是格式或者规划质量问题，比如字段缺失、任务拆分不合理，可以让 Supervisor 重新生成一次。
	如果是执行层面的安全问题，例如工具不存在、权限不足、依赖关系成环，则不能简单降级绕过，需要阻止执行。
	如果重新规划失败，但是用户目标仍然可以通过单 Agent 完成，可以降级到单 Agent；否则需要返回用户澄清。
	
- **为什么限制Worker数量？** 主要是成本和稳定性的考虑。Agent 任务数量越多，不一定代表效果越好，反而可能造成大量重复检索、结果合并困难以及 Token 增长。所以我更关注任务覆盖率，而不是单纯增加 Worker 数量。
	
- **Supervisor 规划错了怎么办？** Supervisor 生成的计划本身不是完全可信的，所以系统不会直接执行模型输出。首先通过结构校验保证计划可解析；然后通过业务校验保证工具、依赖和权限合法；执行过程中 Worker 还有自己的 Agent Loop，会根据 Observation 判断任务是否完成。如果执行过程中连续失败，会触发 Reflection 和 Replanning，让系统重新调整策略。所以 Supervisor 负责提出计划，但最终执行过程仍然受到后端约束。
	
- **为什么 Supervisor 不直接生成完整执行流程，而是生成 SubTask？** 因为 Supervisor 更适合负责高层规划，而具体工具调用过程存在动态性。如果 Supervisor 直接生成完整执行流程，需要提前知道所有工具返回结果，实际执行时容易失效。所以当前设计让 Supervisor 只负责拆分目标，Worker 根据自己的 Agent Loop 在受约束范围内完成具体执行。
	
**补充细节：**

```text
LLM 计划
   ↓
JSON 解析
   ↓
Schema 校验
   ↓
任务数量校验
   ↓
字段与枚举校验
   ↓
工具白名单校验
   ↓
依赖图校验
   ↓
权限与目标校验
   ↓
通过：创建任务步骤
失败：重规划 / 降级 / 终止
```

结构校验、业务校验、权限校验流程应该是：

```
Supervisor生成计划
       ↓
结构校验
(JSON格式、字段)
       ↓
业务校验
(工具、依赖、任务合法性)
       ↓
创建Worker
       ↓
执行工具前
       ↓
权限校验
(userId、资源权限)
```

当前项目已经具备计划解析、任务状态和工具执行约束，但不能把 JSON 清洗等同于完整的 schema 校验。字段校验、依赖环检测和计划语义评估属于需要继续补强的部分。

### 11. Worker 的工具白名单具体怎么保证不被绕过？

Worker 的工具白名单，核心安全原则是**校验全部放在后端执行层强制拦截，完全不依赖模型自觉遵守规则**。

首先，Supervisor 拆分子任务的时候，会根据任务类型生成一份允许使用的工具列表，也就是 allowedTools，保存到当前 Worker 的 AgentState 执行状态里面。比如检索任务只允许 ragSummary，网页分析任务只允许 fetchUrl。

当大模型返回 ToolCall 调用工具时，请求会统一进入 AgentLoop 的工具调用入口。 这里第一层防护是 ToolRegistry 工具注册表。没有用反射动态加载模型传过来的任意工具名称，所有合法工具都在后端提前注册维护成一张固定映射表。如果模型编造了一个不存在的工具名，在注册表查不到，直接拒绝执行。

就算工具已经注册成功，还会走第二层校验：判断这个工具是否存在于当前 Worker 的 allowedTools 白名单里。不在白名单，直接返回 tool_denied 拒绝结果，作为观测值传给 Agent，不会走到真正的工具业务逻辑。

这两层校验通过之后，还有第三层防护。工具路由转发到业务服务时，还要做用户和资源的权限校验，避免操作其他用户的资源。白名单控制的是**这个任务能不能调用这个能力**，业务权限控制的是**这个用户能不能操作某一份具体的数据**。两层权限互不替代。

就算遇到 Prompt 注入，诱导模型去调用高危工具也无法绕过。Prompt 注入只能改变模型输出的内容，后端三层校验逻辑不会失效，最终执行权完全由后端控制，而不是由大模型决定。

如果调用被拒绝，拒绝信息会封装成 Observation 返回给 Agent 并且埋点记录链路日志。Agent 可以尝试更换合规工具继续执行，分析失败原因，没有可行方案时就终止任务。

**可能追问：**

- **Prompt 里已经写了工具范围，为什么还需要后端校验？**：模型可能误选工具，也可能被用户输入中的提示词注入影响。Prompt 是行为约束，后端白名单才是安全边界。
    
- **工具白名单和用户权限有什么区别？**：白名单限制任务能调用哪类能力，用户权限限制用户能操作哪些资源。两层都必须校验，不能互相替代。
    
- **工具调用失败后是否自动换工具？**：只有在新的工具仍然属于白名单、权限允许且目标允许的情况下，才可以由反思和重规划选择替代工具。

**补充细节：**

```text
             Supervisor
                 ↓
        生成 SubTask
        allowedTools=[ragSummary]
                 ↓
              Worker
                 ↓
          AgentLoop执行
                 ↓
       LLM产生 ToolCall
                 ↓
        Tool Registry检查
                 ↓
       是否在allowedTools?
        ↓               ↓
        是              否
        ↓               ↓
 用户/资源权限校验   tool_denied
        ↓
    执行工具
        ↓
 Observation返回Agent
```

当前项目的工具白名单主要用于控制 Agent 执行边界。生产化还应补充工具参数 schema、敏感操作审批、资源级权限、审计日志和拒绝调用指标。

### 12. 子任务状态如何设计？进程中断后能否恢复？

我设计了两层持久化模型：Task 和 Step。Task 对应用户的一次完整请求，记录原始问题、整体计划快照、Token 消耗和全局状态；Step 对应 Supervisor 拆分出来的每一条子任务，维护执行目标、依赖关系、成功标准、独立状态与执行结果。同时我会序列化保存 AgentState 快照，作为推理恢复的辅助材料，但不作为判断任务是否执行成功的唯一依据。

状态分为两套：一套是核心业务状态，`CREATED、RUNNING、COMPLETED、FAILED、BLOCKED、CANCELLED`；另一套是过程状态，`PLANNING、REFLECTING、REPLANNING、WAITING_USER`。**所有状态变更都由后端控制，LLM 只能输出执行动作，没有权限直接修改任务状态**。

关于中断恢复，当前实现的是**人工触发式恢复**，不是服务宕机自动接管。完整恢复流程分为四步：第一，通过 taskId 查询任务，校验用户权限与任务状态，仅允许` FAILED、BLOCKED、WAITING_USER` 这类暂停态恢复；第二，加载计划快照、Step 记录、序列化的 AgentState，拼装恢复上下文；第三，遍历所有子任务，已经标记 COMPLETED 的步骤直接跳过，失败的步骤根据根因判断是重试还是重新规划，同时校验前后计划一致性，防止旧结果复用在新任务上；第四，校验 DAG 依赖关系，继续执行剩余合法子任务。


而 RUNNING 状态的服务崩溃自动恢复，目前只是扩展设计。这个场景风险很高：工具写操作可能数据库落库成功，但服务还没来得及更新 Step 状态，直接重试会造成重复数据。生产化方案需要补充心跳、租约超时、分布式抢占锁、幂等 Key，还要查询业务侧数据确认副作用是否真实完成，这套能力当前项目暂未实现。

**可能追问：**

- **为什么不直接保存 `AgentState` 就够了**：
	AgentState 是 Agent 运行时的推理上下文，保存目标、工具历史和观测结果，用来给大模型做下一步决策。 但它没法准确记录业务真实执行情况。比如创建笔记时服务宕机，仅凭 AgentState 无法判断写入是否成功，重试就会产生重复数据；同时它也承载不了子任务 DAG 依赖、任务阻断这类编排信息，生命周期很短，不适合长期留存审计日志。
	
	所以我们单独持久化 Task 和 Step 表，保存每个子任务的真实状态、依赖和幂等信息。断点恢复时先确认 Step 的执行情况，规避重复执行风险，再加载 Agent 上下文继续运行。 
	简单说：AgentState 负责 Agent 怎么思考，Task/Step 管控任务真实进度、安全恢复和链路追踪，二者互补，不能互相替代。
    
- **`RUNNING` 状态服务挂掉怎么处理？**：现有方案依靠状态判断异常；生产环境补充心跳时间戳，超时之后交由调度器重新接管任务。
    
- **失败为什么不全部直接重试？**：要看失败根因，临时网络故障适合重试；业务逻辑层面的失败重复执行没有价值，需要交给 Agent 反思、重新规划子任务。

**补充细节：**

```text
  CREATED / PENDING
     ↓
  PLANNING
     ↓
  RUNNING
     ├── 完成：COMPLETED
     ├── 需要用户补充：WAITING_USER
     ├── 临时失败后恢复：FAILED / 再次恢复执行
     ├── 前置失败：BLOCKED
     ├── 反思：REFLECTING
     ├── 重规划：REPLANNING
     └── 用户取消：CANCELLED
```

恢复后的执行流程：
```
查询 Task
   ↓
检查状态
   ↓
加载计划快照
   ↓
加载 Step 状态
   ↓
跳过 COMPLETED Step
   ↓
检查依赖关系
   ↓
恢复 AgentState
   ↓
执行未完成 Step
   ↓
更新状态
```

### 13. 任务失败、部分成功和用户介入如何处理？

根据失败类型和影响范围进行处理。

如果是**局部失败**。比如一个复杂问题拆成多个子任务，其中一个检索任务失败，但是其他任务已经成功获取了相关资料，这种情况下不会直接终止整个任务，而是在结果合并阶段标记该部分未完成，使用已有结果生成回答，同时记录失败原因。

其次是**依赖失败**。比如一个子任务需要前一个任务生成的产物作为输入，如果前置任务失败，那么后续任务没有继续执行的条件，会将后续任务标记为 `BLOCKED`，避免基于缺失数据继续执行。

第三类是**不可恢复失败**。例如权限校验失败、危险写操作被拒绝、用户取消任务，这类情况不能通过重试或者重新规划解决，需要直接终止对应流程。

对于需要用户补充信息的情况，比如缺少 URL、版本号或者查询范围不明确，Agent 会返回澄清请求，并暂停当前任务。用户补充信息后，可以基于已有任务状态继续执行，而不是重新创建一次请求。
最终结果返回时，也会区分：
- 完全成功：所有关键子任务完成；
- 部分成功：核心目标完成，但部分非关键任务失败；
- 执行失败：关键步骤失败，无法继续。

同时，内部会通过 Trace 记录详细的失败原因、工具调用过程和状态变化，前端通过 SSE 接收任务进度和澄清事件，让用户知道当前执行到了哪里。

**可能追问：**

- **部分成功时是否返回 HTTP 500？**：要看核心目标是否完成，并通过任务状态和响应字段表达部分成功；基础请求失败与异步任务部分完成可以采用不同协议。
    
- **什么时候一定要让用户介入？用户补充信息后怎么恢复？**：缺少关键业务输入、权限审批、不可恢复的关键步骤失败或检测到结果冲突且无法验证时，都应该请求用户确认或补充信息。
	恢复时根据任务 ID 找到之前保存的状态，包括已经完成的步骤、工具调用记录和已有产物，然后从阻塞位置继续执行，而不是重新走完整 Agent Loop。
    
- **失败原因如何避免泄露内部信息？**：内部 trace 保存详细异常，面向用户只返回经过分类和脱敏的错误码、可执行建议和已完成范围。
    
- **怎么判断一个失败是不是影响最终结果？**：主要依赖子任务之间的依赖关系和任务目标。比如一个“查询故障原因”的任务包含多个独立检索来源，其中一个来源失败影响有限；但是如果“生成修复方案”依赖“获取错误日志”，那么错误日志获取失败会阻塞后续任务。
    
- **部分失败情况下，LLM 会不会自己补全不存在的信息？**：需要限制。合成阶段只能基于 Worker 返回的 Observation 和检索证据生成答案，对于缺失的信息需要明确说明“未找到相关资料”，不能让模型根据经验推测。

### 14. Agent 上下文如何隔离，怎样避免 Worker 互相污染？

多 Worker 执行时上下文隔离主要是通过状态隔离，但结果共享。

每个子任务对应的 Worker 都有独立的执行上下文，保存这个 Worker 专属的子任务目标、工具调用记录、观测结果、独立预算计数器，还有本轮 AgentLoop 全部的运行信息。这部分运行时数据各个 Worker 之间完全隔离，互不修改，只共享任务真正需要的信息。

共享信息包括三层：
	第一层是全局公共基础数据，像用户原始提问、会话 ID、用户权限和可用知识库，所有 Worker 只读，不会各自篡改；
	第二层是依赖任务之间传递的结构化产物，串行任务不会把上游完整的 AgentState 全部下发，只会筛选下游真正需要的关键字段，比如错误码、服务名、证据 ID，过滤掉冗余的工具历史和中间失败记录，减少 Token 开销，避免无效信息干扰；
	第三层是最终汇总阶段，每个 Worker 输出一套标准化的结果对象，交给合并模块生成最终答案。

并行和串行两种模式的隔离策略也不一样。并行执行的 Worker 只会拷贝一份只读的初始公共上下文，各自维护独立状态，运行全程互不干扰，全部执行完毕之后再统一合并结果，规避并发修改带来的数据竞争。而存在依赖的串行任务，下游仅读取上游提炼后的结构化摘要，不继承完整的推理链路。

除此之外，隔离设计也兼顾安全防护。外部文档、网页、工具返回的内容只能作为观测数据，不能改写系统指令、工具白名单这些后端管控的执行规则，防止一个 Worker 拿到恶意内容污染整个任务的执行权限。

**可能追问：**

- **为什么不让所有 Worker 共享一个 `AgentState`？**：如果所有 Worker 共享同一个状态，会有几个问题：
	第一，执行历史会污染。例如 Worker A 调用失败产生的错误 Observation，可能影响 Worker B 后续决策。
	第二，预算统计会混乱。无法判断到底是哪一个 Worker 消耗了 Token 或工具调用次数。
	第三，并发执行时会产生线程安全问题。多个 Worker 同时修改同一个状态对象，可能导致数据覆盖。
	第四，问题定位困难。出现错误时无法知道是哪个 Worker 的执行过程导致。
    
- **`completedContext` 应该传什么？为什么不直接把 Worker A 的完整结果塞给 Worker B？**：上游输出精简结构化产物，下游只读取业务必要字段，不携带完整工具调用和推理历史。不完整传入是因为完整上下文通常包含大量无关信息：工具调用历史、中间失败尝试、大量原始文本、模型推理痕迹。这样会增加 Token 消耗，也容易让后续 Worker 受到错误信息影响。
    
- **上下文隔离能防止 Prompt Injection 吗？**：不能完全防止，它只能降低 Prompt Injection 的影响范围。它主要用来避免恶意内容在多个 Worker 之间横向扩散。比如某个检索 Worker 拿到了一段带注入的文档，如果所有 Worker 共用一份上下文，这条恶意内容就可能影响后面负责写操作的任务。而上下文隔离之后，对话历史、工具记录、观测结果都是每个 Worker 独立维护的，外部不可信数据只会留在当前 Worker 的上下文里，不会自动传播给其他任务，缩小攻击的影响范围。但隔离拦不住**当前这个 Worker 本身被注入诱导**。还需要对外部内容做不可信数据标记、工具权限校验、输出约束和敏感操作审批。

**补充细节：**

```text
用户目标 + 权限范围
          ↓
    Worker A 独立 State
    Worker B 独立 State
    Worker C 独立 State
          ↓
结构化产物 / 证据引用 / 失败状态
          ↓
       合成器
```

当前项目的任务执行链路已经记录工具历史、Observation、产物和 trace，并对顺序任务传递必要上下文。完整的并行 Worker 隔离和标准化证据对象属于后续生产化建设。

### 15. Agent 如何处理 Prompt Injection 和敏感数据？

在企业知识库场景里，Prompt 注入的来源主要分为两类不可信输入：一是用户主动构造的恶意提问，诱导 Agent 忽略系统规则、调用高危工具；二是外部导入的数据，像检索文档、网页、上传文件，内容里藏有篡改指令的恶意文本。我采用分层防护的方案，安全边界最终由后端管控，不依赖大模型自身辨别恶意内容。

我的处理思路是分层防护。

首先，在上下文构造阶段区分不同类型的信息。把系统 Prompt、用户问题、工具返回结果和知识库内容划分成独立的角色区块。检索出来的文档和外部观测结果只会标记为参考素材，不能作为控制 Agent 行为的执行指令。就算文档内带有忽略限制、删除数据这类恶意话术，它仅仅作为回答的参考文本，无权修改工具权限与执行策略。

其次，工具调用不能依赖模型自觉遵守。即便模型被注入诱导，生成了高危的 ToolCall 请求，执行链路依然会做多道拦截：校验当前 Worker 的工具白名单、校验工具参数是否符合 Schema 规范、校验操作用户对目标资源是否具备业务权限。新增、删除、修改这类带有数据副作用的操作，还会附加额外管控，不会仅凭模型的决策直接执行。

对于敏感数据，需要控制数据流转。知识库检索结果进入 Agent 前需要经过权限过滤，避免不同用户之间的数据泄露。链路日志不会直接保存密钥、完整隐私文本这类敏感信息，只留存文档 ID、分片编号、摘要和哈希值用于排查。对于删除配置、对外推送消息等高风险动作，额外增加人工审批，留存完整审计记录。

**可能追问：**

- **只在 Prompt 里写“忽略文档指令”够不够？**：不够。Prompt Injection 属于不可信输入问题，后端能力边界、权限校验和敏感操作审批才是主要防线。
    
- **检索结果中出现另一个用户的数据怎么办？**：这是权限过滤缺陷，必须在进入 Agent 上下文前阻断并报警，不能依赖合成器自行隐藏。
    
- **如何验证防护有效？**：建立包含指令注入、越权工具调用、跨 Space 数据请求和敏感信息泄露的安全回归集，验证拒绝率、误放行率和日志脱敏结果。
    
- **如果注入成功，模型生成了合法的搜索工具调用，如何防护？**：工具白名单只代表允许调用搜索，不代表可以访问全部数据。检索前会基于用户身份、空间权限过滤数据集，用户无权限的文档会直接过滤，模型也拿不到敏感内容。
    
- **为什么不能交给 LLM 自行识别恶意指令？**：大模型本身就是被攻击的对象，如果让模型自己判断内容是否恶意，很容易被绕过。正确的职责划分是：模型负责业务理解与任务规划，后端负责全部安全约束，两层分离保障 Agent 可控安全。

### 16. 如何证明多 Agent 比单 Agent 更好？

不能仅凭一个演示问题或者主观感觉判断 Supervisor 有价值。需要建立固定测试集，覆盖简单事实问答、需要多步证据的问题、存在任务依赖的问题、工具失败和部分成功等场景，并使用相同模型、相同知识库和相同预算进行对照实验。

对照组是单 Agent，实验组是 Supervisor-Worker。除了最终答案质量，还要记录是否正确判断拆分、子任务完成率、目标覆盖率、证据忠实度、重复率、冲突率、回退率、平均和 P95 延迟、模型调用次数、输入输出 Token、工具调用次数以及单位成本。并行方案还要记录峰值并发、下游错误率和资源使用量。

分析时不能只看平均值。少数超慢或高 Token 请求会影响生产体验，所以需要观察 P95、P99 和失败样本。还要单独统计误拆分和漏拆分：简单问题被错误拆分，会增加成本；复杂问题没有拆分，可能导致单 Agent 失败。只有在质量收益能够覆盖额外成本和复杂度时，才适合扩大多 Agent 使用范围。

**可能追问：**

- **最终答案质量怎么评估？**：检索层可以评估 Recall、Precision、MRR 或 NDCG，生成层可以评估 Faithfulness、Relevance、Correctness，并结合人工标注和固定参考答案。
    
- **为什么不能只看成功率？**：成功率无法反映延迟、成本、重复内容和资源峰值；一个成功但耗时和耗费 Token 很高的方案未必适合生产。
    
- **如何避免模型随机性干扰对比？**：固定数据、Prompt、模型版本和预算，记录实验配置，增加重复运行次数，并报告均值和分位数。

### 17. 如果让你重新设计 Supervisor-Worker，你会怎么改？

第一，**增强 Worker 隔离性与异常自动恢复能力**。 现在每个 Worker 天然拥有独立 AgentState，隔离工具历史、观测数据、预算消耗，执行结束只输出结构化结果，不会互相污染上下文。 并且全链路 Task、Step、快照、Trace 都已持久化，支持人工断点恢复。 生产化升级我会补充心跳、租约机制，自动识别宕机卡住的 RUNNING 任务，通过分布式锁实现安全接管，同时针对写操作增加幂等控制，彻底解决恢复重试导致的副作用问题。

第二，**迭代版本化的反思重规划闭环**。 目前已经支持执行失败、无进展时的反思和重规划。 后续我会让每一次重规划都生成**版本化计划快照**，记录原始方案、调整步骤、失败原因，方便任务回放、问题复盘，让重规划过程可追溯、可审计。

第三，**标准化多 Worker 证据融合体系**。 现有已经实现多任务结果合并，我会进一步升级为**结构化证据聚合**。 每个 Worker 输出携带唯一任务 ID、文档来源、分片证据、置信级别，最终合成时自动去重、区分事实与推理、处理结果冲突，大幅降低多 Agent 架构的幻觉和信息混乱问题。

### 18. `AgentRuntime.start` 这条主链路到底怎么跑？

这条链路本质是“先建任务，再决定是否规划，再按步骤执行，再落 Trace 和事件”。用户请求进来后，`AgentService` 先创建 `AgentTask`，再把 `taskId`、`query`、`resolvedQuery`、`systemPrompt`、可用工具和是否启用规划传给 `AgentRuntime.start`。`start` 里先把任务状态改成 `RUNNING`，发 `TASK_CREATED` 事件，然后加载会话历史，构造 `historyMessages`，再决定要不要走 `SupervisorService.plan`。

如果启用规划，`start` 会先发 planning thinking，把状态切到 `PLANNING`，调用 `SupervisorService.plan(query)`。如果计划只有 1 个子任务且不是 artifact write-back，就直接退回单 Agent。计划非空时会把执行模式和计划写入任务快照，再发 `PLAN_CREATED` 事件，随后按 `subTasks` 顺序一个个执行。这里要说死：当前不是 DAG 调度，不是并行池执行，而是 `for` 循环串行跑。

空计划时，系统只构造一个 `WorkerLoopContext`，新建 `AgentState`，直接 `agentLoop.run(context)`。有子任务时，系统会创建共享 `AgentState sharedState`，每步都用 `buildStepContext` 生成步骤上下文，传入步骤级白名单、任务分类和是否恢复标记，然后执行 `agentLoop.run(..., sharedState)`，最后把 `stepResult.state()` 合并回共享状态。也就是说，后一步能看见前一步产物，但代价是上下文更容易膨胀，顺序依赖也被写死了。

**可能追问：**

- **为什么要先写任务和 Trace，再执行？**：为了支持审计、恢复和故障排查。先落库，哪怕进程中途挂了，也能知道任务开始过。
- **为什么共享 `AgentState`？**：为了把前一步证据、产物和 noteId 传给后一步，减少重复检索。但这也意味着步骤间不是完全隔离。
- **当前链路有并行吗？**：没有。字段里有 `dependsOn` 和 `executionMode`，但主执行还是顺序循环。

**补充细节：**

```text
用户请求
   ↓
AgentService.createTask
   ↓
AgentRuntime.start
   ↓
TASK_CREATED
   ↓
加载历史 + 构造上下文
   ↓
是否启用规划
   ├─ 否 → 单 Agent 直接跑
   └─ 是 → Supervisor.plan
             ↓
        PLAN_CREATED
             ↓
        按步骤串行执行
             ↓
        合并共享 State
             ↓
        保存 final result + Trace
```

### 20. `toolHint`、`classifyTask`、`allowedToolsForTask` 是什么关系？

`toolHint` 是 Supervisor 给出的“建议工具”，`classifyTask` 是后端把子任务语义归类成 `FETCH`、`CREATE_NOTE`、`APPEND_NOTE`、`GENERATE_MINDMAP` 这类类型，`allowedToolsForTask` 则是把类型映射成真正可调用的工具白名单。

执行时不能直接信 `toolHint`。`classifyTask` 会先看 `toolHint`，例如 `fetchUrl`、`createNote`、`appendNote`、`generateMindMap`，识别不出来才退到 `label`、`goal`、`description` 的语义匹配。匹配到类型后，`allowedToolsForTask` 才返回固定白名单，比如 `FETCH_ONLY_TOOLS = ["fetchUrl"]`，`CREATE_NOTE_TOOLS = ["createNote"]`。这意味着 `toolHint` 是提示，不是权限；真正执行边界是后端映射出来的白名单。

风险也很明显：如果 `toolHint` 误判，任务会被分到错误白名单，导致 Worker 走不通或者被迫重规划。所以它更像路由信号，不是业务事实。生产化上，应该把工具类型、目标、依赖和输入输出 schema 一起校验，而不是只看一个 hint。

**可能追问：**

- **`toolHint` 为空怎么办？**：走语义分类，实在识别不出来就给空白名单，避免越权。
- **为什么不让模型直接选工具？**：因为模型会误选、会被注入、会越权。后端必须收口。
- **分类错了会怎样？**：要么任务卡住，要么触发反思和重规划，但不能放开白名单兜底。

**补充细节：**

```text
SubTask.toolHint
   ↓
classifyTask
   ↓
任务类型: FETCH / CREATE_NOTE / APPEND_NOTE / GENERATE_MINDMAP
   ↓
allowedToolsForTask
   ↓
固定白名单
   ↓
AgentLoop 内再校验一次
```

### 21. `AgentTaskService`、`AgentTaskStep`、`dependsOnJson` 这套状态怎么落？

`AgentTaskService.createTask` 负责建任务主记录，保存 `userId`、`sessionId`、原始 query、标准化目标和执行模式，初始状态是 `CREATED`。`savePlan` 会把当前计划序列化成快照，写入任务的 `currentPlanSnapshot`，同时删掉旧步骤，再把每个 `SubTask` 落成一条 `AgentTaskStep`，包括 `stepId`、`label`、`goal`、状态、顺序号、`dependsOnJson` 和 `successCriteriaJson`。

`updateStatus` 负责改任务主状态，结束态会写 `finishedAt`。`updateExecutionSnapshot` 记录迭代轮次、工具调用数、token、摘要、失败原因，给恢复和排查用。`markStepStatus` 会按 stepId 更新步骤状态和摘要。`getTaskDetail` 则负责拼装任务、步骤、事件和是否可恢复信息。

恢复时，`AgentTaskResumeService` 会读 `currentPlanSnapshot` 和 `AgentTaskStep`，找出还没完成的步骤，重新构造 `AgentResumeContext`。所以 `dependsOnJson` 不是摆设，它是恢复和继续执行时判断步骤关系的依据之一。但它现在还不是完整 DAG 调度输入，更多是状态记录和恢复参考。

**可能追问：**

- **为什么要删旧步骤重建？**：为了让计划快照和步骤表一致，避免旧计划残留。
- **恢复能保证完全继续吗？**：不能。它是任务级恢复，不是常驻自治；而且当前对复杂重规划的接回还不完整。
- **`writeJson` 失败怎么办？**：当前只能记 warning，说明它不是强一致写入。

**补充细节：**

```text
createTask
   ↓
savePlan
   ↓
AgentTask
   ├─ currentPlanSnapshot
   ├─ executionMode
   └─ status
AgentTaskStep
   ├─ stepId
   ├─ dependsOnJson
   ├─ successCriteriaJson
   └─ status
```

### 22. `AgentTaskResumeService` 怎么恢复，边界在哪？

恢复不是“把进程记忆接着跑”，而是“从落库状态重建剩余步骤”。`prepareResume` 会先校验任务当前状态是不是 `WAITING_USER`、`BLOCKED` 或 `FAILED`，不在可恢复集合里就直接拒绝。然后它把用户补充信息拼进原 query 和 summary，更新任务为 `RUNNING`，再从计划快照里解析出剩余步骤。

`resolveRemainingSteps` 会读取 `currentPlanSnapshot`，反序列化成 `List<SubTask>`，再拿 `AgentTaskStep` 对照，跳过已经完成的步骤。若发现已完成步骤和新计划的 goal 冲突，就直接报错，避免拿着矛盾计划继续跑。最终返回 `AgentResumeContext`，里面带有 taskId、sessionId、userId、resumedQuery、resumedSummary、executionMode、首个待执行 stepId 和 remainingSteps。

边界也要说清：这不是无限恢复，也不是自动重做整个任务。它依赖计划快照和步骤表都还在，而且只适合任务级恢复。若计划快照损坏、步骤和计划冲突、或者关键副作用工具已经执行过又无法幂等，就不能硬接。

**可能追问：**

- **为什么恢复前要改状态为 `RUNNING`？**：为了占住执行权，避免重复恢复。
- **用户补充信息是怎么拼进去的？**：会加到原 query 和 summary 里，保留上下文。
- **冲突检测能防所有问题吗？**：不能，只能挡一部分明显矛盾；副作用幂等还是要工具层补。

**补充细节：**

```text
WAITING_USER / BLOCKED / FAILED
   ↓
prepareResume
   ↓
校验状态
   ↓
拼接用户补充信息
   ↓
读取 currentPlanSnapshot
   ↓
过滤已完成步骤
   ↓
构造 AgentResumeContext
```

### 23. `ReflectionService` 和 `ReplanningService` 真正怎么工作？

`ReflectionService` 不是每轮都跑。它先看 `AgentState`，只有连续无进展达到阈值，或者最近两次同一工具都失败，才触发反思。反思会把目标、成功标准、无进展次数、工具调用次数、最高证据级别、最近工具记录这些上下文喂给精确模型，要求返回结构化 JSON，包括 `shouldReplan`、`shouldAskUser`、`failureType`、`rootCause`、`recommendedActions` 等。结果会落到 `AgentReflection`，同时发 `REFLECTION_CREATED` 事件。

`ReplanningService` 是“要不要换策略”的下一步。只有 `reflectionResult.shouldReplan()` 为真时才会进入。它会根据反思结果重新生成 1 到 4 个步骤，必要时给新步骤补 `RP-1` 这类 ID。失败时会走回退策略，比如 URL 被拦就切本地笔记搜索，网页抓取连续失败就请求用户提供替代链接，没进展就换执行策略。

但这里要分清实现边界：服务层已经有反思和重规划代码，不代表主流程已经完整接回新计划继续执行。`AgentRuntime` 在关键抓取步骤失败后，当前还是更偏向阻断和用户澄清，代码里也明确留了后续才接入重新规划的注释。所以回答时要说“能力在服务里有，主执行链路没有完全闭环”。

**可能追问：**

- **为什么不是每次失败都反思？**：成本太高，也没必要。要先看是否真的卡住。
- **反思 JSON 解析失败怎么办？**：走默认失败分类和 fallback 建议。
- **为什么不直接自动重规划到底？**：会变成无限重试，成本和风险都失控。

**补充细节：**

```text
连续无进展 / 重复工具失败
   ↓
ReflectionService
   ↓
判断 shouldReplan
   ↓
ReplanningService
   ├─ 成功：新步骤 / 新策略
   └─ 失败：fallbackReplan
```

### 24. `AgentEventService`、`AgentTraceService`、SSE 三者区别是什么？

`AgentEventService` 管“事件事实”。它把 `TASK_CREATED`、`PLAN_CREATED`、`STEP_STARTED`、`TOOL_CALLED`、`REFLECTION_CREATED`、`REPLAN_CREATED` 这类事件写进数据库，payload 会序列化成 JSON。`recordAndEmit` 会一边落库一边把同样事件通过 SSE 推给前端。

`SseEmitter` 管“实时展示”。它只负责把当前状态、thinking、response、error 这些事件发给前端，客户端断开后就不保证送达了。它适合聊天窗口、执行进度和流式响应，不适合做唯一真相。

`AgentTraceService` 管“完整链路追踪”。它用 ThreadLocal 暂存 tool call、error、reflection、RAG trace id、LLM interaction，最后 `completeTrace` 统一落库，保存总轮次、工具调用数、token、最终答案、错误和反思记录。SSE 丢了没关系，Trace 还在；事件表丢了，排障就会差很多。所以三者不是重复，而是实时、审计、回放三个层次。

**可能追问：**

- **为什么事件要既落库又 SSE？**：一个给回放，一个给前端实时看。
- **Trace 和事件谁更适合排障？**：Trace 更适合看完整过程，事件更适合看时间线。
- **SSE 断了怎么办？**：前端会断流，但后端 Trace 仍会留记录。

**补充细节：**

```text
AgentLoop / Runtime
   ↓
AgentEventService -> DB + SSE
   ↓
AgentTraceService -> ThreadLocal + DB
   ↓
前端只看 SSE
   ↓
排障看事件和 Trace
```


### 25. 这套多 Agent 方案现在最大短板是什么？

最大短板是“工程闭环还没完全收住”。现在已经有计划、状态、事件、Trace、反思、重规划和恢复雏形，但真正生产级的依赖图调度、完整并行执行、统一证据对象、全局限流、租户级预算、完整幂等和断点恢复，还没全部打穿。

所以面试时不能把字段存在当成能力已实现。`dependsOn`、`executionMode`、`toolHint`、`ReplanningService`、`AgentTraceService` 这些都是真的，但有些只到“预留”和“部分接入”层面。最稳的说法是：当前已经把多 Agent 的主骨架搭起来了，能做任务拆分、白名单执行、失败反思、状态持久化和任务级恢复；但并行调度、证据融合和长期自治，还属于后续要补的生产化能力。

**可能追问：**

- **如果只选一个最先补的点，你选什么？**：依赖图校验加调度器，因为它直接决定计划能不能安全执行。
- **为什么不先补并行？**：没有状态和幂等打底，并行只会把问题放大。
- **现在最适合怎么表述项目？**：受约束的任务编排型 Agent，不是开放式自治 Agent。
