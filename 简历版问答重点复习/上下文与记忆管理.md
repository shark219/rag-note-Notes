## 六、上下文与记忆管理

### 52. Token 上下文管理怎么做？

我觉得这个问题的核心是在有限的上下文窗口内，既要保留足够的历史信息让对话连贯，又不能让 Token 超限导致调用失败或成本失控。

项目中 `ContextManager` 的做法是先估算历史 Token，预算超过 32K 时优先压缩早期长 AI 消息，再把更早消息压成摘要，保留最近消息原文。工具结果压缩后还会限制字符数，摘要失败有兜底。

具体流程是先遍历会话历史，用简单规则估算每条消息 Token（字符数 / 2.5）；累计超过阈值时触发压缩。压缩策略分三层：第一层截断早期长工具结果和 AI 响应，保留开头和结尾各 N 字符；第二层把更早的多轮对话合并成摘要，调用 LLM 提取关键信息；第三层如果仍超预算，丢弃最早轮次并记录日志。压缩后的消息列表重新计算 Token，确保在预算内再发送给模型。

核心取舍是保留近期意图和任务状态，牺牲早期长原文的细节。摘要不是无损操作，因此需要保留原始消息或支持重新检索，不能把摘要当作唯一证据。如果用户提到很早之前的内容，可以从 MySQL 历史记录中重新加载或提示用户重新提供上下文。

我认为上下文管理不能只看 Token 数量，还要看信息的实际价值。最近几轮对话往往包含当前任务的核心意图，必须完整保留；早期的长工具结果可能只是中间过程，压缩影响不大。所以压缩顺序很重要，不能简单地"从最早的开始删"。

**可能追问：**

- **为什么不直接截断最早消息？**：简单截断会丢失上下文连贯性，用户可能提到早期内容；摘要可以保留关键信息骨架。
- **摘要失败怎么办？**：降级到简单截断或保留消息标题，标记压缩降级；不能因为摘要失败导致整个对话无法继续。
- **如何验证压缩效果？**：构造超长历史会话，断言压缩后 Token 在预算内、最近消息保留原文、早期消息被摘要或截断；追问早期内容应能部分回忆或提示重新提供。

**补充细节：**

压缩顺序：长工具结果截断 → 早期 AI 消息截断 → 更早消息摘要 → 最早消息丢弃。每步压缩后重新计算 Token，达到预算即停止。

验证方法：构造包含 10 轮对话、每轮包含长工具结果的历史，触发压缩后检查消息列表、Token 估算和最近轮次是否完整保留。

### 53. 为什么先压缩长工具结果，再做历史摘要？

我觉得这个顺序的核心考虑是：长工具结果通常占 Token 多，但信息密度不稳定，后续往往只需要结论和关键证据。先压缩它们能减少成本，也较少破坏用户原始意图；如果仍超预算，再摘要更早的对话。

项目中压缩优先级是：长工具结果 > 早期 AI 长消息 > 更早多轮对话。工具结果可能包含完整检索上下文、长文档片段或详细日志，这些内容模型在生成答案后不一定需要完整保留。压缩时保留工具名、参数和结果摘要（如"检索到 5 个相关文档"），截断详细内容。AI 长消息也可以压缩开头和结尾，保留关键结论。只有这两步仍超预算时，才把更早的完整对话轮次合并成摘要。

但要注意代码实现中是按早期 AI 长消息压缩，并不等于识别了所有真实工具消息。面试时应表述为"当前实现采用长 AI/工具结果压缩策略"，不要夸大成完美语义分类。如果压缩后用户追问早期内容，可以从历史记录重新加载或提示"该内容较早，请重新提供上下文"。

我认为压缩的关键是既要节省 Token，又要尽量保持对话可理解性。用户的原始问题永远不能压缩，因为那是意图的直接表达；工具结果可以大胆压缩，因为它们是中间过程；AI 的最终回答要慎重压缩，因为可能被后续对话引用。

验证方法：构造包含 10 轮对话、每轮包含长工具结果的历史，触发压缩后检查消息列表、Token 估算和最近轮次是否完整保留。

### 54. 当前项目有长期记忆吗？

我觉得这个问题要诚实回答：严格说没有完整的持久化长期记忆。当前已有的是会话级历史压缩和 `ConversationContextManager` 维护的活动笔记、任务进度等上下文状态。

短期消息用于多轮对话，结构化会话上下文用于指代解析和 Agent 执行；如果要跨会话保留用户偏好、事实或经验，需要增加持久化记忆、召回策略、过期和删除机制。不能把内存态会话上下文说成长期记忆。

项目中 `ConversationContextManager` 维护当前会话的活动笔记列表、进行中的任务、最近提及的文档和关键实体，这些状态只在会话生命周期内有效。新会话开始时这些状态清空，不会跨会话保留。如果要实现真正的长期记忆，需要把用户偏好、历史决策、常用工具、重要事实等持久化到数据库，并在新会话中根据相关性召回。

生产化长期记忆还需要考虑记忆更新、冲突解决、过期策略和用户删除权限。比如用户上次说”我喜欢简洁回答”，下次会话应该记得；但用户也可能改变偏好，系统要能更新或删除过期记忆。

我认为长期记忆不是简单地把所有历史都存下来，而是要有选择地提取有价值的信息，并在需要时能够精准召回。这需要语义索引、时效性判断和冲突处理，是一个独立的子系统，不是会话管理的自然延伸。

**可能追问：**

- **会话上下文和长期记忆有什么区别？**：会话上下文只在当前对话中有效，新会话清空；长期记忆跨会话持久化，新会话可以召回使用。
- **如何实现长期记忆？**：持久化用户偏好、关键事实到数据库，带时间戳和重要性评分；新会话根据用户 ID 和问题相关性召回 TopK 记忆。
- **长期记忆会有冲突吗？**：会，用户可能前后说法不一致；应记录时间戳，新记忆覆盖旧记忆或明确提示用户确认。

**补充细节：**

当前能力：会话历史压缩、活动笔记列表、任务进度、最近文档引用。缺失能力：跨会话记忆召回、用户偏好持久化、记忆更新和过期。

生产化方案：新增 `UserMemory` 表，保存用户 ID、记忆类型（偏好/事实/决策）、内容、时间戳、重要性；新会话开始时召回相关记忆注入上下文。

验证方法：当前会话记录用户偏好，新会话应不记得（无长期记忆）；实现长期记忆后，新会话应能召回并应用偏好。

### 55. 上下文压缩有什么风险？

我觉得上下文压缩的主要风险是信息丢失：摘要可能漏掉边界条件，长结果截断可能丢证据，压缩边界还可能误删下一轮需要的信息。解决方式是优先保留最近原文、当前任务相关事实、来源 ID 和结构化状态；需要具体证据时重新检索原文，而不是只依赖摘要。

项目中压缩风险主要有三类。第一是摘要丢失细节：比如用户提到"版本 2.3.5 有个 bug"，摘要后可能只剩"早期版本有问题"，丢失具体版本号。第二是截断破坏完整性：工具返回的检索上下文截断后，可能保留了无关开头、丢失了关键结论。第三是过度压缩导致指代不清：用户说"按照刚才的方案"，如果"刚才的方案"已被摘要，模型可能无法理解具体指什么。

缓解措施是优先保留最近 3 轮完整对话，保留结构化状态（活动笔记、任务列表、文档引用），保留证据来源 ID（chunk ID、文档 ID）而不只是文本片段。需要早期内容时，从 MySQL 历史记录重新加载或通过 chunk ID 重新检索原文。摘要失败有降级兜底，不能因摘要异常导致对话中断。

压缩效果应通过 Token、延迟、追问成功率和答案忠实度一起验证，不能只看 Token 是否降低。

我认为压缩不是为了压而压，而是为了在有限窗口内保留最有价值的信息。如果压缩后用户频繁需要重复早期信息，或者答案质量明显下降，说明压缩策略有问题，需要调整保留规则或者增加上下文预算。

**可能追问：**

- **如何验证压缩没有丢失关键信息？**：构造依赖早期内容的追问，断言模型能回忆或提示重新提供；统计追问成功率，压缩后不应显著下降。
- **摘要质量如何保证？**：用明确的摘要 Prompt（保留时间、实体、关键决策），人工抽样检查摘要是否保留核心信息；摘要失败降级到截断。
- **什么时候不应该压缩？**：当前任务强依赖早期上下文、用户明确引用早期内容、会话轮次很少（< 5 轮）时不应压缩。

**补充细节：**

保留优先级：最近 3 轮原文 > 结构化状态 > 证据来源 ID > 早期摘要 > 更早丢弃。

验证方法：长对话后压缩，追问早期内容（如"刚才提到的版本号是多少"），断言能回答或提示重新提供；对比压缩前后的追问成功率和答案质量。
