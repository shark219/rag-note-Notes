## 八、测试开发与质量保障

### 63. 这个项目如何做测试分层？

测试分层的核心是把质量分成协议正确性、系统可靠性和 AI 效果三个层面。协议层包括 Controller 参数、鉴权、错误码、JSON 结构、SSE 事件顺序和幂等；系统层包括 MySQL/Redis/Chroma 故障、异步任务、并发重复上传、重试、超时、线程池和数据一致性；效果层包括检索是否召回证据、回答是否忠实、是否相关、上下文精确度和召回率。

测试分层上，纯逻辑用单元测试，例如 RRF、切片、MD5、JSON 清洗、预算判断和状态转换；Repository、事务、Redis 用集成测试；API 和 SSE 用契约测试；上传、异步向量化、检索和问答用少量端到端测试。模型调用不能全部放在单测里，否则结果随机、耗时高、成本不可控；单测 Mock 模型和工具，固定数据集上的真实模型评估放到隔离回归任务。

RAG 回归集不能随机写几条问题，而要覆盖术语、同义表达、错误码、上下文指代、多跳问题、空结果、文档缺失和高幻觉风险问题。每条样本记录预期答案或证据范围、文档版本、检索配置和模型版本。发现错误时先查看 trace：关键证据没有召回，是检索问题；证据召回但答案没用，是生成问题；证据过时或错误，是知识库问题。

最终还要做故障注入和恢复测试。例如 Chroma 断开、embedding 超时、批量部分失败、MySQL 提交后进程退出、补偿任务重复执行、SSE 中途断线。质量标准不是”接口返回 200”，而是错误被正确分类、状态闭环、数据不重复、任务可以恢复或明确失败。

我认为测试分层不是为了凑覆盖率，而是为了快速定位问题。单元测试快，能立即发现逻辑错误；集成测试覆盖模块交互，能发现集成问题；端到端测试少但关键，验证完整链路。每一层都有明确的职责，不要混在一起。

**可能追问：**

- **如何 Mock 模型调用？**：单测中用 Mockito mock LLM 服务，返回固定响应；集成测试用测试桩返回预设 JSON；回归测试用真实模型但固定数据集。
- **如何测试 SSE？**：用支持流式的 HTTP 客户端逐事件接收，断言事件类型、顺序和字段；测试断线重连、超时和并发订阅。
- **测试覆盖率要求多少？**：单元测试行覆盖 > 70%，核心逻辑 > 90%；集成测试覆盖主要业务流程；端到端测试覆盖关键用户路径。

**补充细节：**

测试金字塔：单元测试（快速、大量、Mock 外部依赖）→ 集成测试（中等、覆盖模块交互）→ 端到端测试（慢、少量、覆盖关键路径）。

验证方法：CI 中自动运行单元和集成测试，回归测试定期或发布前运行；故障注入测试手动或自动化执行，验证系统韧性。

### 64. RAG 最难测什么？

我觉得 RAG 最难测的是答案不是固定字符串，但系统仍需要可判断的质量标准。解决方式是保存完整 trace，把问题拆成检索质量、生成忠实度、答案相关性、延迟、Token 和降级率，再用固定数据集批量比较。

测试最终答案前，先测试检索结果。如果关键证据没召回，是检索问题；证据已召回但答案没有使用，是生成或 Prompt 问题；证据本身错误，则是知识库问题。

项目中 RAG 测试分三层。第一层测检索：固定问题集，断言关键 chunk 被召回（chunk ID 匹配），统计 Recall@K。第二层测生成：给定固定上下文，断言答案包含关键事实、不包含幻觉内容。第三层测端到端：完整问答流程，用 RAGAS 四项指标评估质量，保存 trace 便于分析。

难点还包括：答案表述多样但语义相同、部分正确部分错误的答案如何评分、如何区分模型能力问题和系统问题。因此需要 LLM judge + 规则评分 + 人工抽样组合，不能只依赖单一方式。

我认为测试 RAG 不能只看最终答案对不对，而要看整个链路每一步是否符合预期。检索没召回正确文档，后面再怎么生成都是错的；检索对了但生成错了，说明 Prompt 或模型有问题；检索和生成都对但用户不满意，可能是知识库本身的问题。分层测试才能快速定位问题根源。

**可能追问：**

- **如何测试检索召回？**：人工标注每个问题的关键 chunk ID，检索后断言这些 ID 在 TopK 结果中；统计召回率和排名位置。
- **如何测试幻觉？**：给定上下文和问题，模型生成答案，用 Faithfulness 评估答案中每个事实是否被上下文支持；构造故意不相关的上下文，断言模型不生成答案或明确说"无相关信息"。
- **如何区分检索问题和生成问题？**：检索返回正确证据但答案错误 → 生成问题；检索未返回关键证据 → 检索问题；证据和答案都对但不相关 → Prompt 或理解问题。

**补充细节：**

测试用例设计：
- 精确术语匹配："NullPointerException 如何处理" → 应召回包含该异常的文档
- 同义改写："怎么解决空指针" → 应召回相同文档
- 多跳问题："A 接口调用 B 服务失败怎么办" → 需要召回 A 接口文档和 B 服务文档
- 空结果："不存在的概念" → 应返回空或明确说明无相关信息

验证方法：准备 50+ 标注样本，每个样本包含问题、预期召回 chunk、预期答案要点；批量测试并生成报告，分析失败样本定位问题。

### 65. 如何设计 RAG 回归集？

我觉得回归集设计的关键是按场景分层：术语精确匹配、同义改写、代码和异常栈、多跳问题、上下文指代、空结果、文档缺失和容易产生幻觉的边界问题。每条样本保存预期答案、证据范围或关键事实。

项目中回归集设计包含以下类型：精确术语（"NullPointerException"、"HTTP 404"、"版本 2.3.5"）、同义改写（"如何解决" vs "怎么处理"）、技术栈特定（Java 代码、异常栈、配置文件）、多跳推理（"A 调用 B 失败"需要 A 和 B 两份文档）、上下文指代（"按照刚才的方案"）、边界情况（不存在的概念、过时文档、冲突信息）。

每条样本记录：问题文本、预期召回的 chunk ID 列表、预期答案要点或完整答案、文档版本、检索配置（TopK、是否 rerank）、模型版本。执行回归时固定这些配置，对比实际召回和答案与预期的差异。

固定测试集不等于永远不更新。新增线上失败样本时要脱敏后加入回归集，并记录数据集版本，避免测试集变化导致指标无法比较。回归集应该持续积累，从初始 20 条逐步扩展到 100+ 条，覆盖各类典型场景和历史失败案例。

我认为好的回归集不是随便写几个问题，而是要覆盖真实用户会问的各种情况。精确术语、同义改写、多跳推理、边界情况，每一类都要有代表性样本。而且回归集要随着系统演进持续更新，每次发现新的失败案例，都要加进去，这样才能真正防止质量退化。

**可能追问：**

- **如何标注预期答案？**：人工根据文档内容编写预期答案要点，或标注必须包含/不能包含的关键词；完整答案标注成本高，关键要点更实用。
- **回归集多大合适？**：初期 20-50 条覆盖主要场景，成熟后 100-200 条；过小覆盖不足，过大运行耗时长、维护成本高。
- **如何处理过时样本？**：定期人工审查，文档更新或业务变化后更新预期答案；标记样本版本和有效期。

**补充细节：**

回归集示例：
```json
{
  "id": "test-001",
  "question": "NullPointerException 如何排查",
  "expectedChunks": ["chunk-123", "chunk-456"],
  "expectedKeywords": ["堆栈信息", "null检查", "日志"],
  "avoidKeywords": ["数据库", "网络"],
  "documentVersion": "v1.2",
  "modelVersion": "gpt-4",
  "config": {"topK": 5, "useRerank": true}
}
```

验证方法：定期运行回归集，生成对比报告（召回率、答案质量、指标变化）；新功能上线前必须通过回归测试；失败样本加入回归集防止重复。

### 66. 如何测试模型返回非法 JSON？

我觉得测试 Agent 的关键是把模型当成一个有不确定输出的外部依赖。协议测试覆盖纯 JSON、Markdown 代码块、中文前缀、截断数组、字段缺失、类型错误和未知字段，验证清洗、解析、回退和错误记录。语义测试则验证规划是否覆盖目标、依赖是否合理、工具是否符合任务和权限。

轨迹测试把模型响应和工具结果 Mock 成固定序列，覆盖：规划成功后正常完成；规划失败后降级单 Agent；工具临时失败后有限重试；连续无进展触发反思；反思后换工具；预算超限终止；暂停后恢复；一个子任务失败但其他任务继续并最终标记缺失。每轮断言 AgentState、pending steps、tool history、任务状态、trace 和终止原因。

还要测幂等和安全边界：同一写工具重复执行不能重复创建；模型传入其他用户的文档 ID 必须被拒绝；高风险写操作需要确认。最终文本可以做宽松断言，但状态、工具次数、权限和终止事件应该做严格断言，因为这些是后端必须稳定保证的协议。

项目中协议测试用固定非法 JSON 字符串（带 Markdown 代码块、中文前缀等），调用 `cleanLlmJson` 和解析逻辑，断言能正确清洗或降级。轨迹测试 Mock LLM 返回固定规划和决策序列，Mock 工具返回固定结果，执行完整 Agent 循环并断言每轮状态。

我认为测试 Agent 不能只看最终答案，因为答案是自然语言，很难严格断言。但是状态转换、工具调用次数、权限检查、终止原因这些都是确定性的，必须严格测试。这样即使模型输出变化，我们也能保证系统行为是可控的。

**可能追问：**

- **如何 Mock 模型返回？**：单测中注入 Mock LLM 服务，预设返回内容（合法/非法 JSON、空、超长）；集成测试用测试桩按序列返回。
- **轨迹测试如何设计？**：定义场景（如"工具失败重试后成功"），Mock 模型返回工具调用、Mock 工具第一次失败第二次成功，断言重试发生且最终成功。
- **如何测试越权？**：Mock 模型返回包含其他用户文档 ID 的工具调用，断言被权限检查拒绝并记录审计日志。

**补充细节：**

协议测试用例：
```java
// 带 Markdown 代码块
String json = "```json\n[{\"label\":\"task1\"}]\n```";
List<SubTask> tasks = supervisor.parseAndClean(json);
assert tasks.size() == 1;

// 中文前缀
String json = "好的，规划如下：[{\"label\":\"task1\"}]";
// 应能提取出 JSON 数组

// 截断
String json = "[{\"label\":\"task1\"}, {\"label\":\"tas";
// 应降级返回空列表或部分解析
```

验证方法：准备各类非法 JSON，断言清洗和解析逻辑；轨迹测试覆盖正常和异常路径，断言状态机转换正确。

### 67. 如何做 Agent 轨迹测试？

我觉得轨迹测试的核心是把模型决策和工具结果 Mock 成固定轨迹，覆盖规划成功、工具成功、临时失败重试、连续无进展触发反思、预算超限、暂停恢复和子任务部分失败。

断言每轮状态、工具顺序、最大调用次数、终止原因、trace 完整性以及 SSE 是否发送且只发送一个终止事件。轨迹测试比只断言最终自然语言更容易定位问题。

项目中轨迹测试场景包括：正常完成（规划 → 检索 → 生成 → done）、规划失败降级（非法 JSON → 清洗失败 → 单 Agent）、工具重试（检索超时 → 重试成功）、预算超限（达到最大轮次 → 终止并记录原因）、反思触发（连续两轮无进展 → 反思 → 换工具）、部分失败（子任务 A 成功、B 失败 → 合成时标记 B 未完成）。

每个场景 Mock 完整交互序列，断言每轮的 AgentState（目标、工具历史、观察结果）、任务状态变化、trace 记录和最终输出。不只断言成功/失败，还要断言中间状态转换和资源清理。

我认为轨迹测试的价值在于让 Agent 行为可预测。模型输出可能变化，但是给定相同的模型输出和工具结果，系统的状态转换、重试逻辑、终止条件应该是确定的。这样即使模型升级，只要协议不变，系统行为就是稳定的。

**可能追问：**

- **如何 Mock 完整轨迹？**：定义场景脚本，按顺序返回模型决策和工具结果；用队列或状态机控制 Mock 行为，每次调用返回预定内容。
- **如何验证反思触发？**：Mock 连续两轮工具返回空结果或无新信息，断言第三轮触发 ReflectionService 且 trace 记录反思事件。
- **并发轨迹如何测试？**：Mock 多个子任务并行执行，断言工具调用顺序符合依赖关系、共享状态隔离、最终合成正确。

**补充细节：**

轨迹示例（工具重试成功）：
```
轮次1: 规划 → 返回 [task1]
轮次2: 调用检索工具 → Mock 超时
轮次3: 重试检索工具 → Mock 成功返回结果
轮次4: 调用生成 → 返回答案
断言: 工具调用2次、重试记录存在、最终状态completed
```

验证方法：准备 10+ 轨迹场景，每个场景 Mock 完整交互，运行后断言状态机转换、trace 完整性、资源释放；失败场景不应泄漏资源或无限循环。

### 68. 如何测试最终一致性？

我觉得测试最终一致性的核心是构造 MySQL 失败、embedding 超时、Chroma 失败、批量部分失败、提交后进程崩溃、重复补偿等场景。每个场景检查数据库状态、重试次数、错误原因、向量数量、是否重复和最终可恢复性。

还要验证”永远失败”路径：超过最大重试后进入人工处理或死信，不能无限重试。

我认为测试最终一致性不是验证”数据一定一致”，而是验证”出问题后能自动恢复”。短暂不一致是允许的，但必须有补偿机制、有状态标记、有最大重试限制。测试要覆盖各种异常场景，确保系统不会卡在中间状态，也不会无限重试。

项目中最终一致性测试覆盖以下场景：正常流程（MySQL 成功 → 异步成功 → 状态 completed）、Chroma 不可用（MySQL 成功 → 向量失败 → 状态 vector_failed → 补偿恢复）、批量部分失败（10 个 chunk，1 个超长 → 批量失败 → 单条回退 → 9 个成功 1 个失败）、进程崩溃（事务提交后、异步前崩溃 → 重启后补偿任务处理）、重复补偿（同一文档触发多次补偿 → 幂等保证不重复向量）。

每个场景验证：MySQL 数据完整性、BM25 索引存在、Chroma 向量数量正确、文档状态准确、重试记录完整、补偿任务执行且幂等。最终验证检索能返回文档（降级到 BM25 或完整混合检索）。

**可能追问：**

- **如何模拟进程崩溃？**：在关键点（事务提交后、异步投递前）抛异常或强制退出，重启后检查状态和补偿机制。
- **如何验证幂等？**：同一文档多次补偿，查询 Chroma 向量数量不变、MySQL 无重复记录、状态最终为 completed。
- **补偿任务如何触发？**：定时任务扫描 vector_failed 或超时 pending 状态文档，重新投递；测试时手动触发或减少扫描间隔。

**补充细节：**

测试步骤示例（Chroma 失败恢复）：
```
1. 关闭 Chroma 服务
2. 上传文档
3. 断言 MySQL 和 BM25 成功，状态 vector_failed
4. 检索文档，断言降级到 BM25
5. 恢复 Chroma 服务
6. 触发补偿任务
7. 断言状态变为 completed，Chroma 有向量
8. 检索文档，断言走混合检索
```

验证方法：自动化故障注入测试，覆盖各类失败场景；每个场景检查数据一致性、状态流转和最终可恢复性。

### 69. 如何做并发测试？

我觉得并发测试的核心是验证：文档重复上传最终只有一条业务记录和一份有效索引；同一任务重复暂停/恢复不能破坏状态；同一缓存 Key 并发 miss 不能造成数据库或模型请求风暴。

逐步增加并发，观察 QPS、P95/P99、错误率、线程池队列、数据库连接池和外部限流；结束后核对数据，不只看 HTTP 200。

项目中并发测试覆盖：重复上传（100 并发上传相同文件 → 断言只有一条记录）、并发检索（1000 QPS 检索 → 观察延迟、错误率、降级率）、缓存击穿（热点 Key 过期瞬间 100 并发 → 断言只有一次模型调用）、线程池压测（提交超过队列容量任务 → 断言拒绝策略生效）、数据库连接池（并发查询超过连接数 → 断言等待或拒绝，无死锁）。

并发测试工具用 JMeter、Gatling 或自写压测脚本。测试后检查：数据一致性（无重复记录、状态正确）、资源释放（连接归还、线程回收）、错误日志（无死锁、无资源泄漏）、监控指标（CPU、内存、GC、慢查询）。

我认为并发测试不只是看系统能不能扛住压力，更重要的是看并发下数据会不会乱。比如并发上传相同文件，如果没有幂等保护，可能产生重复记录；缓存击穿时如果没有锁，可能瞬间打爆数据库。测试完一定要对账，确认数据没问题。

**可能追问：**

- **如何模拟并发上传？**：用 JMeter 或线程池并发调用上传接口，传入相同文件；断言只有一个请求成功创建，其他返回"已存在"或冲突。
- **缓存击穿如何验证？**：并发请求同一个刚过期的 Key，在处理逻辑中打点记录模型调用次数；断言只有一次模型调用、其他请求等待或快速失败。
- **压测后如何验证数据一致性？**：查询数据库记录数、Chroma 向量数、BM25 索引；对比压测前后数据，检查是否有重复、遗漏或脏数据。

**补充细节：**

并发测试指标：
- 吞吐量：QPS（每秒请求数）
- 延迟：P50、P95、P99、max
- 错误率：HTTP 非 200、业务错误、超时
- 资源：CPU、内存、线程数、连接数、队列长度
- 降级率：缓存 miss、检索降级、模型限流

验证方法：逐步增加并发（10 → 50 → 100 → 500），记录各阶段指标；达到瓶颈后分析原因（CPU、数据库、外部服务）；压测后检查数据完整性和一致性。

### 70. 如何测试 SSE？

我觉得测试 SSE 的关键是逐事件检查响应头、事件类型、字段和顺序。正常流程应有任务创建、进度或工具事件、响应事件和 done；异常流程应有 error，不能同时 done 和 error。

测试慢客户端、断网、服务端超时、重复订阅、事件去重和客户端主动断开。必须使用流式客户端逐事件断言，不能等完整响应后才测试。

项目中 SSE 测试覆盖：正常流程（连接 → thinking → tool_call → response → done）、异常流程（连接 → error 且 HTTP 200）、断线重连（连接中途断开 → 重连后查询任务状态）、超时（长时间无响应 → 服务端发送心跳或超时关闭）、并发订阅（同一任务多个客户端订阅 → 都能收到事件）。

测试用流式 HTTP 客户端（如 OkHttp 支持 SSE、或原生 EventSource），逐事件读取并断言。检查响应头 `Content-Type: text/event-stream`、`Cache-Control: no-cache`；事件格式 `event: type\ndata: json\n\n`；事件顺序和完整性。

我认为测试 SSE 不能只测正常流程，断线重连、超时、并发订阅这些异常场景更重要。因为 SSE 本质上是长连接，网络不稳定时很容易断开。测试要验证断开后任务不会丢失，重连后能恢复状态，这样用户体验才能有保障。

**可能追问：**

- **如何测试断线重连？**：连接后收到几个事件，主动关闭连接，重新连接并查询任务状态，断言能获取完整结果。
- **如何模拟慢客户端？**：客户端接收事件后 sleep 延迟读取，观察服务端缓冲区和超时处理。
- **如何验证事件顺序？**：记录接收到的事件类型序列，断言符合预期顺序（如 thinking 必须在 response 之前、done 必须最后）。

**补充细节：**

SSE 事件格式：
```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

event: thinking
data: {"taskId":"123","content":"正在检索..."}

event: tool_call
data: {"taskId":"123","tool":"ragSearch","status":"running"}

event: response
data: {"taskId":"123","content":"根据检索结果..."}

event: done
data: {"taskId":"123","status":"completed"}
```

验证方法：用流式客户端逐事件接收，断言响应头、事件类型、字段完整性、顺序正确；测试异常场景（断线、超时、并发）并验证行为符合预期。

### 71. 如何测性能？

我觉得性能测试的关键是把文档导入、关键词检索、混合检索、单 Agent 和多 Agent 问答分成不同场景，固定文档规模、Query 集、TopK、模型和并发，分别测冷缓存和热缓存。报告吞吐、P50/P95/P99、错误率、Token、队列和资源占用。

如果没有真实压测记录，只能准确说”采用了异步、缓存、批量和降级机制”，不能给出未经验证的提升百分比。

项目中性能测试场景包括：文档导入（100 个文档并发上传 → 观察 MySQL、BM25、异步任务耗时）、关键词检索（1000 QPS → P95 延迟、错误率）、混合检索（500 QPS，启用向量+BM25+rerank → P95、降级率）、单 Agent 问答（100 QPS → 端到端延迟、Token）、多 Agent 问答（50 QPS → 规划+执行+合成总耗时）。

测试前准备：固定知识库（1000 文档、10000 chunk）、固定问题集（100 个问题）、固定配置（TopK=5、模型版本）。测试时逐步增加并发，记录各阶段指标。冷缓存测试重启服务清空 Redis，热缓存测试预热后再压测。

报告包含：吞吐量（QPS）、延迟分布（P50/P95/P99/max）、错误率、Token 消耗、降级率、资源占用（CPU/内存/GC）、瓶颈分析（数据库/模型/网络）。

我认为性能测试不是为了追求数字好看，而是为了了解系统的真实能力和瓶颈。知道 P95 延迟是多少，才能给用户设定合理的预期；知道瓶颈在哪里，才能有针对性地优化。而且性能数字必须有依据，没有压测过就不要编造提升百分比。

**可能追问：**

- **冷缓存和热缓存有什么区别？**：冷缓存所有请求都 miss，需要计算或查询；热缓存高命中率，延迟更低。两者都要测，反映真实情况。
- **如何确定瓶颈？**：分段计时，观察哪个阶段耗时最长；监控资源占用，CPU 高是计算瓶颈，IO 等待高是存储瓶颈，队列堆积是下游限流。
- **性能优化后如何验证？**：相同场景、相同数据、相同并发下对比优化前后指标；P95 延迟降低、吞吐提升、错误率不增加才算有效优化。

**补充细节：**

性能基线示例：
- 关键词检索：P95 < 200ms，QPS 1000，错误率 < 0.1%
- 混合检索：P95 < 800ms，QPS 500，降级率 < 1%
- 单 Agent：P95 < 5s，QPS 100，Token 均值 2000

验证方法：用 JMeter/Gatling 压测，记录指标并生成报告；对比基线发现回归；优化后重新压测验证效果。
