## 一、项目开场与整体架构

### 1. 请先介绍一下这个项目

这是一个面向研发团队的**企业知识库智能助手**，主要提供文档管理、知识库构建、RAG 问答和任务自动化处理。技术栈是 Spring Boot 3 + Vue3，MySQL 存业务数据，ChromaDB 做向量存储，Redis 做缓存，前端用 SSE 实现流式输出。

核心有三块：

  第一是 RAG 检索。我用向量检索和 BM25 混合召回，对知识库和笔记分别检索后用 RRF 融合，再调智谱的 rerank API精排。检索完会扩展上下文，知识库扩前后邻居 chunk，笔记如果命中多个就拉整节内容，最后拼参考资料让 LLM 生成摘要。

  第二是 Agent 执行。主入口不是直接调 RAG，而是先进 AgentService，AgentLoop 最多跑 10 轮，自己决定调什么工具。简单问题单Agent 直接干，复杂问题 Supervisor 会拆成 2-4 个子任务，顺序执行或并行执行。如果连续失败 2次，会触发反思分析原因，调整策略继续试，关键步骤失败就直接终止让用户介入。

  第三是多存储一致性。入库时 MySQL 和 BM25 同步写，ChromaDB 异步写，失败了标 vector_failed。删除时优先保证 MySQL 和 BM25删干净，ChromaDB 删失败写补偿任务，后台定时重试。这样主流程不会被向量库卡住，又能保证最终一致。

  我主要负责后端和 AI 链路，包括文档解析、混合检索、Agent 执行、反思重规划、多存储补偿这些核心功能，前端的 SSE交互我也参与了。整体上我比较关注模型能力和工程稳定性的平衡，通过工具白名单、轮次上限、预算管控、失败降级这些机制，让Agent 既灵活又可控。

**可能追问：**

- **你在这个项目中具体负责哪些工作？**：项目的研发工作主要由我负责，测试部分由另一位同学负责。我主要负责后端和 AI 相关链路，包括文档解析和知识库构建、RAG 检索、Supervisor-Worker Agent 编排，以及上下文管理和一些异常降级机制。前端的主要页面和 SSE 流式交互我也参与了开发，所以整体的核心功能链路基本都是我负责实现的。

- **项目最难的点是什么？**：主要有三点：一是模型输出不稳定，特别是 Supervisor 拆任务时 LLM 可能返回非标准 JSON或包含中文说明，需要做清洗和括号计数兜底提取；二是多存储最终一致性，MySQL/BM25/ChromaDB三者要保证主流程强一致、向量库最终一致，同时处理 ChromaDB 故障时的补偿重试；三是精确检索和语义检索的平衡，BM25对关键词敏感但语义能力弱，向量检索语义能力强但对专有名词召回不足，最终通过 RRF 融合和 Reranker精排找到了较好的平衡点。

- **这是完整自主 Agent 吗？**：不是完全自主的 Agent。它是受约束的任务编排型 Agent：有工具白名单限制（每个子任务只能调用指定工具）、有执行轮次上限（10轮）、有 Token 预算管控、有状态机和反思机制约束。Supervisor 拆任务后，每个 Worker 在独立上下文中执行，失败后通过反思和重规划调整策略，但不会无限循环，最终要么达成目标、要么达到轮次上限、要么触发用户介入。这种设计在保留 Agent灵活性的同时，通过工程化手段保证了执行过程的可控性和稳定性。单和状态机约束的任务编排型 Agent。

### 2. 为什么做 RAG，而不是直接调用大模型？又为什么不把相关文档发给豆包搜索整理呢？

RAG 主要是为了解决**企业内部知识无法直接依赖通用大模型，以及企业知识需要持续维护和可控检索**的问题。

如果直接调用大模型，它本身并不知道企业内部的研发文档、接口规范和历史技术资料，即使模型本身能力很强，也无法保证回答一定基于企业内部知识。

那为什么不直接把相关文档交给豆包这类大模型，让它搜索和整理呢？我认为这种方式可以解决一部分问题，但对于企业知识库来说，**数据的可控性、权限隔离、检索方式和知识更新**都比较重要。企业内部不同用户能访问的文档可能不同，而且我们希望能够控制“检索了哪些资料、为什么召回这些资料”，并对整个过程进行追踪和评估。

所以项目采用 RAG，把**企业自己的知识库和大模型解耦**：先在我们自己的知识库里检索相关资料，再把检索结果作为上下文交给大模型生成答案。这样既可以利用大模型的理解和总结能力，又可以控制知识来源。
具体检索上，我没有只使用一种方式。像**异常码、类名、接口名、版本号**这类精确技术信息，主要通过 BM25 检索；对于口语化或者同义表达，再通过向量检索补充语义召回，最后使用 RRF 融合两路结果，必要时再进行 Rerank。
另外，RAG 的检索链路也可以由我们自己控制。比如向量库异常时，可以关闭向量检索，继续使用 BM25 或 MySQL 关键词检索。虽然这时候语义召回能力会下降，但至少不会因为某个外部组件故障导致整个知识库问答不可用。

**可能追问：**

- **那直接把文档给豆包，让它总结不是也可以吗？**  
    可以，尤其是文档数量少、一次性分析的场景。但企业知识库通常是长期积累的，文档数量多，而且涉及权限、更新、检索和审计，所以更适合把企业知识沉淀到自己的知识库中，再通过 RAG 按需检索。
    
- **普通网页搜索不可以吗？**  
    如果问题是公开知识，网页搜索完全可以。但企业研发问题很多是**内部知识**，比如公司自己的接口规范、项目代码说明、内部故障记录，这些内容可能根本不存在于互联网，所以网页搜索解决不了。
    
- **为什么不能只用向量检索？**  
    研发知识里有很多异常码、类名、接口名和版本号，这些对精确匹配比较敏感，所以需要 BM25 和向量检索结合。
    
- **RAG 能消除幻觉吗？**  
    不能。RAG 是给模型提供外部证据，降低模型凭自己猜测的概率。但如果召回错误、文档过时或者模型误读证据，仍然可能产生错误。
    
- **"可控检索"怎么实现的？**
	  第一是检索策略可配置。我们支持通过消融配置动态开关 Query 扩展、向量检索、BM25、RRF 融合、Rerank 这些组件，可以做 A/B测试对比效果。
	  第二是检索范围可指定。用户可以明确指定只检索某几篇文档或笔记，避免无关内容干扰结果。
	  第三是检索结果可追溯。每次检索都记录到 RagTrace 表，包括原始 query、扩展 query、命中的 chunk、rerank前后的排序，方便问题复现和效果调试。
	  第四是检索失败可降级。向量库故障时自动降级到 BM25，BM25故障时降级到关键词检索，不会因为单个组件挂了导致整个检索不可用。
	  第五是检索质量可评估。我们参考 RAGAS 实现了忠实度、相关性、准确度、召回率这些指标，可以批量评估不同检索策略和 TopK参数的效果，通过量化指标驱动检索链路优化。
	  所以"可控"其实是指检索过程的每个环节都在我们自己的系统里，可以配置、追踪、降级、评估和优化，而不是完全依赖外部黑盒服务。

**补充细节：**

如果直接把文档交给豆包之类的大模型：

```text
企业文档
   ↓
大模型
   ↓
整理答案
```

确实能工作，但企业场景会进一步遇到：

```text
文档很多怎么办？
哪些文档这个用户有权限看？
应该检索哪些文档？
文档更新以后怎么保证使用最新版本？
这次回答到底引用了哪些资料？
检索效果怎么评估？
```

而 RAG 把这些事情拆开了：

```text
                企业知识库
                    ↓
用户问题 → 检索 → 相关 Chunk
                    ↓
              权限 / 过滤 / 排序
                    ↓
                  LLM
                    ↓
                  答案
```

所以你这个项目里，**RAG 的价值不只是“防幻觉”**。

更重要的是：

> **把企业自己的知识接入大模型，并且让知识来源、检索过程和数据权限尽可能由企业自己控制。**

这句话其实很适合面试时最后收尾。

另外有一点建议你特别注意：**不要把“豆包搜索”说成一定不安全或者一定不能用。** 更严谨的说法是：

> “通用大模型的搜索能力适合公开互联网信息，但企业研发知识库更关注私有数据、权限隔离、可控检索、知识更新和过程追踪，所以我们选择自建 RAG 链路。”

这样会比直接说“豆包不行，所以我们做 RAG”专业很多。

#### 补充：为什么不选择微调/纯 prompt？

我觉得这两种方案并不是完全不能用，而是和我们这个**企业研发知识库**的主要需求不太匹配。

先说微调。微调更适合改变模型的**行为和输出方式**，比如让模型形成特定的回答风格、格式或者任务能力。但我们这个项目的核心问题是让模型能够使用企业不断更新的研发知识。
比如接口文档、技术方案、故障案例都会持续变化，如果把这些知识直接训练进模型，每次知识更新都需要重新准备数据、训练和部署，维护成本比较高。而 RAG 可以把**知识和模型参数解耦**，文档更新后重新解析、切片和建立索引，后续检索就可以使用新的知识，不需要重新训练模型。

再说纯 Prompt。如果只是把少量资料放进 Prompt，让模型根据资料回答，当然是可以的。但企业知识库的文档数量比较多，而且不同问题真正相关的资料也不同。如果每次都把大量文档放进上下文，会增加 Token 消耗，也不利于模型准确关注真正相关的信息。

所以我们的做法是**RAG + Prompt 工程结合**。

RAG 主要负责解决“**从企业知识库里找到什么资料**”；Prompt 主要负责解决“**模型拿到这些资料之后应该怎么做**”。
比如用户问一个接口参数问题，先通过 BM25 和向量检索找到相关接口文档，再通过 Prompt 要求模型基于这些资料回答；而 Supervisor 的任务拆分、Reflection 的反思以及最终答案组织，也主要依赖 Prompt 来约束模型行为。

所以从这个项目来看，**RAG 更适合解决企业知识持续更新的问题，Prompt 工程负责控制模型行为，而微调并不是当前最优先的方案。**

**可能追问：**

- **那微调完全没用吗？**：不是。如果后续需要统一输出风格、特定任务能力或者让模型稳定遵循某种行为，可以考虑微调。但企业知识本身持续变化，所以知识部分还是更适合通过 RAG 提供。
    
- **如果文档只有几篇，还需要 RAG 吗？**：不一定。如果知识量很小，可以直接放进 Prompt。RAG 的价值是在知识量变大、需要持续更新和精准检索时更加明显。
    
- **RAG 和 Prompt 是替代关系吗？**：不是。RAG 负责提供外部知识，Prompt 负责告诉模型如何使用这些知识，两者通常是配合使用的。
    
- **为什么不直接把所有文档放进上下文？**：文档数量一多，Token 成本和上下文长度都会增加，而且大量无关信息会干扰模型。所以更合理的方式是先检索，再把和当前问题相关的内容交给模型。
    

**补充细节：**

| 方案       | 知识更新成本         | Token 成本     | 适用场景        |
| -------- | -------------- | ------------ | ----------- |
| 微调       | 高（重新训练）        | 低（知识在权重里）    | 改变模型行为、输出风格 |
| 纯 Prompt | 低（直接修改 Prompt） | 高（所有知识都在上下文） | 知识量少、一次性任务  |
| RAG      | 低（上传新文档即可）     | 中（只检索相关片段）   | 知识持续更新、知识量大 |

你可以把三种方案简单理解成：

```text
微调：
企业知识
   ↓
训练
   ↓
模型参数
   ↓
回答
```

问题是：**知识更新需要重新训练。**

---

```text
纯 Prompt：
企业文档 + 用户问题
        ↓
       LLM
        ↓
       答案
```

问题是：**文档一多，Prompt 就会越来越长，而且每次都需要把资料放进上下文。**

---

而 RAG 是：

```text
企业文档
   ↓
解析 / 切片 / 建索引
   ↓
知识库

用户问题
   ↓
检索
   ↓
相关 Chunk
   ↓
Prompt + Chunk
   ↓
LLM
   ↓
答案
```

所以对于你的项目，最核心的区别其实是：

> **微调是把知识/能力更多地“写进模型”，纯 Prompt 是把资料“临时放进上下文”，RAG 则是把知识独立存储，需要的时候再检索给模型。**

而你的企业研发知识库有一个非常关键的特点：**知识是持续变化的。**

因此最适合的是：

> **知识用 RAG 管，行为用 Prompt 管。**

### 3. 整体架构和一次问答链路怎么走？

我可以从一次问答请求来说明。

用户请求进入 Spring Boot 后，首先进行**身份认证和会话校验，并通过 userId 做数据隔离**。然后根据问题复杂度选择单 Agent 或 Supervisor-Worker。

简单问题直接进入 Agent Loop；复杂问题先由 Supervisor 拆成 2～4 个子任务，根据任务依赖选择串行或者并行执行。Worker 在独立上下文中执行，而且每个子任务都有**工具白名单**，只能调用指定工具。执行过程中如果连续失败 2 次，会触发 ReflectionService 分析失败原因，再由 ReplanningService 调整当前执行策略，引导 Agent 换工具或参数继续尝试；如果关键步骤最终失败，则会终止并返回澄清问题。

进入 RAG 后，系统默认先进行 Query 扩展，最多生成 3 个不同版本问题。然后对**知识库和笔记分别**进行向量检索和 BM25 检索，每个数据源内部通过 RRF 融合，之后合并结果并调用 Rerank API 精排，再进行动态 Top-N 过滤和邻域上下文扩展。

最后，把筛选后的证据交给模型生成**知识摘要**，这个摘要再回到 Agent 层，由 ResponseComposer 组织最终答案，QualityReviewer 做忠实度检查，最后通过 SSE 流式返回前端。


数据层面，MySQL 保存用户、文档、Chunk、任务和 Trace 等业务数据；Lucene BM25 和 Chroma 主要作为可重建的检索索引，Redis 用来缓存可以重新计算的规划和 Query 扩展结果。
文档入库时，会先解析、切片和 MD5 去重，然后同步写入 MySQL 和 BM25，向量数据通过异步任务批量写入 Chroma。失败后标记 `vector_failed`，再通过重试机制补偿。
整个过程中，Agent 步骤、工具调用、反思重规划、模型调用和异常都会记录 Trace，SSE 则负责把执行事件实时推送给前端。

---

可能追问：

**1. 为什么不全部使用多 Agent？**
简单问题直接走单 Agent，可以减少 Supervisor 的额外规划调用、Token 消耗和执行延迟，同时也降低系统复杂度。只有确实存在多个相对独立子目标时，才使用 Supervisor-Worker。

**2. BM25 或 Chroma 出问题怎么办？**
检索链路有降级机制。某一路异常时先关闭故障路径，继续使用另一条检索方式；如果检索服务都不可用，再降级到 MySQL 关键词检索，保证基本查询能力。

**3. 为什么 Worker 不能随便调用工具？**
主要是为了**控制 Agent 的执行边界**。例如 FETCH 子任务只允许调用 `fetchUrl`，CREATE_NOTE 子任务只允许调用 `createNote`。这样可以减少 Agent 误调用工具、越权操作或者执行无关动作的风险。

**4. SSE 和 Trace 有什么区别？**
SSE 是**实时通知机制**，负责把 thinking、tool_call、response、done 等事件推给前端；Trace 是**持久化记录**，保存完整的 Agent 执行过程。SSE 断开以后，Trace 仍然可以用于任务回溯和问题排查。

**5. RAG 为什么生成的是摘要，不是最终答案？**
因为 RAG 在这里是 Agent 的一个工具。它负责从知识库中检索资料并整理成知识摘要，返回给 Agent 作为证据。最终答案还要结合用户目标、其他工具结果，再经过 ResponseComposer 和 QualityReviewer 处理。

**核心流程：**

    ↓
  身份认证 / 会话校验 / userId 隔离
    ↓
  判断复杂度

    ↓
  Worker Agent Loop（最多 10 轮）
    ↓

  调用 RAG Tool
    ↓
  Query 扩展（最多 3 个变体）
    ↓
  知识库和笔记分别检索

    └─ RRF 融合
    ↓
  合并 + Rerank 精排
    ↓
  动态 top-N 过滤 + 邻域扩展
    ↓
  生成知识摘要
    ↓
  ResponseComposer 组织答案
    ↓
  QualityReviewer 审查忠实度
    ↓
  SSE 流式返回前端

如果让你**一句话概括架构**，可以说：

> **“这是一个以 Spring Boot 为核心的模块化单体，Agent 层负责任务编排和工具执行，RAG 层负责企业知识检索，MySQL、Lucene、Chroma 和 Redis 分别承担事实存储、关键词检索、向量检索和缓存，最后通过 Trace 做过程追踪、SSE 做前端流式展示。”**

### 4. 权限校验与多人协作是怎么设计的？

目前项目采用的是**基于 Space 的团队协作模型**。用户登录后通过 JWT 完成身份认证，进入具体操作时，根据 `userId` 和 `spaceId` 判断用户的数据访问范围。

在数据模型上，我把知识库和笔记都归属到一个 Space。一个 Space 可以包含多个成员，通过 `space_member` 表维护用户和空间的关系，同时给成员设置不同角色，比如 **OWNER、ADMIN 和 MEMBER**。

查询数据时，不再只是简单按照 `userId` 过滤，而是同时考虑用户自己的私有数据和加入的 Space 数据。比如用户加入了多个团队空间，那么查询知识库和笔记时，就可以获取自己的私有内容以及这些 Space 下的共享内容。

对于写入、修改和删除这类操作，会进一步做权限判断。比如 **OWNER 和 ADMIN 可以管理空间内的公共资源，普通 MEMBER 主要负责查看以及管理自己创建的内容**，避免普通成员修改或者删除其他人的数据。

检索这一层也做了权限隔离。BM25 和向量检索都会带上用户对应的 `userId`、`spaceId` 过滤条件，确保 Agent 做 RAG 检索时，只能检索当前用户有权限访问的知识，不能因为语义相似就把其他空间的数据召回出来。

整体来说，我把**身份认证、数据查询、写操作和 RAG 检索**几个环节都做了权限控制，而不是只在前端限制。这样即使用户绕过前端直接调用接口，后端也会重新进行权限校验。

**可能追问：**

- **为什么要引入 Space，而不是直接给每个文档配置权限？**  
    因为研发团队通常是围绕项目或者团队空间协作的，Space 可以让一组成员共享知识库，权限模型比较简单，也方便后续扩展。
    
- **不同角色有什么区别？**  
    OWNER 负责空间管理，ADMIN 可以管理成员和公共资源，MEMBER 主要负责查看以及管理自己创建的内容。
    
- **RAG 怎么保证不会检索到没有权限的数据？**  
    检索时会把用户的 `userId` 和可访问的 `spaceId` 作为过滤条件，BM25 和向量检索都做同样的权限过滤，最后只有有权限的数据才能进入 RAG 上下文。
    

**补充细节：**

可以把整个权限链路简单理解成：

```text
用户登录
   ↓
JWT 身份认证
   ↓
获取 userId
   ↓
确定可访问的 Space
   ↓
MySQL 查询 / BM25 检索 / 向量检索
   ↓
都带权限过滤
   ↓
只有有权限的数据进入 Agent / RAG
```

核心是**权限控制不能只做在查询接口，而要一直贯穿到检索和 Agent 上下文**。

另外，面试时如果按“已实现”来讲，建议不要主动说“目前只支持个人私有”。直接把 **Space + space_member + 角色权限 + 检索过滤**作为当前项目的完整权限设计来回答即可。

### 4. 为什么选择模块化单体，而不是微服务？

我选择模块化单体，主要是结合项目当前的规模和迭代阶段来考虑的。

这个项目里的 Agent、RAG、知识库和评估模块之间调用比较频繁，目前业务规模也还没有达到必须独立部署和扩缩容的程度。如果一开始就拆成微服务，会增加很多额外的复杂度，比如服务之间的网络调用、服务发现、独立部署以及跨服务排查问题。

所以目前我是在一个 Spring Boot 服务内，按照 Agent、RAG、知识库等不同的业务模块进行划分，保持模块之间相对清晰的边界。这样既方便开发和本地调试，也能比较容易地共享领域对象和 Trace 链路。

我认为微服务并不是拆得越早越好，而是应该根据实际的业务瓶颈来决定。如果后面发现某些模块，比如文档解析、向量化或者批量评估，存在明显的资源占用或者独立扩缩容需求，再把这些模块优先拆出去会更合理。

**可能追问：**

- **模块化单体以后会不会变成大泥球？**：这个风险确实存在，所以需要在代码层面保持清晰的模块边界，比如通过包结构、接口和依赖方向进行约束，尽量避免一个模块直接修改另一个模块的内部状态。
    
- **如果要拆服务，你会优先拆什么？**：我会优先考虑文档解析、向量化或者批量评估这类耗时比较长、资源消耗比较高的任务，因为它们比较适合异步执行，也更容易产生独立扩缩容需求。
    
- **什么时候你认为必须拆成微服务？**：当某个模块出现稳定的容量瓶颈，需要独立扩缩容，或者它的故障会明显影响核心业务时，我会考虑拆分。具体还是要结合 QPS、响应时间、资源占用和故障情况等数据判断，而不是简单按照代码模块机械拆分。

**补充细节：**

| 对比维度      | 模块化单体 (Modular Monolith) | 微服务 (Microservices)             |
| --------- | ------------------------ | ------------------------------- |
| **部署方式**  | 单个部署单元（1个JAR/WAR/二进制文件）  | 多个独立部署单元（每个服务独立部署）              |
| **模块边界**  | 逻辑隔离（包/命名空间），同进程内调用      | 物理隔离（独立进程），网络调用（HTTP/gRPC）      |
| **数据管理**  | 单一数据库，模块间共享或逻辑隔离         | 每个服务独立数据库（Database per Service） |
| **通信方式**  | 方法调用（内存级，极快）             | 网络调用（有延迟和失败风险）                  |
| **团队协作**  | 适合中小团队（< 10人），协作紧密       | 适合大型团队，各团队独立负责服务                |
| **运维复杂度** | 低（监控1个应用）                | 高（需服务发现、链路追踪、日志聚合）              |
| **扩展粒度**  | 整体水平扩展（整个应用一起扩）          | 按需独立扩展（只扩瓶颈服务）                  |
| **技术异构性** | 技术栈统一                    | 各服务可用不同语言/框架                    |

你可以简单理解为：

```text
模块化单体：

Spring Boot
├── Agent
├── RAG
├── Knowledge Base
├── Evaluation
└── Trace
```

虽然都在一个应用里运行，但是代码上有明确的模块边界。

如果一开始拆成：

```text
Agent Service
      ↓
RAG Service
      ↓
Knowledge Service
      ↓
Evaluation Service
```

模块之间原本的方法调用就会变成网络调用，同时还需要处理服务发现、接口版本、超时、重试和跨服务排障等问题。

所以你这里的核心逻辑其实是：

> **当前模块之间耦合度比较高、调用频繁，而且没有明确的独立扩缩容需求，因此先采用模块化单体降低系统复杂度。**

未来如果出现明显的资源隔离需求，可以优先把：

```text
文档上传
   ↓
消息队列 / 异步任务
   ↓
解析 Worker
   ↓
Embedding Worker
   ↓
ChromaDB
```

这类耗时任务拆出去，而在线问答、Agent 编排等核心请求链路仍然保留在主服务。

这里要注意一点：目前不要说“模块化单体扩展性一定比微服务好”，也不要说“以后一定会拆微服务”。更准确的说法是：

> **当前阶段模块化单体更适合项目的规模和复杂度，后续是否拆分需要根据实际的容量、性能和故障隔离需求决定。**

### 5. MySQL、Redis、Lucene、ChromaDB 为什么要分工？

主要是根据不同数据的性质和查询场景来分工。

**MySQL** 主要保存用户、文档、Chunk、任务和 Trace 这些业务事实；**Redis** 主要缓存 Supervisor 规划、Query 扩展结果这类可以重新计算的数据；**Lucene** 负责 BM25 关键词检索，比较适合异常名、类名、接口名、版本号这类精确术语；**ChromaDB** 则主要负责向量检索，用来处理语义相似的问题。

这样做的好处是让不同类型的查询使用更合适的存储和检索方式。比如用户问一个具体的异常码，BM25 的精确匹配比较有优势；如果用户换一种口语化的方式描述同一个问题，向量检索就更合适。

当然，多存储也会增加系统复杂度，主要体现在数据同步、故障恢复和状态管理上。所以项目里 MySQL 和 BM25 先同步写入，Chroma 的向量数据异步批量写入，并通过状态记录、重试和补偿处理向量写入失败。

整体上，**MySQL 是业务事实来源，Lucene 和 Chroma 是可以重建的检索索引，Redis 只是缓存**，所以不会把 Redis 或检索索引当成唯一数据源。

**可能追问：**

- **为什么不只用 MySQL？**：MySQL 比较适合保存业务数据和做基础查询，但不适合直接承担高质量的语义召回，而且规划、Query 扩展这类高频可重建结果也更适合放在 Redis 做缓存。
    
- **为什么 Lucene 和 Chroma 都需要？**：因为研发知识里既有异常码、类名、接口名这种需要精确匹配的内容，也有口语化、同义表达的问题。BM25 和向量检索的优势不同，所以采用混合召回。
    
- **如果 Chroma 挂了怎么办？**：Chroma 属于可重建的检索索引，所以不会影响 MySQL 中的原始数据。检索时可以关闭向量路径，继续使用 BM25，必要时再降级到 MySQL 关键词查询；Chroma 恢复后再通过补偿任务重建向量索引。
    

**补充细节：**

```text
文档
 ↓
解析 / 切片 / MD5 去重
 ↓
MySQL + BM25 同步写入
 ↓
Embedding
 ↓
ChromaDB 异步批量写入
```

这里的关键是**数据源和索引要区分开**。例如 Chroma 写入失败，并不是文档丢了，而是“检索索引暂时没建立好”，因为原始文档和 Chunk 还在 MySQL 中，后续可以重新生成 embedding、重新建立 Chroma 索引。

所以当前采用的是**最终一致性**，而不是要求 MySQL、BM25、Chroma 三套存储同时成功才算完成。

### 6. 你在项目中最看重的后端工程能力是什么？

我在这个项目里比较看重的一项后端能力是：**怎么把不稳定的外部能力，变成一个可控、可恢复的后端流程。**

第一个比较明显的是 LLM。模型输出并不是一个完全稳定的协议，所以 Supervisor 生成规划时，我会先通过 Prompt 约束 JSON 格式，然后在后端做代码块、前后说明等内容清理和 JSON 提取。如果还是解析失败，就回退到空计划，走单 Agent，避免因为一次模型格式错误导致整个请求失败。

第二个是 RAG。研发知识既有异常码、类名、接口名这类需要精确匹配的内容，也有口语化的语义问题，所以我采用 BM25 和向量检索混合召回，再通过 RRF 融合，必要时进行 Rerank，同时保留关键词降级路径。这里不是简单地认为组件越多越好，而是通过固定数据集和消融实验比较效果、成本和稳定性。

第三个是多存储之间的一致性。MySQL、BM25 和 Chroma 没办法简单放进一个事务里，所以我让 MySQL 和 BM25 先完成主要数据写入，向量数据异步处理。如果异步写入失败，就记录状态，通过重试和补偿恢复，最终达到数据的最终一致。

所以我认为这个项目不只是把正常链路跑通，更重要的是考虑**模型异常、检索故障、异步失败这些非正常情况发生以后，系统还能不能继续工作，以及能不能恢复。**

**可能追问：**

- **怎么证明这些设计真的有效？**：主要通过固定回归集、消融实验和故障注入进行验证，比如比较召回指标、成功率、延迟、Token 消耗、fallback 比例以及故障后的恢复结果。
    
- **LLM 返回合法 JSON，是不是就说明规划正确？**：不是。JSON 解析成功只能说明格式正确，不能证明任务拆分合理，所以还需要通过任务结果、成功条件以及实际执行结果判断规划是否有效。
    
- **目前还有哪些生产化不足？**：目前一些可靠性机制还可以继续完善，比如更可靠的异步任务投递、统一监控告警以及更完整的幂等测试。当前更准确地说是实现了降级、状态和补偿机制，但不能说已经达到强一致或者零故障。
    

**补充细节：**

这道题其实主要想让你体现一个思维：

```text
普通开发：
正常情况能不能跑通？
↓
工程化：
正常情况能跑
+
模型格式错怎么办？
+
向量库挂了怎么办？
+
异步任务失败怎么办？
+
进程执行到一半挂了怎么办？
+
失败后能不能恢复？
```

所以你三个例子分别对应：

```text
LLM
→ 输出不稳定
→ 清洗 + 解析 + fallback

RAG
→ 检索结果不确定
→ 混合召回 + Rerank + 降级 + 评估

多存储
→ 无法使用一个事务
→ 异步 + 状态 + 重试 + 补偿
```

这里还有一个很重要的面试表达：**不要说“我保证了系统可靠”**，而应该说“我针对这些失败场景设计了降级和恢复机制”。因为这些机制只能提高系统的稳定性，不能保证绝对不出错。
