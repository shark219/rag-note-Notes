## 三、混合检索与 RAG 链路

### 16. 什么是 RRF？

RRF（Reciprocal Rank Fusion）是一种排名融合策略，用排名而不是原始分数来合并多路检索结果。

因为向量检索返回的相似度通常在 0-1 之间，BM25 分数可能几十上百，直接加权平均需要手动归一化和调权重，而且分数分布可能随数据变化。RRF 把每个候选在各路中的排名转换成 `1 / (k + rank + 1)`，然后累加。这样高排名候选的累加值更大，而且不需要归一化。

项目里用 chunk ID、doc ID 或 note ID 去重，确保同一内容在不同路径中只计算一次。RRF_K 是可调参数，k 越大，排名差异对累加值的影响越小；项目默认 k=60，可以通过消融实验对比其他值。

RRF 适合合并来源分数分布不同的多路检索，比直接加权平均分数更稳定。但 RRF 也有局限：如果某路召回质量很差，垃圾排名仍会得到不小的 RRF 加成，可能污染最终 TopK；如果某路异常返回空，RRF 本身不做降级，需要外层逻辑兜底。

是否使用 RRF、候选扩大倍数、RRF_K 等参数都需要消融实验找平衡。不要迷信 RRF，它本质是一个排名聚合策略，不解决召回本身的质量问题。

**可能追问：**

- **为什么不用加权平均？**：向量相似度 0-1、BM25 分数可能几十上百，量纲不同。如果要加权平均，就要先归一化，还要手动调权重。RRF 把分数抽象成排名，不需要归一化，而且对分数分布变化更鲁棒。
    
- **RRF_K 怎么选？**：k 控制尾部惩罚幅度。k 越大，排名差异对累加值影响越小；k 越小，高排名和低排名的差距越明显。项目默认 k=60，可以消融对比其他值，看最终召回和答案质量。
    
- **多路都返回空怎么办？**：RRF 无结果可融合，外层逻辑走关键词 fallback。降级策略由 HybridRetriever 控制，不是 RRF 职责。
    

**补充细节：**

RRF 计算示例（假设 k=60）：

```text
chunk A：
  向量检索排名第 2 → 1/(60+2+1) = 0.0159
  BM25 排名第 5    → 1/(60+5+1) = 0.0152
  RRF 总分 = 0.0159 + 0.0152 = 0.0311

chunk B：
  向量检索排名第 1 → 1/(60+1+1) = 0.0161
  BM25 排名第 10   → 1/(60+10+1) = 0.0141
  RRF 总分 = 0.0161 + 0.0141 = 0.0302

chunk A 总分更高 → 排在前面
```

RRF 不关心原始分数，只关心每路给的相对排名。如果某 chunk 在两路都排名靠前，RRF 就会给它更高的总分。

### 17. 什么是 Rerank？

Rerank 是在融合后的候选池上再做一次精排，用更强的模型把语义不相关的候选往下压。

前序召回阶段的目标是高召回，候选池可能包含一些语义相关性不高的结果。Rerank 模型通常是专门训练的排序模型，比向量相似度更能捕捉细粒度的语义相关性。把 query 和候选文本一起发给 rerank 模型，模型返回每个候选的相关性分数，然后重新排序，截取最终 TopK。

项目里可选 cohere、jina 或其他 rerank 模型。开启 rerank 需要一次额外调用和网络往返，会增加延迟和 Token 消耗，但能提高精度。是否使用 rerank 要看业务对延迟和质量的取舍，通过消融实验对比有无 rerank 的答案忠实度和召回覆盖。

Rerank 模型本身也有局限：它只能对候选池重新排序，不能挽救之前召回阶段遗漏的内容。如果前序召回质量差，rerank 也无力回天。所以 rerank 是在召回质量已经不错的基础上做精排，而不是用来弥补召回缺陷的。

Rerank 适合候选池较大、语义噪音较多、对精度要求高、能容忍增加的延迟的场景。不要盲目打开 rerank，它不是万能开关。

**可能追问：**

- **Rerank 用什么模型？**：项目支持 cohere、jina 等。具体选哪个要看延迟、成本和质量平衡，通常通过对比实验决定。不同 rerank 模型的延迟、成本和精度都不一样，要根据业务需求选择。
    
- **Rerank 延迟多少？**：取决于候选数、模型和网络。常见 100-500ms。候选越多、模型越大，延迟越高。如果候选池有几十个文档，rerank 延迟可能比召回本身还高。
    
- **什么时候不用 Rerank？**：延迟敏感、候选池已经很干净、成本受限、或者消融实验发现 rerank 收益不明显时，可以关闭。Rerank 不是必选项，要根据实际效果决定。
    

**补充细节：**

Rerank 流程示意：

```text
融合后得到候选列表
   ↓
把 query 和候选文本一起发给 rerank 模型
   ↓
模型返回每个候选的相关性分数
   ↓
按相关性分数重新排序
   ↓
截取最终 TopK
```

Rerank 不改变候选内容，只改变排序。Rerank 模型的输入是 query 和候选文本对，输出是相关性分数，通常是 0-1 的浮点数。

Rerank 和向量检索的区别：

```text
向量检索：
- 用 embedding 计算相似度
- 基于向量空间的几何距离
- 速度快，但语义粒度粗

Rerank：
- 用排序模型直接打分
- 基于训练好的语义相关性模型
- 速度慢，但语义粒度细
```

Rerank 是在召回之后做的，所以前序召回阶段要保证候选池覆盖足够广，rerank 才能发挥作用。

### 18. Query 扩展怎么做？

Query 扩展是把用户的原始问题改写成多个相关问题，用来扩大检索覆盖范围。

用户问题有时候很短或者很口语化，比如"502 怎么办"，如果直接用这个问题去检索，可能召回不全。Query 扩展会把它改写成"502 错误如何排查""Bad Gateway 原因分析""网关超时处理方法"等多个相关问题，然后分别检索，扩大候选范围。

项目里用 LLM 做改写，通过 Prompt 要求模型生成 2-3 个语义相近但表达不同的问题。改写之后，每个 query 分别走向量和 BM25，最后融合去重。

但 Query 扩展也不是必选项。扩展会增加 LLM 调用、检索次数、Token 消耗和延迟。如果扩展出来的问题质量不高，可能引入噪音，反而降低精度。所以要通过消融实验验证是否有收益。

Query 扩展适合用户问题表达不清晰、关键词覆盖不全、需要提高召回覆盖的场景。如果用户问题已经很明确，或者对延迟很敏感，可以关闭扩展。

**可能追问：**

- **扩展多少个 query 合适？**：项目默认 2-3 个。太少覆盖不够，太多会引入噪音、增加延迟和 Token。具体数量要根据业务需求和消融实验结果调整。
    
- **怎么保证扩展质量？**：Prompt 里要求模型生成语义相近但表达不同的问题，避免生成完全无关的内容。可以加一些约束，比如"保持原问题的核心意图""不要生成反义问题"。
    
- **扩展之后检索结果怎么融合？**：每个 query 分别检索，然后按照 RRF 融合。去重的时候用 chunk ID、doc ID 或 note ID，避免同一内容被重复计算。
    

**补充细节：**

Query 扩展流程：

```text
用户原始问题
   ↓
LLM 改写成 2-3 个相关问题
   ↓
每个 query 分别检索
   ↓
融合去重
   ↓
最终候选池
```

Query 扩展的成本：

```text
额外的 LLM 调用：
- 改写本身需要一次 LLM 调用
- 输入和输出都消耗 Token

额外的检索调用：
- 原来检索 1 次，扩展后检索 3 次
- 向量检索和 BM25 都要重复调用

额外的延迟：
- LLM 改写延迟 + 额外检索延迟
```

所以 Query 扩展要权衡收益和成本，不能盲目打开。

### 19. Agent 工具调用如何避免越权？

避免越权不能只依赖 Prompt，必须在服务端做严格校验。

虽然可以在 Prompt 里告诉模型"不要访问其他用户的资源"，但模型输出是不稳定的，不能把安全完全寄托在 Prompt 上。所以服务端必须校验参数格式、资源归属和当前用户权限。

对于检索工具，`userId`、`spaceId`、`documentId` 这些参数不是完全相信模型传入的值，而是由服务端从会话中提取，或者在工具执行前二次查库校验归属关系。对于写操作、删除操作和外部发布这类高风险操作，我会增加确认或审批流程。

在项目里，工具白名单在 `AgentPolicyService` 中定义。每次调用工具之前，系统会检查工具名是否在白名单里、参数是否完整、资源是否有权限访问、操作类型是否允许。对于高风险的写操作，系统会先返回一个待确认状态，等用户确认之后才真正执行。所有的工具调用和结果都会记录到 trace 里，便于后续审计。

多租户 RAG 系统最危险的不是模型答错了，而是模型通过参数读取了其他用户的文档。所以检索工具会从 Session 里提取 userId，笔记和知识库工具会二次查库验证归属关系，不接受模型直接传入的用户标识。

**可能追问：**

- **工具白名单如何维护？**：当前是按任务类型配置可用工具列表，不在列表里的工具名会被直接拒绝并记录。生产化的话应该支持租户级白名单和运行时动态调整。
    
- **参数校验具体做哪些？**：非空检查、长度检查、格式检查（比如 documentId 是否是合法的 UUID）、资源存在性检查、归属关系检查和权限检查。复杂的参数可以用 schema 校验。
    
- **审计日志记录什么？**：工具名、调用时间、参数摘要（脱敏后的）、执行结果、错误原因和关联的 trace ID。不记录完整的敏感参数，比如完整的文档内容或者用户密码。
    

**补充细节：**

工具越权风险可以分成三类：

```text
读越权：
读取其他用户的文档、笔记、知识库

写越权：
修改或删除其他用户的资源

执行越权：
调用未授权的工具（比如删除、发布）
```

防护需要分层：

```text
第一层：工具白名单
拦截不在列表里的工具名

第二层：参数校验
拦截格式错误的参数

第三层：权限校验
拦截归属不符的资源访问

第四层：二次确认
拦截高风险操作
```

验证方法：

- 构造模型返回其他用户 ID 或资源 ID 的工具调用
- 断言被拒绝并记录审计日志
- 未授权的工具名应该返回明确错误，不执行任何逻辑

核心原则：

> **不信任模型传入的任何用户标识或资源标识，所有权限都由服务端基于 Session 和数据库校验决定。**


### 20. Agent 重试为什么不能无限重试？

无限重试会把一次错误变成模型、线程和外部服务的持续消耗，而且可能重复执行写操作。

如果某个工具调用失败了，无限重试的话，模型会一直消耗 Token、线程会一直被占用、外部服务（比如检索、数据库）会一直被请求。而且对于带副作用的工具，比如创建笔记、发送消息，重复执行可能会创建多条重复记录。

所以在项目里，`AgentLoop` 会通过多个维度限制循环：**最大轮次、最大工具调用次数、最大 Token、运行时间、连续失败次数和相同工具调用次数**。如果检测到相同的失败参数，会被拦截不再重试。比如抓取网页这个步骤连续失败达到 3 次，就会标记失败并终止这个步骤。

另外，不是所有错误都应该重试。网络超时、连接重置这类临时错误可以有限重试，并且使用指数退避（第一次等 1 秒、第二次等 2 秒、第三次等 4 秒）。但是参数错误、权限不足、资源不存在这类确定性错误，通常不应该原样重试，因为重试也不会成功。

对于带副作用的工具，必须保证幂等性。比如创建笔记的时候用一个稳定的业务键，重试的时候先检查是否已经创建过，避免重复创建。

每次重试都会记录 attempt（第几次尝试）、错误类型和耗时，并且受总时间和 Token 预算约束。达到上限之后，任务会进入失败、人工处理或者降级路径，保证任务一定能结束。

**可能追问：**

- **项目里怎么防止重复调用？**：拦截相同的失败参数和上一轮完全相同的动作，并且受 `maxSameToolCalls`、轮次和工具预算的限制。
    
- **为什么不是失败就换工具？**：要先判断错误是否可恢复。如果是权限不足、参数错误或者资源不存在，换工具也解决不了问题。
    
- **指数退避怎么实现？**：对于临时错误，重试间隔递增（比如 1 秒、2 秒、4 秒），避免瞬间把下游服务压垮。对于确定性错误，直接失败不退避。
    

**补充细节：**

重试策略分类：

```text
临时错误（可重试）：
- 网络超时
- 连接重置
- 服务暂时不可用
→ 指数退避重试，最多 3 次

确定性错误（不重试）：
- 参数格式错误
- 权限不足
- 资源不存在
→ 直接失败并记录原因

幂等性要求：
- 创建操作：用业务键去重
- 删除操作：先检查是否存在
- 修改操作：用版本号或时间戳防并发
```

重试计数示例：

```text
第 1 次调用失败（网络超时）
  ↓ 等待 1 秒
第 2 次调用失败（网络超时）
  ↓ 等待 2 秒
第 3 次调用失败（网络超时）
  ↓ 等待 4 秒
第 4 次调用失败
  ↓
达到重试上限，标记失败
```

核心原则：

> **有限重试 + 指数退避 + 幂等保证 + 明确终止条件。**

### 21. 为什么用 MySQL + Redis + Lucene + Chroma 四层存储？

因为不同的查询场景对数据结构和查询性能的要求不同，单一存储无法同时满足所有需求。

MySQL 是主存储，用来存结构化的笔记、文档、用户、会话和任务信息，支持事务、关联查询和持久化。但 MySQL 不擅长全文检索和向量相似度计算。

Lucene（通过内存索引）用来做 BM25 关键词检索。它能快速找到包含特定关键词的文档或 chunk，适合精确匹配和短语搜索。但 Lucene 不支持语义相似度计算。

Chroma 是向量数据库，用来存 embedding 并做相似度检索。它能找到语义相关的内容，即使关键词不完全匹配。但 Chroma 不适合做精确关键词匹配。

Redis 用来做缓存和会话状态存储。热点数据、LRU 缓存、分布式锁和实时计数都放在 Redis 里，减少数据库压力。但 Redis 是内存存储，不适合存大量持久化数据。

所以这四层存储各司其职：MySQL 做主存储和事务、Lucene 做关键词检索、Chroma 做语义检索、Redis 做缓存和实时状态。数据在写入的时候会同步到不同的存储，查询的时候根据场景选择合适的存储路径。

**可能追问：**

- **数据同步怎么保证一致性？**：写入 MySQL 之后异步同步到 Lucene 和 Chroma。如果同步失败，会记录到失败队列并重试。最终一致性可以接受，但 MySQL 是唯一的主存储和真实来源。
    
- **为什么不用 Elasticsearch 替代 Lucene？**：Elasticsearch 更重，需要独立部署和维护。项目用内存 Lucene 索引更轻量，适合中小规模数据。如果数据量很大，可以考虑迁移到 Elasticsearch。
    
- **Redis 挂了怎么办？**：缓存失效，请求会直接打到 MySQL。性能会下降，但功能不受影响。Redis 应该有持久化和主从备份，保证可用性。
    

**补充细节：**

四层存储的职责：

```text
MySQL：
- 笔记、文档、用户、会话、任务
- 事务和关联查询
- 主存储和真实来源

Lucene：
- BM25 关键词检索
- 精确匹配和短语搜索
- 内存索引，轻量快速

Chroma：
- 向量相似度检索
- 语义相关查询
- Embedding 存储

Redis：
- 热点数据缓存
- 会话状态
- 分布式锁和计数
```

数据流示意：

```text
写入流程：
用户创建笔记
   ↓
写入 MySQL（主存储）
   ↓
异步同步到 Lucene（关键词索引）
   ↓
异步同步到 Chroma（向量索引）
   ↓
热点数据写入 Redis（缓存）

查询流程：
用户问题
   ↓
先查 Redis 缓存
   ↓ 未命中
根据查询类型选择：
├─ 关键词检索 → Lucene
├─ 语义检索 → Chroma
└─ 结构化查询 → MySQL
```

核心原则：

> **MySQL 是真实来源，其他存储是派生视图。一致性要求：最终一致性，MySQL 优先。**

### 22. 向量和 BM25 索引怎么保持和数据库一致？

通过异步同步机制保持最终一致性，MySQL 是唯一的真实来源。

当用户创建或修改笔记、文档的时候，先写入 MySQL，事务提交成功之后，再异步同步到 Lucene 和 Chroma。如果同步失败，会记录到失败队列，后台定期重试。

项目里用的是事件驱动的同步方式。写入 MySQL 之后发布一个同步事件，监听器收到事件之后分别调用 Lucene 索引服务和 Chroma 向量服务。Lucene 索引是内存的，重启会重建；Chroma 是持久化的，但也支持重建。

因为是异步同步，短时间内可能出现不一致：MySQL 已经写入了，但 Lucene 和 Chroma 还没有同步完成。这时候用户可能搜不到刚创建的内容。这是最终一致性的代价，但可以通过减少同步延迟来缓解。

如果索引损坏或者长期不一致，可以用全量重建任务。全量重建会从 MySQL 读取所有数据，重新构建 Lucene 和 Chroma 索引。重建期间查询仍然可以走旧索引，重建完成之后切换。

删除操作也是一样：先从 MySQL 删除，再异步从 Lucene 和 Chroma 删除。如果删除失败，重试或者等下次全量重建清理。

**可能追问：**

- **同步延迟多久？**：正常情况下几百毫秒到几秒。如果队列积压或者服务异常，可能更长。可以通过监控同步延迟和失败率来发现问题。
    
- **用户刚创建的内容搜不到怎么办？**：可以在前端加一个"正在同步"的提示，或者在创建之后等待几秒再刷新列表。也可以在检索之前查一下 MySQL，把最新的内容直接加到候选池里。
    
- **全量重建会影响线上吗？**：重建期间查询走旧索引，不影响可用性。重建完成之后切换到新索引。但重建会消耗 CPU、内存和 LLM 调用（生成 embedding），要在低峰期执行。
    

**补充细节：**

同步流程示意：

```text
用户创建笔记
   ↓
写入 MySQL 事务提交
   ↓
发布同步事件
   ↓
监听器收到事件
   ↓
并行同步：
├─ 写入 Lucene 索引
└─ 写入 Chroma 向量库
   ↓
同步成功 → 完成
同步失败 → 记录失败队列 → 后台重试
```

一致性保证：

```text
强一致性（不支持）：
写入 MySQL 的同时同步写入 Lucene 和 Chroma
→ 会增加写入延迟和失败率

最终一致性（当前实现）：
MySQL 先写入，异步同步到 Lucene 和 Chroma
→ 短时间不一致，但最终收敛

降级策略：
索引不可用 → 查 MySQL 关键词 fallback
索引长期不一致 → 全量重建
```

核心原则：

> **MySQL 是唯一真实来源，索引是派生视图。接受最终一致性，不追求强一致性。**

### 23. 为什么 Agent 状态用最终一致性？

因为 Agent 执行是异步的，强一致性会严重影响性能和可用性。

如果要求强一致性，每次状态变更都要等所有副本确认，这会大幅增加延迟。而且如果某个副本不可用，整个任务就会被阻塞。

Agent 的状态更新频率很高：每轮迭代都会更新工具历史、Token 消耗、观察结果和状态摘要。如果每次更新都要同步等待，延迟会很明显。

所以项目里用最终一致性：状态先写入主存储（MySQL），然后异步同步到 Redis 缓存和前端 SSE 推送。前端收到的 SSE 事件只是实时通知，不保证和数据库完全同步。如果用户刷新页面或者 SSE 断线，前端会从数据库重新查询最新状态。

这样设计的好处是：写入延迟低、不会因为副本故障阻塞任务、可以异步推送给多个订阅者。代价是短时间内可能看到旧状态，但最终会收敛到最新状态。

对于关键决策（比如任务是否完成、是否超预算），仍然以数据库为准，不依赖缓存或 SSE 事件。

**可能追问：**

- **SSE 断线怎么办？**：前端重连之后从数据库查询最新状态，不依赖断线期间错过的事件。SSE 只是实时通知，不是状态的唯一来源。
    
- **Redis 缓存和数据库不一致怎么办？**：缓存用来加速查询，但关键决策仍然查数据库。缓存不一致可以通过 TTL 过期或者主动失效来解决。
    
- **为什么不用分布式事务？**：分布式事务会增加复杂度和延迟，而且 Agent 状态更新频率很高，用分布式事务得不偿失。最终一致性对 Agent 场景足够了。
    

**补充细节：**

强一致性 vs 最终一致性：

```text
强一致性：
写入 → 等待所有副本确认 → 返回成功
优点：读到的一定是最新数据
缺点：延迟高、可用性低

最终一致性：
写入主存储 → 立即返回 → 异步同步副本
优点：延迟低、可用性高
缺点：短时间可能读到旧数据
```

Agent 状态更新频率示意：

```text
Agent 执行 1 次任务：
├─ 每轮迭代更新状态：10-20 次
├─ 每次工具调用更新历史：5-15 次
└─ 每次 LLM 调用更新 Token：10-20 次

总更新次数：30-50 次/任务

如果每次都强一致 → 总延迟增加数秒
最终一致性 → 总延迟增加几十毫秒
```

核心原则：

> **高频状态更新用最终一致性，关键决策查主存储。**

### 24. 会话状态为什么放 Redis？

因为会话状态需要高性能读写、支持过期和分布式访问。

会话状态包括用户的登录信息、当前对话上下文、临时缓存的检索结果和正在执行的任务 ID。这些状态的读写频率很高，而且需要在多个服务实例之间共享。

MySQL 虽然可以存会话，但读写延迟比 Redis 高，而且会增加数据库压力。Redis 是内存存储，读写延迟只有几毫秒，而且支持 TTL 自动过期，不需要手动清理过期会话。

项目里用 Redis 存 JWT Token 的黑名单、用户的当前会话 ID、SSE 连接标识和正在执行的任务状态。这些数据都有时效性，过期之后自动删除，不需要持久化。

如果 Redis 挂了，会话会失效，用户需要重新登录。但这不会影响已经持久化到 MySQL 的数据，只是临时状态丢失。所以 Redis 应该有持久化（RDB 或 AOF）和主从备份，保证可用性。

**可能追问：**

- **为什么不全部放 MySQL？**：MySQL 读写延迟比 Redis 高，而且会话状态读写频率很高，会增加数据库压力。Redis 更适合高频临时状态。
    
- **Redis 挂了用户数据会丢吗？**：会话状态会丢，用户需要重新登录。但 MySQL 里的笔记、文档、任务记录不会丢。Redis 应该有持久化和备份，保证可用性。
    
- **会话过期时间怎么设置？**：项目里默认 24 小时。可以根据业务需求调整。过期之后用户需要重新登录，会话状态会被清理。
    

**补充细节：**

Redis 存储的会话状态：

```text
用户会话：
- JWT Token 黑名单
- 当前会话 ID
- 用户 ID 和权限信息
- 临时检索缓存

任务状态：
- 正在执行的任务 ID
- SSE 连接标识
- 实时进度缓存
```

Redis vs MySQL 对比：

```text
Redis：
- 内存存储，延迟低（1-5ms）
- 支持 TTL 自动过期
- 适合高频临时状态
- 数据可能丢失（需要持久化）

MySQL：
- 磁盘存储，延迟高（10-50ms）
- 需要手动清理过期数据
- 适合持久化数据
- 数据不会丢失（事务保证）
```

核心原则：

> **高频临时状态放 Redis，持久化数据放 MySQL。**

### 25. 为什么向量检索和 BM25 要结合？

因为研发问题既有语义表达，也有精确术语，单一检索方式覆盖不全。

研发知识库里的问题，有些是”怎么处理””如何解决”这类语义表达，有些是错误码、类名、接口名、版本号这类必须精确命中的术语。如果只用向量检索，异常码、接口名这类精确匹配会失分；如果只用 BM25，同义表达和口语化问题又召回不好。

所以在项目里，`HybridRetriever` 会按照配置分别走 Chroma 向量检索和 Lucene BM25，然后用 RRF 按排名融合、去重，最后可以选择是否用 rerank。这样先扩大候选覆盖，再做精排。

向量检索擅长语义相似和同义改写，BM25 擅长异常名、类名、版本号、接口名等精确匹配。研发知识库同时存在这两类问题，只用一种检索会在另一类问题上失分。所以项目采用双路召回，再融合和精排。

混合检索的目标是提高候选覆盖率，但最终效果要用固定测试集和指标验证，不能只凭几次主观体验就下结论。

**可能追问：**

- **为什么不直接把两个分数加起来？**：BM25 分数和向量相似度的分布可能完全不同，直接相加需要额外的归一化和权重调参。RRF 只比较排名，不需要归一化。
    
- **怎么证明混合检索有效？**：用固定的数据集和配置做单路基线、逐项消融实验，比较召回率、答案质量、延迟、Token、空结果率和 fallback 率。
    
- **为什么不能只用向量检索？**：研发知识里有很多异常码、类名、接口名和版本号，这些内容对精确匹配比较敏感，向量检索不能完全替代 BM25。
    

**补充细节：**

你可以这样理解两种检索的优势：

```text
BM25（关键词检索）：
擅长：异常码、类名、接口名、版本号
不擅长：同义表达、口语化问题

向量检索：
擅长：语义相似、同义改写
不擅长：精确术语匹配

混合检索：
先用两路各自召回 → 扩大候选池
   ↓
RRF 融合去重 → 综合排名
   ↓
可选 Rerank → 精排
   ↓
最终 TopK
```

降级策略：

```text
向量路径不可用 → 关闭向量检索
BM25 异常 → 当前 query 使用 MySQL 关键词 fallback
全部没有 ranking → 走关键词检索
```

降级能保证基本可用，但不能说语义质量等价。这是已实现的检索组合和降级机制，不代表已经证明了固定收益。项目没有可公开的量化指标时，只能通过固定测试集和消融实验验证 Recall、Context Precision、忠实度、延迟和 Token。

### 26. 完整检索链路是什么？

完整的检索链路从读取配置开始，到返回最终 TopK 结束。

首先，系统会读取消融配置或者默认配置，确定 Query 扩展、向量检索、BM25、RRF、rerank、TopK 和 RRF_K 是否启用。如果 Chroma 不可用，就关闭向量路径；如果 BM25 不可用，就关闭 BM25。

如果打开了 Query 扩展，就把原始问题改写成多个语义相关的 query；否则只使用原始 query。

对每个 query，向量路径会调用 Chroma，候选数通常扩大到最终 TopK 的两倍；BM25 路也会查询扩大后的候选。如果 BM25 调用报错，不是直接让整个链路失败，而是对当前 query 使用 MySQL 关键词 fallback。

所有 ranking 收集之后，如果有多路并且启用了 RRF，就按照每个结果在各路中的排名计算 `1 / (rrfK + rank + 1)`，用 chunk ID、doc ID 或 note ID 去重并累加。如果 RRF 未启用，就走简单合并和相似度排序。

融合结果如果打开了 rerank，就交给 reranker 精排；没有 rerank 的话直接截取最终 TopK。如果向量不可用但 BM25 可用，就继续走 BM25；如果 BM25 也不可用或者没有任何 ranking，就用 MySQL 关键词检索。

关键词 fallback 能保住可用性，但语义召回质量会下降。所以应该在 trace 或日志里记录降级原因、路径和耗时。

这条链路的设计取舍是：**先高召回，再精排，故障逐层降级**。Query 扩展和 rerank 会增加 Token、延迟和失败面，所以要通过消融实验验证，而不是默认全部打开。

**可能追问：**

- **为什么候选要扩大到 TopK 两倍？**：先多召回再精排，避免单路遗漏。融合和 rerank 之后再截取最终 TopK，可以提高最终结果的质量。
    
- **降级路径怎么触发？**：检测到服务异常、超时或者返回空的时候自动降级。降级决策会记录到 trace，便于排查质量问题。
    
- **Query 扩展一定有用吗？**：不一定。扩展可能引入噪音、增加延迟和 Token。需要通过消融实验比较有无扩展的召回和答案质量。
    

**补充细节：**

完整检索链路示意图：

```text
用户 query
   ↓
Query 扩展（可选）→ query1, query2, query3
   ↓
并行检索
├─ 向量检索（Chroma）→ 候选 TopK×2
└─ BM25（Lucene）→ 候选 TopK×2
   ↓
RRF 融合去重
   ↓
Rerank 精排（可选）
   ↓
截取最终 TopK
   ↓
返回结果
```

降级层次：

```text
完整链路：向量 + BM25 + RRF + Rerank
   ↓
降级1：向量失败 → BM25 + Rerank
   ↓
降级2：BM25 失败 → MySQL 关键词
   ↓
降级3：全部失败 → 返回空并记录
```

检索链路每个阶段都可能失败，所以设计为逐层降级。降级不是质量等价，只是保底可用。每次降级都要记录原因、使用的路径和耗时，便于后续分析质量问题。

### 27. 为什么使用 RRF，而不是直接加权分数？

因为 BM25 分数和向量相似度的分布完全不同，直接加权需要先归一化，还要反复调权重，很麻烦。

BM25 的分数可能是几十、上百，向量相似度通常在 0-1 之间。如果要直接相加或加权平均，就得先把它们归一化到同一个范围，然后还要设置权重（比如 BM25 占 0.3、向量占 0.7）。但这个权重不好定，不同的数据集、不同的查询类型，最优权重可能都不一样。而且分数分布可能随着数据变化，今天调好的权重明天可能就不合适了。

RRF（Reciprocal Rank Fusion）不看原始分数，只看排名。每个候选在某一路检索中排名越靠前，它的 RRF 分数就越高。如果同一个 chunk 在向量检索里排第 2，在 BM25 里排第 5，它的 RRF 分数就是这两个排名的贡献之和。

项目里的实现是：排名从 0 开始，用公式 `1 / (rrfK + rank + 1)` 计算每一路的贡献，然后用 chunk ID 做 key 累加。这样同一个 chunk 在多路都排名靠前的话，累加分数就会更高。默认 rrfK 是 30，可以通过配置改。

RRF_K 这个参数控制排名差异的衰减速度。K 越大，排名 1 和排名 10 的差距就越小；K 越小，头部排名的影响就越强。具体选多少，要通过消融实验对比不同 K 值在固定测试集上的召回率、答案质量和候选分布。

RRF 只负责融合排序，不负责权限过滤、文档版本过滤这些。这些还是要在检索前后单独处理。

**可能追问：**

- **RRF_K 如何选择？**：通过消融实验比较不同 K 值（如 10、30、60）在固定测试集上的召回、答案质量和候选分布。当前默认 30 可通过配置覆盖。
    
- **RRF 会丢失原始分数信息吗？**：会。RRF 只保留排名信息。如果需要原始分数可以在融合前记录，但最终排序仍然用 RRF 分。
    
- **为什么不用学习排序（LTR）？**：LTR 需要大量标注样本和特征工程。当前规模下 RRF 足够简单稳定，而且不依赖训练数据。
    

**补充细节：**

RRF 公式：`score = sum(1 / (k + rank_i + 1))`，其中 rank_i 是该 chunk 在第 i 路检索中的排名（从 0 开始）。

去重依赖稳定 ID：chunk ID 最优，文档 ID 次之，内容 hash 兜底。没有稳定 ID 时可能把相同内容重复返回。

多路都命中的 chunk 得分更高，说明它在不同检索策略下都被认为相关。

### 28. Query 扩展有什么收益和风险？

收益是把用户的口语化问题改写成知识库里可能出现的专业表达，提高召回覆盖。风险是增加模型调用、Token 消耗，还可能引入噪音。

用户问"怎么搞定空指针"，知识库里可能写的是"如何处理 NullPointerException"。直接用原问题检索，可能匹配不到。Query 扩展会把原问题改写成 2-3 个相关表述，比如"如何处理空指针异常""NullPointerException 解决方法""空指针错误排查"，然后分别检索，理论上能提高召回的多样性。

但扩展也有代价。首先要调用一次 LLM 做改写，消耗 Token 和时间。其次，扩展出来的问题可能偏离原意，或者引入无关术语，导致召回的候选里噪音变多。最后，每个扩展出来的 query 都要走一遍完整检索，检索次数变多了，总延迟也会增加。

所以 Query 扩展不是越多越好。项目里默认扩展成 2-3 个，扩展结果会缓存到 Redis（TTL 10 分钟），避免重复调用模型。所有扩展 query 的检索结果进入 RRF 融合，理论上能过滤掉一部分噪音，但如果扩展质量不好，后续 rerank 可以部分补救。

评估 Query 扩展不能只看召回数量变多了，要看 Context Recall（证据覆盖率）、Context Precision（噪音比例）、最终答案质量、延迟和 Token 成本。如果召回变多但噪音也变多，不一定是优化。

**可能追问：**

- **扩展后召回变多就是好事吗？**：不一定。召回数量增加但相关性下降时，反而增加模型上下文噪音，影响最终答案质量。
    
- **扩展结果如何缓存？**：用原始 query 的 hash 作为 key，扩展结果存 Redis，TTL 10 分钟。缓存失效或未命中时重新调用模型。
    
- **什么场景适合 Query 扩展？**：用户问题口语化、同义词多、知识库术语标准化的场景。精确查询（如错误码）扩展可能引入噪音。
    

**补充细节：**

Query 扩展属于召回增强策略，不是精排策略。扩展后的多个 query 都会走完整检索链路，结果在 RRF 阶段融合。

验证方法：固定测试集分别跑无扩展、扩展 2 条、扩展 5 条，比较 Context Recall、Context Precision、最终答案质量、延迟和 Token 消耗。

### 29. 为什么要保留关键词降级？

因为向量库和 BM25 都可能暂时不可用，关键词检索虽然能力较弱，但可以保住基本可用性。

Chroma 是独立的向量数据库服务，可能因为网络、重启、资源不足等原因暂时不可用。Lucene BM25 是内存索引，进程重启就要重建。如果两者都不可用，完全不返回结果的话，用户体验很差。

关键词检索走 MySQL 的 `LIKE %keyword%` 或全文索引，虽然无法理解同义表达和语义相似，但能匹配文档标题、chunk 内容中的精确字符串。对于"某某接口""某某异常"这类包含明确术语的问题，仍然能返回部分结果。

项目里的降级路径是：Chroma 不可用时关闭向量检索，继续使用 BM25；BM25 也异常时对当前 query 使用 MySQL 关键词 fallback；全部失败返回空结果并记录降级路径。

降级必须显式记录到 trace：使用了哪一路、为什么降级、结果数量和耗时。否则用户看到答案，却不知道答案来自完整 RAG 还是低质量 fallback，后续也无法分析质量下降。

这是可用性优先的设计，不是质量等价的替代方案。降级之后语义召回能力会明显下降，但至少能保证系统不完全不可用。

**可能追问：**

- **关键词检索为什么不能替代向量？**：关键词只能精确匹配字符串，无法理解"如何解决"和"怎么处理"是同义表达，也无法召回语义相关但用词不同的文档。
    
- **降级后用户会感知吗？**：如果前端展示降级提示，用户可以感知。后端至少要在 trace 和日志中记录，便于排查答案质量问题。
    
- **MySQL 关键词检索性能如何？**：`LIKE %keyword%` 无法使用索引，大表扫描慢。全文索引（FULLTEXT）性能较好但功能受限。这是保底方案，不适合作为主检索路径。
    

**补充细节：**

降级路径优先级：

```text
向量 + BM25（最优）
   ↓ 向量不可用
仅 BM25
   ↓ BM25 也不可用
MySQL 关键词
   ↓ 全部失败
返回空并记录
```

每级降级都要记录到 trace，包含降级原因、实际使用路径、返回结果数和耗时。

验证方法：故障注入，分别关闭 Chroma、BM25 和两者都关闭，断言系统仍能返回结果（即使质量下降）并正确记录降级信息。

### 30. rerank 为什么放在召回之后？

因为 rerank 通常比 BM25 或向量查询更贵，适合在候选集已经缩小后使用。

Rerank 模型要把 query 和每个候选文本一起输入，计算它们的语义匹配度，这比向量相似度或 BM25 分数更精确，但计算成本也更高。如果一开始就对全量文档做 rerank，延迟和成本都受不了。

所以项目里的检索链路是：先用向量和 BM25 做高召回，扩大候选池（比如召回 TopK 的两倍），然后 RRF 融合去重，再对融合后的候选做 rerank，最后截取最终 TopK。

这样的好处是：第一阶段（召回）追求高覆盖、低延迟，允许一定噪音；第二阶段（精排）追求高精度，只处理少量候选。在效果和成本之间找到平衡。

如果 rerank 超时或失败，应该降级返回 RRF 融合结果，不能让一个精排服务故障导致整个问答失败。当前通过消融配置控制是否启用 rerank，可以对比有无 rerank 的质量和延迟差异。

**可能追问：**

- **rerank 和向量检索有什么区别？**：向量检索用 embedding 相似度快速筛选大规模候选。rerank 用更复杂模型对少量候选精确打分，计算成本高但更准确。
    
- **rerank 失败怎么办？**：降级到 RRF 融合结果，跳过精排步骤。记录降级原因到 trace，便于分析质量下降。
    
- **候选多大合适？**：太少可能漏掉相关内容，太多增加 rerank 耗时和成本。当前设为 TopK 两倍（如最终要 5 条，rerank 候选 10 条），可通过消融实验调整。
    

**补充细节：**

两阶段检索架构：

```text
第一阶段（召回）：
- 目标：高覆盖、低延迟
- 策略：向量 + BM25 双路召回
- 允许：一定噪音

第二阶段（精排）：
- 目标：高精度
- 策略：rerank 模型打分
- 代价：高延迟、高成本
```

验证方法：固定测试集比较"无 rerank""有 rerank"的 Context Precision、答案质量、P95 延迟和 Token。rerank 应该降低候选噪音、提升最终答案质量，代价是增加延迟。

### 31. 如何证明检索优化有效？

我觉得证明检索优化有效必须用数据说话，而不是凭主观感觉。核心方法是固定测试集、文档版本和模型配置，分别跑基线和消融实验组，比较召回率、答案质量、延迟和 Token。消融实验一次只改一个组件，才能归因。

不能只凭几次主观体验就说"优化有效"。要有固定的问题集、固定的知识库版本、固定的模型和配置，然后分别跑不同的检索策略，对比客观指标。

项目里通过 `AblationExperimentService` 管理实验配置。每组配置包含是否启用 Query 扩展、向量检索、BM25、RRF、rerank，以及 TopK、RRF_K 等参数。固定问题集在不同配置下运行，保存每次的召回结果、最终答案、耗时、Token 和四项 RAGAS 指标（Context Precision、Context Recall、Faithfulness、Answer Relevancy）。

分析时不能只看综合分，要看各指标变化。向量检索可能提高同义召回，BM25 提高术语精确率；Query 扩展可能提高 Context Recall 但引入噪音；rerank 可能提高 Context Precision 但增加延迟。每个改动都要看它带来了什么、牺牲了什么。

消融实验的关键是一次只改一个变量。如果同时改了 TopK、关了 rerank、还换了模型，即使效果变好了，也不知道是哪个改动起的作用。应该先定基线（完整流水线：Query扩展 + BM25 + 向量检索 + RRF + rerank），然后逐个关闭组件，每次只改一项，对比指标变化。

**可能追问：**

- **基线怎么选？**：当前项目的基线是完整流水线配置（Query扩展 + BM25 + 向量检索 + RRF + rerank 全部启用），这是 application.yml 中 ablation.rag 的默认配置。消融实验时逐个关闭组件，验证每个组件的必要性和贡献。
    
- **测试集怎么构建？**：从真实用户问题中抽样，覆盖常见场景、边界情况和历史失败案例。人工标注预期答案或关键证据，作为评估基准。
    
- **如果没有测试集怎么办？**：只能说实现了检索优化机制，不能声称带来了具体的提升百分比。应该尽快补充测试集，用数据说话。
    

**补充细节：**

消融实验示例：

```text
基线（完整流水线）：Query扩展 + BM25 + 向量 + RRF + rerank
  → Context Recall: 0.82
  → Context Precision: 0.82
  → Answer Relevancy: 0.88
  → 延迟: 2.6s

- 关闭 rerank：
  → Context Precision: 0.70 (-15%)
  → 延迟: 1.9s (-27%)
  结论：rerank 对精度贡献明显，但延迟较高

- 关闭 Query 扩展：
  → Context Recall: 0.75 (-9%)
  → Context Precision: 0.84 (+2%, 噪音减少)
  → 延迟: 2.4s (-8%)
  结论：Query 扩展提升召回，但引入噪音

- 关闭向量检索（仅 BM25）：
  → Context Recall: 0.60 (-27%)
  → Context Precision: 0.75 (-9%)
  → 延迟: 1.2s (-54%)
  结论：向量检索对同义召回至关重要

- 关闭 RRF（多路结果简单合并）：
  → Context Precision: 0.75 (-9%)
  → Context Recall: 0.80 (-2%)
  结论：RRF 融合提升精度，延迟影响小
```

每次改动都记录指标变化，最后根据业务需求选择最优组合。

同时记录空结果率、fallback 率、rerank 失败率和重复 chunk 率。没有固定数据集时，只能说完成机制，不能声称效果提升。每个结论要结合效果、成本和稳定性，不能只看单一指标。

**可能追问：**

- **为什么基线是完整流水线而不是最简配置？**：因为项目的设计目标就是实现混合检索的完整流水线，消融实验的目的是验证每个组件的贡献和必要性。如果某个组件关闭后指标下降明显，说明该组件是必要的；如果下降不明显但成本降低很多，可以考虑在性能敏感场景关闭该组件。
- **消融实验怎么做？**：基线上逐项增加组件（+Query扩展、+RRF、+rerank），每次只改一项，观察指标变化并归因。
- **多次运行结果不一致怎么办？**：LLM 评估有随机性，应多次运行取均值和方差；方差过大说明评估不稳定或测试集太小，需要扩充样本或固定随机种子。

**补充细节：**

Recall@K 看是否召回关键证据，Precision 看召回内容噪音比例，Answer Relevancy 看答案是否回应问题，Faithfulness 看答案是否基于证据。四项指标组合才能定位问题：召回不足是检索问题，召回噪音大是精排问题，答案不忠实是生成问题。

验证方法：准备 20-50 条标注问题，每条记录预期证据范围或关键事实；同一套问题在不同配置下运行，生成对比报告；人工抽样验证 LLM judge 是否合理。
