## 七、后端工程高频题

### 56. Redis 缓存穿透、击穿、雪崩分别是什么？项目怎么处理？

我觉得这三个问题的本质都是缓存失效导致大量请求直接打到后端，但原因和解决方式不同。

穿透是查询大量不存在的 Key，每次都穿透到后端；击穿是热点 Key 过期瞬间并发查询；雪崩是大量 Key 同时过期或 Redis 故障。

项目中 Redis 主要缓存 Supervisor 规划和 Query 扩展结果。穿透风险：如果用户故意查询不存在的问题，每次都穿透到模型调用，增加成本。处理方式是缓存空结果并设置短 TTL（如 1 分钟），避免相同无效查询反复调用模型。击穿风险：热点问题缓存过期瞬间，大量并发请求同时调用模型。处理方式是用 SETNX 获取分布式锁，只有一个请求去调用模型，其他请求等待或返回降级结果。雪崩风险：大量缓存同时过期或 Redis 故障，所有请求穿透到模型。处理方式是给 TTL 加随机抖动（如 10 分钟 ± 1 分钟），避免集中过期；Redis 故障时降级直接调用模型。

项目已有空值标记、短锁和随机 TTL。缓存数据必须可重建，写操作还要明确更新或删除顺序。Redis 故障时，规划和 Query 扩展可以直接重新计算，业务事实仍从 MySQL 读取。

我认为缓存不是万能的，不能把所有问题都指望缓存解决。如果热点问题本身计算就很贵，除了缓存还要考虑限流和降级；如果 Redis 经常故障，说明容量或配置有问题，要从根本上解决。

**可能追问：**

- **SETNX 锁如何实现？**：`SETNX key lock_value EX 10`，获取锁的请求计算结果并写缓存，其他请求等待或快速失败；释放锁时检查 lock_value 防误删。
- **空值 TTL 为什么要短？**：避免长时间缓存无效数据；如果业务数据可能新增，短 TTL 可以较快感知变化。
- **Redis 完全不可用怎么办？**：规划和扩展直接调用模型，业务数据从 MySQL 读取；监控 Redis 可用性并告警，尽快恢复。

**补充细节：**

缓存更新策略：先更新 MySQL，再删除 Redis 缓存（Cache-Aside）；下次查询时重建缓存。不采用先删缓存再更新库，避免并发读到旧数据又回写缓存。

验证方法：并发查询不存在的 Key，断言空值缓存生效、模型调用次数受限；热点 Key 过期瞬间并发请求，断言只有一个请求调用模型；关闭 Redis，断言降级到直接计算且功能可用。

### 57. MySQL 事务和异步任务怎么配合？

我觉得这个问题的核心是：本地事务只覆盖 MySQL 内部的文档、chunk 和状态写入。事务提交后再启动或投递向量化任务，避免异步线程读取到未提交数据。异步执行使用有界线程池，并记录任务状态、重试次数和错误原因。

项目中文档上传流程是：开启 MySQL 事务 → 插入文档记录 → 插入 chunk 记录 → 更新 BM25 索引 → 提交事务 → 投递异步向量化任务。如果在事务内就投递异步任务，异步线程可能立即查询文档，但事务还未提交，导致查不到数据或读到不一致状态。因此必须先提交事务，再投递任务。

异步任务通过 `CompletableFuture` 或线程池执行，使用有界队列（如容量 1000）防止任务堆积。任务记录文档 ID、批次、状态（pending/processing/completed/failed）、重试次数和错误原因到数据库。失败任务按指数退避重试，超过最大次数（如 3 次）标记为 failed。

如果要支持进程重启后的可靠投递，生产化应使用任务表或消息队列，而不是只依赖内存 `CompletableFuture`。任务领取要有租约、状态锁或乐观锁，防止多个 Worker 重复处理。

我认为事务和异步任务的配合关键是明确边界：事务内保证 ACID，事务外通过状态机和补偿保证最终一致。不要试图用一个大事务把所有操作都包进去，那样会导致锁等待时间长、回滚代价高。

**可能追问：**

- **事务内投递任务有什么问题？**：异步线程可能读到未提交数据（脏读），或者事务回滚但任务已执行，导致不一致。
- **如何保证任务不丢失？**：进程内异步任务，进程崩溃会丢失；生产化应持久化任务到任务表或消息队列（如 RabbitMQ、Kafka），Worker 从队列消费。
- **任务重复执行怎么办？**：用稳定业务键（文档 ID + chunk ID）保证幂等，Chroma 写入时相同 ID 覆盖而非新增。

**补充细节：**

事务和异步配合模式：
```
try {
    beginTransaction()
    insert document
    insert chunks
    commitTransaction()
    // 事务已提交，异步任务可以安全查询
    submitAsyncTask(documentId)
} catch {
    rollbackTransaction()
    // 不投递任务
}
```

验证方法：事务内抛异常，断言异步任务未执行；事务提交后投递任务，断言任务能查询到文档；进程重启前任务未完成，重启后检查任务状态和补偿机制。

### 58. 如何设计文档上传幂等？

我觉得幂等设计要从三个层面考虑：业务层去重、数据库约束兜底、向量存储幂等写入。

项目中幂等设计分三层。第一层是业务去重：计算文件 MD5，查询 `user_id + md5` 是否存在，存在直接返回已有文档 ID。第二层是数据库约束：`users_documents` 表建立 `UNIQUE KEY uk_user_md5 (user_id, md5)`，并发插入时数据库保证只有一个成功，其他返回唯一约束冲突。第三层是向量幂等：Chroma 写入时用 `chunk_id` 作为向量 ID，相同 ID 多次写入会覆盖而非新增，保证重试不产生重复向量。

如果需要接口级幂等，还应引入客户端 `Idempotency-Key` 并保存请求结果。客户端生成唯一 Key（如 UUID），首次请求保存 Key 和结果到 Redis（TTL 24 小时），重复请求直接返回缓存结果。这样即使文件不同但请求重复（如网络重试），也能保证幂等。

MD5 不是万能幂等键，文件内容相同但解析版本或 embedding 模型变化时应重新构建索引。生产化应把 parser_version 和 embedding_model 纳入幂等判断。

我认为幂等不是一次性设计好就完事了，而是要考虑业务演进。比如初期只用 MD5，后来发现模型升级后需要重建，就要增加版本字段；再后来发现需要支持接口重试，就要增加 Idempotency-Key。每一层幂等都有明确的保护范围，不能指望一个机制解决所有问题。

**可能追问：**

- **并发上传如何处理？**：数据库唯一约束兜底，冲突的请求返回错误或查询已有文档返回；前端可以重试或提示"文件已存在"。
- **Idempotency-Key 如何使用？**：客户端生成 UUID 放 Header，服务端首次处理后缓存结果，重复请求直接返回；Key 过期后视为新请求。
- **模型升级后如何重建？**：扫描所有文档，embedding_model 不匹配的标记待重建，异步重新生成向量并覆盖 Chroma。

**补充细节：**

幂等流程：
```
1. 计算 MD5
2. 查询 user_id + md5 → 存在返回
3. 插入文档（唯一约束保护）→ 冲突查询返回
4. 异步向量化（chunk_id 幂等）
5. 重试时跳过已有向量
```

验证方法：并发上传相同文件，断言只有一条记录；重复上传，断言快速返回不重复解析；异步失败重试，断言向量不重复。

### 59. SSE 和 WebSocket 怎么选？SSE 断线怎么办？

我觉得这个选择的核心是看通信模式：如果主要是服务端单向推送，SSE 更简单；如果需要双向频繁通信，WebSocket 更合适。

我认为 SSE 的核心优势是简单可靠，但要处理好断线场景。不能假设连接一直在，也不能把 SSE 当成唯一的状态通道。持久化是根本，推送只是体验优化。

项目中选择 SSE 因为问答流程是单向推送：服务端生成事件（如 `thinking`、`tool_call`、`response`、`done`），客户端只需接收展示。SSE 基于 HTTP，复用现有鉴权和负载均衡，浏览器原生支持 `EventSource`，断线后自动重连。如果用 WebSocket，需要处理握手、心跳、状态同步和连接池管理，复杂度更高。

SSE 连接断开不能丢任务状态。任务和 trace 要先持久化，客户端断线后通过 task 查询接口获取最终状态或重新订阅；事件应带任务 ID 和可去重信息。服务端要处理心跳、超时、客户端断开和后台任务取消，避免连接没了任务还无限消耗模型资源。

项目中每个 SSE 事件包含 `taskId`、`type`（thinking/tool_call/response/done/error）、`data` 和时间戳。客户端断线时服务端检测到连接关闭，停止发送事件但任务继续执行；任务完成后状态和结果保存到数据库。客户端重连后可以查询任务状态，决定是继续等待还是重新订阅。

**可能追问：**

- **SSE 如何检测客户端断线？**：发送事件时捕获 IOException，或定期发送心跳事件（如 `:ping`），写入失败说明断线。
- **任务执行中客户端断线怎么办？**：任务继续执行到完成或超时，状态保存到数据库；客户端重连后查询状态并展示结果。
- **什么场景适合 WebSocket？**：需要客户端频繁发送消息（如实时协作、游戏、双向聊天）、需要服务端主动推送且延迟要求极低的场景。

**补充细节：**

SSE 事件格式：
```
event: tool_call
data: {"taskId":"123","tool":"ragSearch","status":"running"}

event: response
data: {"taskId":"123","content":"根据检索结果..."}

event: done
data: {"taskId":"123","status":"completed"}
```

验证方法：客户端断线后任务继续执行，重连后能查询到完成状态；服务端检测断线并停止推送；多次断线重连不影响任务执行。

### 60. Java 线程池如何设置？

我觉得线程池设置的核心是：先区分 CPU 密集和 IO 密集，再结合 embedding、数据库连接池和外部模型的容量设置并发。必须使用有界队列和明确拒绝策略，监控活跃线程、队列长度、拒绝次数和任务耗时。

项目中有三类线程池。文档向量化线程池用于异步 embedding 和 Chroma 写入，属于 IO 密集，核心线程 10、最大 20、队列 1000、拒绝策略 `CallerRunsPolicy`（降级到调用线程执行）。评估线程池用于批量评估任务，核心 5、最大 10、队列 500。Agent 后台任务线程池用于 Supervisor-Worker 执行，核心 5、最大 15、队列 200。

文档向量化、评估和 Agent 后台任务最好使用隔离线程池，避免评估任务挤占在线问答资源。直接 `new Thread` 无法统一限流、回收、监控和优雅停机。线程池命名便于排查（如 `document-vector-pool-1`），并注册到监控系统上报线程数、队列长度和拒绝次数。

核心线程数参考：IO 密集 = CPU 核心数 × 2~4，CPU 密集 = CPU 核心数 + 1。最大线程数不应过大，避免上下文切换开销。队列长度根据任务积压容忍度设置，过大导致任务等待时间长、OOM 风险，过小导致频繁拒绝。

我认为线程池配置不是一次性的，要根据实际运行情况调整。初期可以保守设置，通过监控观察队列积压、拒绝率、任务耗时，再逐步优化。关键是要有监控和告警，不能设置完就不管了。

**可能追问：**

- **拒绝策略如何选择？**：`CallerRunsPolicy` 降级到调用线程、适合可以慢但不能丢的任务；`AbortPolicy` 抛异常、适合需要感知拒绝的场景；`DiscardPolicy` 静默丢弃、一般不推荐。
- **如何监控线程池？**：暴露 `activeCount`、`queueSize`、`completedTaskCount`、`rejectedCount` 指标到 Prometheus，设置队列积压和拒绝率告警。
- **为什么不用无界队列？**：无界队列可能导致 OOM，任务无限积压也无法及时发现问题；有界队列能暴露容量瓶颈。

**补充细节：**

线程池配置示例：
```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10, // corePoolSize
    20, // maximumPoolSize
    60, TimeUnit.SECONDS, // keepAliveTime
    new LinkedBlockingQueue<>(1000), // 有界队列
    new ThreadFactoryBuilder().setNameFormat("doc-vector-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝策略
);
```

验证方法：提交大量任务，观察活跃线程数、队列长度变化；任务超过容量时断言触发拒绝策略；优雅停机时等待任务完成或超时强制终止。

### 61. 如何定位一次慢请求？

我觉得定位慢请求的关键是分段计时：先用 traceId 拆分排队、数据库、Redis、BM25、向量、rerank、LLM 和 SSE 各阶段耗时，再看 Token、重试和线程池队列。慢 SQL 看执行计划，缓存看命中率，模型调用看上游延迟和输入长度。

项目中每次请求生成唯一 traceId，记录到日志和 trace 表。慢请求排查步骤：第一步查看 trace，按阶段拆分耗时（如检索 500ms、LLM 3000ms、总计 4000ms）；第二步定位最慢阶段，检索慢看 BM25 和向量查询日志，LLM 慢看输入 Token 和模型响应时间；第三步检查是否有重试、降级或队列等待。

常见慢请求原因：BM25 索引未优化、向量库查询超时、rerank 批量过大、上下文 Token 过多（历史未压缩）、模型调用排队、SSE 推送阻塞。优化方向：BM25 索引优化、向量查询并行、rerank 限流、上下文压缩、模型调用异步、线程池扩容。

优化后用相同数据集、模型和并发条件比较 P50、P95、P99、错误率和成本。没有分段指标时先补观测，不能凭感觉改参数。

我认为性能优化最怕的是盲目猜测。看到慢就加缓存、加并发、加机器，结果可能根本不是瓶颈所在。必须先有数据，知道瓶颈在哪里，再针对性优化，最后验证效果。

**可能追问：**

- **如何拆分各阶段耗时？**：在关键节点记录时间戳（开始/结束），计算差值；用 AOP 或拦截器自动记录方法耗时。
- **LLM 调用慢怎么优化？**：压缩上下文减少输入 Token、使用流式响应提前返回、缓存高频问题结果、升级模型或增加并发配额。
- **数据库慢查询怎么排查？**：开启慢查询日志（如 > 1s），分析执行计划（EXPLAIN），检查索引覆盖、回表、全表扫描。

**补充细节：**

Trace 记录示例：
```
traceId: abc123
├─ 鉴权: 50ms
├─ 检索: 800ms
│  ├─ 向量查询: 400ms
│  ├─ BM25: 300ms
│  └─ RRF融合: 100ms
├─ LLM调用: 3000ms (输入2000 tokens)
└─ SSE推送: 200ms
总计: 4050ms
```

验证方法：构造慢请求场景（大上下文、复杂检索），查看 trace 定位瓶颈；优化后对比 P95 延迟下降。

### 62. MySQL 分页和索引怎么设计？

我觉得索引设计的核心是围绕真实过滤和排序场景，不能凭感觉建索引。例如用户文档列表可考虑 `user_id + created_at + id` 联合索引；任务列表要覆盖用户、状态和稳定排序字段。大 offset 分页会扫描并丢弃大量数据，适合改成基于最后 ID/时间的游标分页。

项目中文档列表查询 `WHERE user_id = ? ORDER BY created_at DESC, id DESC LIMIT 20`，建立 `idx_user_created (user_id, created_at DESC, id DESC)` 联合索引，覆盖过滤和排序。任务列表查询 `WHERE user_id = ? AND status IN (?) ORDER BY created_at DESC LIMIT 20`，建立 `idx_user_status_created (user_id, status, created_at DESC)`。

大 offset 分页问题：`LIMIT 10000, 20` 需要扫描前 10020 行再丢弃 10000 行，越往后越慢。改成游标分页：`WHERE user_id = ? AND (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20`，利用索引直接定位起始位置，性能稳定。

排序必须稳定，时间相同用 ID 做第二排序键，否则翻页可能漏数据或重复。最终以 `EXPLAIN` 和实际数据分布验证，不背固定索引结论。

我认为索引不是越多越好，每个索引都有维护成本。应该根据高频查询建立索引，低频查询可以容忍稍慢。而且索引设计要考虑数据分布，如果某个字段区分度很低（比如性别只有两个值），单独建索引意义不大。

**可能追问：**

- **为什么要用联合索引而不是单列索引？**：单列索引只能优化一个条件，联合索引可以同时优化过滤、排序和避免回表，提升查询效率。
- **游标分页有什么限制？**：不能跳页（如直接跳到第 100 页），只能顺序翻页；适合流式加载（下拉刷新）场景。
- **如何验证索引生效？**：用 `EXPLAIN` 查看执行计划，检查 `type` 是否为 ref/range、`key` 是否使用预期索引、`rows` 扫描行数是否合理。

**补充细节：**

索引设计原则：
1. 最左前缀匹配：联合索引 (a, b, c) 可以优化 a、a+b、a+b+c 查询，但不能优化 b 或 c 单独查询
2. 区分度高的列放前面：如 user_id 区分度高于 status
3. 覆盖索引：查询列都在索引中，避免回表

游标分页示例：
```sql
-- 首页
SELECT * FROM docs WHERE user_id = 1 
ORDER BY created_at DESC, id DESC LIMIT 20

-- 下一页（上一页最后记录：created_at=2024-01-01, id=100）
SELECT * FROM docs WHERE user_id = 1 
  AND (created_at < '2024-01-01' OR (created_at = '2024-01-01' AND id < 100))
ORDER BY created_at DESC, id DESC LIMIT 20
```

验证方法：大 offset 分页测试性能（LIMIT 10000, 20），对比游标分页性能；检查 EXPLAIN 执行计划确认索引使用。
